01

まず理解すること

SpecDockは、GitHub Issueに結び付いた仕様をInitiative・Epic・Issueの三階層で扱うCLIです。実行プログラムは通常のPython packageとしてworktree外に導入し、各作業場には仕様と最小限の作業記録を置きます。

対応OSはLinuxとmacOS、Pythonは3.10以上です。他のOSでは業務コマンドを開始せず、変更前にUNSUPPORTED_PLATFORM（終了値3）を返します。help・version・completionは、repositoryや業務用のOS機能に依存せず利用できます。

仕様の正本

Requirement・Design・PlanはGitで共有する一次仕様です。Reportは実施・検証の記録、Artifactは採用前も含む証拠です。

Scopeの番号

新規Scopeは必ずGitHubを使います。GitHubが発行した番号を既存のIDに使い、UUIDやオフライン用の新しい連番を追加しません。

現在の作業

一つのworktreeの直接対象は同時に一件です。親Epic・Initiativeは文脈や集計であり、別の作業を暗黙に開始しません。

並行作業の観測

Gitが列挙する同じcloneのmainとlinked worktreeを必要時に読みます。別clone、別PC、Codexのプロセスは探索しません。

正確な引数は導入版のspec-dock help COMMANDと各leafの--helpで確認できます。本書は外部CLI・直接対象方式の操作を説明します。実装、テスト、レビュー、PR、mergeはそれぞれ独立した完了証拠です。

02

実行プログラムとGitの役割

ここでいう「engine」はCLIを実行するPythonプログラムです。常駐サービスや中央の状態管理サーバーを追加する意味ではありません。package managerでworktree外に導入した一つの実行環境を、どのworktreeからも呼び出します。

spec-dock/scripts/spec-dockはPATH上の外部consoleへ引数、標準出力、標準エラー、終了値を渡すshimです。checkout内PythonやGit共有controlを探しません。外部consoleが見つからないときは導入/PATHを確認します。旧engineへの自動fallbackや自動installは行いません。

Gitのcommon directoryは同じcloneを識別するために読みます。Startの短いOS排他にも既存の物理実体を使いますが、SpecDock独自のデータfile、登録情報、config/refをGit管理領域へ保存しません。branchやworktreeの作成ではGit自身が必要なrefs/index等を変更します。

03

何をどこへ置くか

情報置き場所・権威扱い
CLIのPython実装worktree外の通常packagecheckoutやmain worktreeのcontrolに依存しません。
仕様・metadata・Report各checkoutのspec-dock配下Gitで共有する一次情報です。既存ID/path/linkageを保持します。
Scopeの番号・GitHub完了状態GitHub新規作成はオンラインです。観測できない状態はunknownです。
直接作業対象spec-dock/.agent/work-target/自身のworktreeだけ、ignoredで0または1件。開始時のbranchとScopeを記録します。
文書・template・skill・shim明示したworktreeの静的資産packageが持つ既知path/hashに基づいて導入・更新します。
Syncの集計そのコマンドの出力予約・完了・祖先を都度観測し、index/treeやcacheを保存しません。
保全backup全worktree・Git・installed packageの外新しい絶対pathに保存し、独立した一時場所へ実際に復元して比較します。

直接記録のfile tokenは、捕捉した一件だけを安全に解除するための識別子です。ScopeのUUID、GitHub番号の代替、永続的な操作IDではありません。追跡済み、またはignoreされていない保存先には新しい直接記録を公開しません。

04

用語と状態を区別する

用語意味
main worktreecloneの最初の作業場です。main branchとは別概念で、制御拠点ではありません。
直接対象・選択中そのworktreeが明示取得した一つのScopeです。GitHubがopen/closedか、Codexが稼働中かとは別です。
予約直接記録に残る作業対象です。別branchへcheckoutしても自動解除しません。
論理active・祖先集計整合する直接対象と、現在のmetadataから導く親の文脈です。異なる子Issueは並行して開始できます。
completedGitHubではclosedかつstate_reason=completedです。単にclosedなら常に完了、とは扱いません。
stale / unavailable / invalid対象や祖先を解決できない、読取不能、破損/複数記録等です。emptyに置き換えません。
Artifact / WorkbenchArtifactは証拠、Workbenchはignoredの一時作業です。作成・import・一回copyだけで正本や採用済み判断にはなりません。
partial / unknown一部効果が成立した、または成否を確定できない状態です。成功・未実施と区別します。

GitHubと結び付いた古いlocal綴りのIDは改名しません。既存true-local metadataの読取・Finish互換性も保持しますが、新規local Scopeやオフライン作成を許すものではありません。

05

対象を正確に指定する

Scope ID、GitHub番号/ref/URL、現在の直接対象に基づくdynamic selectorを使います。曖昧な番号、未選択、stale、親チェーン不整合から変更対象を推測しません。必要ならscope show TARGETで明示対象を読みます。

--project ABSは正確なGit worktree rootです。worktree show/remove/bootstrapやinstallationの対象も実体の絶対pathで指定します。独自alias台帳を作りません。同じremote URLでも別cloneはこの観測範囲に含めません。

Artifact所有者の@rootはrepository rootのArtifactに限ります。Scope作成、Start、依存対象に流用しません。Artifact create/importの保存先はJSONのdata.result.artifact.pathを使い、pathを組み立て直しません。

06

Start・Finish・clearの違い

  1. Startの事前確認

    対象と依存のlive readinessを確認します。GitHub照会は短い排他の外で行います。

  2. 短い排他の中で開始を確定

    同cloneの予約を再観測し、重複を確認してbranch作成/checkout、直接記録の公開まで行います。

  3. 作業中の通常操作

    文書編集、Artifact、Sync、Finishに共通Start lockや編集権限制度は設けません。

  4. FinishでIssueを完了

    GitHub完了を確認して、捕捉した直接記録だけを解除します。branchに留まり、後から始まった別対象を消しません。

Gitは同じbranchの同時checkoutを防ぎます。それだけでは、別branchで同じIssueを同時Startする競合を防げません。短いStart排他は重複確認と取得の間の競合だけを防ぎます。通常のfile編集をロックする機能ではありません。

新しいbranchのStartには--base REFが必要です。既存branchを再利用する場合は--branch NAMEを明示し、baseを渡しません。既存refをresetせず、同じ妥当な対象/branchへのStartはunchangedです。

active setは現在の妥当な直接対象と同じ場合だけunchangedです。空・別対象への取得はWORK_START_REQUIREDで停止します。親への暗黙昇格やfocusの第二状態は作りません。

active clearはselectionだけを解除し、Issueを閉じたりbranchを変更したりしません。scope closeはbackend状態だけを変えます。Finishは作業完了なので、未完了作業を引き継ぐために使いません。今回、work releaseという新コマンドは追加しません。

07

通常操作の流れ

作成結果から実際のIDを読み、親を明示します。下のEPIC_ID、ISSUE_ID、BASE_REFは実際に返されたIDと存在するbaseへ置き換えてください。

spec-dock scope create issue --backend github --parent EPIC_ID --title "変更の目的" --json
spec-dock scope show ISSUE_ID --json
spec-dock work start ISSUE_ID --base BASE_REF --json
spec-dock active show --json
spec-dock workspace sync --source github --json
# 実装・検証・レビューと必要な提出を別途完了する
spec-dock work finish ISSUE_ID --yes --json

一つのworktreeでIssue AをFinishした後、Issue BをStartする連続利用は可能です。A/Bを同時に直接選択することはできません。同じEpic配下の異なるIssueを別worktreeで開始すれば、Syncが各予約と祖先件数を集計します。

Syncの既定sourceはlocalです。GitHubを読んでいなければGitHub状態はunknownです。--source githubを明示すると現在状態を照会します。出力のdata.completeとfindingsを読み、process_state=not_observedを実行中の証拠にしません。

08

途中失敗を正直に扱う

新しい永続journalやresume/rollback操作はありません。実体、Gitの原文エラー、返されたeffects、残った候補とbackupを確認してから、次の明示操作を判断します。自動checkout、branch削除、reset、stash等による巻戻しを行いません。

終了値意味確認すること
0成功、unchanged、dry-runのplannedstatus、実際の結果、effectsを読みます。
1効果前の内部不具合診断を保全し、不具合を調べます。
2文法や廃止optionの診断現在helpの文法へ戻ります。旧journal optionを付けません。
3事前条件が満たされない対象・予約・readiness・保全・確認を調べます。
4明示local対象が存在しない正確な対象を確認します。通信失敗を不存在とみなしません。
5変更効果のない実行失敗errorと実体を読み、成功を仮定しません。
6一部効果が成立、またはunknownsucceeded / unknown / not_attemptedを区別し、残存pathとbackupを保全します。
7必要な観測や検証が不完全complete=falseやfindingsを読みます。不明なworktreeをemptyと見なしません。

Gitのargv/stdout/stderr/returncodeを保持します。checkout後に記録公開が失敗したときも、成立したGit効果を隠しません。GitHub応答が不明なら、Issue作成やcloseが未実施とは断定せず、自動的に再作成しません。

--yesは通常のCLI確認を省略するだけで、破損・重複・対象安全性・backup要件を迂回しません。--dry-runは変更計画で、書込み、backup作成、GitHub更新、Start lock取得を行いません。

09

導入・移行・静的資産更新

レビュー・通常試験が済んだwheelを、例えばuv tool install /absolute/path/spec_dock-VERSION-py3-none-any.whlでworktree外に導入します。packageの更新と、checkoutの静的資産更新を別操作として扱います。

spec-dock installation init /absolute/project --dry-run --json
spec-dock installation init /absolute/project --yes --json
spec-dock installation show --target /absolute/project --json

initは明示した一つのGit worktreeに文書・template・skill・shimとworkspace宣言を置きます。既存の配布先fileがあれば書込み前に停止します。Python runtime、直接記録、Git内の独自領域は作りません。

旧schema3 writerの移行では、旧writerと自動起動を停止し、仕様・ignored成果物・旧Git独自領域を含む実体の外部保全と復元確認を先行します。raw doctorで分類し、自workspace宣言だけを新protocolへ切り替えます。旧activeを新しい予約へ取り込みません。

spec-dock --project /absolute/project workspace doctor --raw --legacy --json
spec-dock --project /absolute/project workspace migrate --to-schema 3 --to-writer-protocol specdock.worktree-writer/v1 --dry-run --json
spec-dock --project /absolute/project workspace migrate --to-schema 3 --to-writer-protocol specdock.worktree-writer/v1 --backup-dir /absolute/new-migration-backup --confirm-old-writers-stopped --yes --json
spec-dock installation update --target /absolute/project --backup-dir /absolute/new-static-backup --yes --json

static updateは現在/既知旧hashだけを更新し、既知旧runtime filesを一件ずつ退役させます。ユーザー改変はmanual mergeへ戻します。backupには変更する旧bytes/modeだけを保存し、独立した一時場所へ復元して比較します。directory単位の削除はしません。

uninstallは正確な対象とtool資産削除の明示許可がある場合だけ使います。既知static filesを保全して削除し、workspace、ignore規則、仕様、Artifact、Workbench、直接記録、未知file、directoryを残します。schema3未満、未知protocol、旧writer停止未確認は適用対象にしません。

詳しい条件は導入・移行・保全で確認できます。旧engineの実行、Git controlの更新、journal replay、全worktree一括書換えを移行手順に戻しません。

11

この方式が保証する範囲

協調して新CLIを使う同じphysical cloneのStartを直列化します。旧writer、任意の手編集、別clone、別PC、複数ホストの共有filesystemを完全に封鎖する仕組みではありません。未対応のOS/FS原語は成功と装わず停止します。

main worktreeは制御拠点ではありません。読み取れない作業場、stale、破損、複数記録は診断に残します。Startの重複確認が完全でなければGit変更前に停止します。別branchへ移った直接記録も予約として捨てません。

既存の仕様・ID・GitHub linkage・成果物を保全します。破壊的操作には正確な対象と削除等の明示的な許可が必要です。PR mergeは人間が行います。Finishの成功だけを、実装・テスト・Strict review・mergeの合格証拠にしません。

12

詳細へ進む

  • CLI参照：44 leafと引数、JSON、Start/Finish。
  • worktree参照：native Git一覧、作成、bootstrap、削除。
  • 状態の観測と検証：Sync、working tree/CI validate、doctor。
  • GitHub参照：番号、ref、完了とunknown。
  • 依存参照：宣言/継承、readiness。
  • 命名と識別子：既存ID、branch、捕捉token。
  • 文書作成ガイド：Requirement、Design、Plan、Report、Artifactの役割。
  • 文書の入口：CurrentとHistoricalを区別して読む。

本書はpackageに同梱する日本語の操作ガイドです。外部script・font・通信を使わない単独HTMLとして開けます。既存の会話、古いengine/controlの操作説明、Historical資料を新CLIのauthorityにしません。
