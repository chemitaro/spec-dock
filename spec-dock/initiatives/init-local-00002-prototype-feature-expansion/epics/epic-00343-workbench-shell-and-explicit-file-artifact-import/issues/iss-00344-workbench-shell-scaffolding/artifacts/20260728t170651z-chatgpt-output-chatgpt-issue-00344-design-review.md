# Issue 344 Design Review

## Verdict FAIL

**FAIL**。指定ブランチは指定コミット `e2ba9dde7acfc5325ba12a6ea3de85922a3faeef` と同一であり、そのコミット上の Issue 設計を対象にレビューした。freshness / no-backfill、semantic opacity、既存 `workbench copy`、prune / package、docs、rollback、sibling Issue 境界の大枠は親 Epic と整合している。

ただし、承認済み要件に対する **blocking design contradiction が3件**残るため、design phase の昇格は認められない。

## Findings

### BLOCKING B-001 — 提案された `.gitignore` 規則では、宣言した entry-type 契約を満たせない

設計は次の二行を exact contract とし、direct child の regular `README.md` だけを再包含し、同名の directory と symlink は引き続き ignore されると規定している。

```gitignore
**/.workbench/*
!**/.workbench/README.md
```

しかし Git ignore の否定規則は pathname に適用され、regular file、symlink、directory を区別しない。このため、正確な path が `.workbench/README.md` であれば symlink も再包含される。また、その path が directory の場合、配下 entry が status surface に現れ得る。

承認済み要件は top-level `.workbench/README.md` だけを tracking 可能とし、その他の entry、nested `README.md`、case variant を ignore することを要求する。設計自身はさらに directory / symlink の除外を `[N]` としているため、規則と設計保証が内部矛盾している。

**必須訂正:**

1. tracking 契約が「pathname identity」なのか「direct regular file」なのかを明示する。
2. direct regular file のみを許す場合、`.gitignore` 単独では symlink を区別できないため、追加の enforcement boundary を設計する。
3. exact path に対する regular file、symlink、directory、directory descendant の real-Git matrix を `TC-344-004` に明記する。
4. pathname-only 契約へ緩和する場合は、承認済み requirement の意味変更となる可能性があるため requirement phase へ戻す。

---

### BLOCKING B-002 — requirement が要求する canonical README 完全本文が design で固定されていない

承認済み requirement は、README の **exact wording を design で固定する**と明記している。

現在の design は、9つの guidance element、exact command spelling、root / node copy 境界を列挙しているだけで、配布する完全な Markdown 本文を示していない。さらに、exact wording は可読性の範囲で後から調整可能としており、requirement の固定条件と反する。

親 Epic design の例示本文も代替の正本にはできない。親の例示は `spec-dock artifact import file` という global CLI に見える表記を含み、Issue requirement が後から固定した repo-local exact invocation と root / node helper distinction を満たしていない。

**必須訂正:**

* design に4 asset共通の完全な canonical Markdown 本文を掲載するか、同一コミット内の単一 canonical byte sourceを normative pathとhashで固定する。
* 本文について、UTF-8、newline、末尾 newline、placeholder token 不在を固定する。
* `./spec-dock/scripts/spec-dock artifact import file ...`、node-scoped helper、root exclusion、evidence-only authority を本文そのものでレビュー可能にする。
* wording 変更は design amendment と fresh review を要する契約へ変更する。

---

### BLOCKING B-003 — root と node の materialization seam が generated byte identity を保証していない

design は、root README を既存 installer copy seam で配置し、Initiative / Epic / Issue README は既存 `copy_scaffolded_tree` の generic recursion で生成する。その一方で、生成された4 README の byte identity を normative guarantee としている。

現行コードでは両 seam の byte semantics が異なる。

* installer の `_copy_file` は `shutil.copy2` により source bytes をそのまま複製する。
* node scaffolder は UTF-8 text として読み、placeholder replacement を適用して、text として再エンコードする。

この差により、placeholder token、newline normalization、platform text-write semanticsによって root と node の bytes が異なる可能性がある。byte parity test は差を検出できるが、設計上の保証手段そのものにはならない。

**必須訂正:**

* 4出力に共通する byte-stable materialization contract を固定する。
* 推奨は、Workbench README を opaque provider asset とし、root / node とも generic な byte-copy pathで配置する方式である。
* text rendering を維持する場合は、root と node の双方を同じ normalization function に通し、encoding、newline、placeholder prohibitionを normativeに固定する。
* README 固有の semantic branchを追加しないという既存方針は維持し、必要な変更は generic scaffold primitiveとして設計する。

### NON-BLOCKING NB-001 — exact five-file inventory の探索 root が不明確

requirement と親 Epic design が意図しているのは、`assets/spec_dock/templates/**/README.md` に対する exact allowlist である。

Issue design の「source / wheel / normalized sdist / installed resources の README inventory は5 fileだけ」という記述は探索 root が省略されており、package 全体の README inventory と読める。package には docs 等の別 README が存在するため、その解釈では成立しない。

現行 `_prune_legacy_scaffold` は `templates/README.md` 以外の nested README を削除し、`pyproject.toml` も broad nested README exclusion を持つため、対象 subtree の明示は実装上も重要である。

**訂正案:** source、wheel、sdist、installed resource ごとに正規化後の探索 rootを `spec_dock/assets/spec_dock/templates` と明記し、その rootからの相対 path 5件を列挙する。

## Scope and consistency checked

### Freshness / no-backfill

pre-mutation の `os.path.lexists` 相当で freshness を一度だけ固定し、file、directory、symlink、empty directory を existing と扱う設計は requirement と整合する。existing `init --force` / update は managed provider assetsを更新できる一方、root READMEを生成しない境界も適切である。

### Four README assets

root / Initiative / Epic / Issue の4 explicit provider asset、future node の generic recursion、ancestor / sibling no-backfillという責任配置は親 Epic と一致する。ただし、完全本文と byte-stable materialization が未確定であるため B-002 / B-003 が blocking となる。

### Git-ignore behavior

nested `README.md`、case variant、near-name pathを除外する pathname設計は要件方向と一致する。regular / symlink / directory の型区別だけが B-001 として未解決である。

### Semantic opacity

現行 provider source は exact `.workbench` subtree を metadata walk開始前に pruneしており、current testsも fake metadata の非発見と descendant accessの抑止を固定している。Issue design がこの実装を read / verify only とする判断は妥当である。

### Node-scoped source-wins copy / root exclusion

現行 application contract は full Initiative / Epic / Issue IDのみを受け取り、root routeを持たない。filesystem mergeは source entryを再帰処理し、source file / symlinkを優先しつつ destination-only entryを保持する。

current testsも `--root`、`--from`、`--date`、`--path` の拒否、node-scoped copy、copied metadata / ADR / dependency content の opacityを確認する構造になっている。

### Prune / packaging

current broad pruneとpackage exclusionを exact allowlistへ狭め、4 hidden READMEを package dataへ明示追加する方向は正しい。NB-001 の探索 root表現を除き、親 Epic ownershipと整合する。

### Docs / rollback / sibling Issue boundaries

provider-first の4 docs、generic importを Issue 345 の未実装機能として扱う境界、ignore ruleを先に戻す rollback、generated / user Workbench contentを自動削除しない方針は妥当である。Issue 345へのgeneric import、Issue 346へのcandidate-wheel consumer E2E、dogfood、full regression、最終送達の委譲も親 Epic planと一致する。

### Standard-grade completeness

traceability、normative design delta、failure handling、security / authority、responsibility table、verification obligations、rollback、sibling handoff、open-question sectionは備わっている。ただし、B-001〜B-003はいずれも `[N]` contractを実装前に一意化できていない問題であり、Standard designとして planへ渡せる完全性に達していない。

## Residual risks

* hidden `.workbench/README.md` の wheel / sdist / installed-resource収録挙動は、build artifactによる後続検証対象のままである。これは設計上明示された residual riskであり、現時点の実測済み事実ではない。
* exact README本文が未固定なため、replacement token混入、command spelling drift、root helper誤認、authority wording driftを現設計だけでは排除できない。
* 本レビューでは source と current testsを静的に点検したが、pytest、Git matrix、wheel / sdist buildは実行していない。
* report上も design gate は pending / blocking と記録されており、implementation evidenceはまだ存在しない。

## Promotion decision

**design phase から plan phase への昇格不可。**

B-001について pathname / regular-file 契約を確定し、必要なら requirement phaseへ戻す。続いて canonical README完全本文とbyte-stable materialization contractを designへ固定し、NB-001のpackage inventory rootを明確化した後、fresh design reviewを行う。

本判定は **advisory / evidence-only** であり、実装、テスト合格、PR、merge、Issue完了を示さない。
