# epic-00424 Centralize Specs On Canonical Branch And GitHub Issues — 要件定義

詳細: [Requirement Guide](../../../../docs/authoring/requirement.md)

表示名：仕様の正本を `spec-dock/canonical` ブランチと GitHub Issue に集約する

## 目的

仕様の最新の状態を、どのPC・どのworktree・どのエージェントからも、同じ1か所で読み書きできるようにする。その仕組みを SpecDock に加え、spec-dock 自身で使い始める（dogfooding）。

- 仕様の内容（要件・設計・計画・報告・Artifact）の正本を、コードと履歴を共有しない1本のブランチ `spec-dock/canonical` に置く。
- 仕様の構造（番号・種類・親子・依存・状態・題名）の正本を GitHub Issue に置き、`.meta.json` を廃止する。
- 保存と同期を、人やエージェントが意識しない SpecDock の定期の仕組みに任せる。
- 既定のブランチ（main など）とその系列には、仕様を一切置かない。
- GitHub の構造を、リポジトリごとに一括で取得して手元に持ち、使い回す。操作のたびに GitHub に問い合わせず、GitHub の負荷と待ち時間を抑える。
- 今までと同じ Markdown と PlantUML のダッシュボードを、GitHub の構造から作り直す。
- 利用者のすべてのリポジトリ（R-J1 の5つ）を新しい仕組みに移し、従来の仕組みのコードを撤去して、SpecDock を1つの仕組みだけにする。

利用者のほかのリポジトリの移行と、従来の仕組みのコードの撤去も、この Epic で行う（2026-10-25 に利用者が決めた。それまでは、各プロジェクトに任せ、撤去は別の Epic で行う予定だった）。第三者のリポジトリの移行の支援は含めない。HTML のダッシュボードと、仕様の文書の CUE と HTML への移行は、次の Epic（epic-00425）で行う。この Epic は、その土台になる1か所の正本と、構造の一括取得の仕組みを作る。

## 背景

### 解く問題

今は、仕様のツリー `spec-dock/initiatives/` を、既定のブランチとすべての作業ブランチが追跡している。そのため、次のことが起きている。

- 仕様の最新の状態が、worktreeとブランチごとに分かれ、中央で全体を把握できない。
- ほかのworktreeの書きかけや、マージ前の更新が見えない。反映にはPRのマージが必要になる。
- ブランチを消すと、そのブランチにしかない仕様が失われる（孤児のScope）。
- 構造の情報が `.meta.json` にだけあり、GitHub と食い違っている。GitHub には親子も依存も登録されていない。spec-dock では、`.meta.json` の題名が GitHub の題名と36件食い違う。

### 利用の実態（このPC、2026-10-25 時点）

- 仕様の編集は286回。そのうち263回が、Orca や Codex の作業用worktreeの通常のセッションによるもので、mainのチェックアウトからは23回、隔離されていないサブエージェントからは3回だった。
- Claude Code の隔離セッション（`--worktree`）は、一度も使われていない。

### 関係者

- 利用者（人）：仕様を確認し、判断し、PRをマージする。HTMLの説明資料で議論する。
- エージェント（Claude Code、Codex。Orca から起動されることが多い）：仕様を読み書きし、コードを実装する。
- SpecDock を使うリポジトリ：利用者の5つのリポジトリ（spec-dock、退去費用プロダクト、housing-lifecycle、input-devices、company-os。R-J1）。どれも利用者1人が使っていて、この Epic で、すべて移行する。
- 複数のPC：同じリポジトリを、別々のPCで同時に扱う。

### 使いやすさの約束

利用者の方針（2026-10-25）は、複雑にしすぎず、簡単に使え、エージェントが迷わず、複雑な設定が要らないことである。これを次の5つの約束にする。以下の要件は、すべてこの約束に従う。

1. **仕様はいつもの場所にある**：仕様は今と同じ `spec-dock/initiatives/` にあり、普通のファイルとして読み書きする。仕様のために Git を操作することはない。
2. **用意はコマンド1つ**：`spec-dock canonical link` を実行すれば使える。何度実行しても同じ結果になる。
3. **自動で動くのは定期の同期だけ**：保存、取り込み、push と、GitHub の構造の取り直し、ダッシュボードの作り直しは、PCごとの定期の同期が行う。Claude Code や Codex のフックには頼らない。
4. **ツールの設定を書き換えない**：要るのは、作業用のworktreeから仕様に触れるための、ツールごとに1行の設定だけ。SpecDock は、その1行を正確に示すだけにする。
5. **おかしいときは止まり、次の1手を示す**：推測で直さず、実行すべきコマンドか、足すべき設定を示す。

### 前提とする検証

検証した事実は、Artifact [検証済みのGitとGitHubの挙動](artifacts/20261025t080353z-research-verified-git-github-behaviors.md) にまとめた。先行の分析と設計の草案（v0.8）は、同じ `artifacts/` にある3つのHTML資料で、証拠として扱う。

## 観測可能な要件

### A. 正本の置き場

- **R-A1 内容の正本**：仕様の内容は、`spec-dock/canonical` ブランチだけに置く。このブランチは、既定のブランチと共通の祖先を持たず、仕様のツリーと、SpecDock が管理する少数のファイル（無視の設定、正本であることを示す README、形式の版）だけを含む。
- **R-A2 構造の正本**：番号、種類、親子、依存、状態、題名は、GitHub Issue だけに置く。親子は sub-issue、依存は blocked by、種類はラベル（`spec-dock:initiative`、`spec-dock:epic`、`spec-dock:issue`）、識別名（slug）は本文の印で表す。種類のラベルのない Issue は、Scope として扱わない。`.meta.json` は廃止する。
- **R-A3 入れ子は写し**：canonical のディレクトリの入れ子は、GitHub の親子を見やすく写したものとする。両者がずれたときは GitHub に合わせる。人やエージェントが手でディレクトリを動かしても、正本の変更とは見なさない。
- **R-A4 既定のブランチに仕様を置かない**：既定のブランチと、そこへ入るPRのツリーには、`spec-dock/initiatives` と `spec-dock/.canonical` の下のパスと `.meta.json` が1つもない（ファイル、リンク、gitlink を含む）。canonical と既定のブランチの間では、同期も、コピーも、マージもしない。
- **R-A5 版の違う SpecDock から壊さない**：移行したリポジトリに、移行前の版の SpecDock が書き込もうとしても、書き込む前に止まる。canonical は形式の版を持ち、SpecDock は自分より新しい形式には書き込まない。
- **R-A6 移行の間だけ、移行していないリポジトリは今のまま動く**：SpecDock のパッケージは、PCのユーザーごとに1つで、すべてのリポジトリが共有する。そのため、0.3.0 は、移行していないリポジトリ（ワークスペースの宣言の版が今の3）では、今と同じに動く。新しい仕組みは、移行したリポジトリ（宣言の版が4）でだけ動く。これは、R-J1 のリポジトリを移し終えるまでの、移行の間だけの扱いである。今の動きを残す部分は、改善も変更もしない。すべてのリポジトリを移したら、この Epic の中で撤去する（R-J6）。

### B. 用意と診断

- **R-B1 カタログ**：クローンごとに1つ、mainのチェックアウトの `spec-dock/.canonical/` に canonical のworktree（以下、カタログ）がある。誤って消されないよう保護され、Git では追跡も表示もされない。mainのチェックアウトがない構成（bare）は対象外で、理由を示して止まる。
- **R-B2 リンク**：各チェックアウトの `spec-dock/initiatives` は、カタログを直接指すリンクにする。mainのチェックアウトでは相対、作業用のworktreeでは絶対のパスを使う。リンクのリンクは使わない。リンクとカタログは Git で管理しない、そのPCの作業環境とする。
- **R-B3 用意のコマンド**：`spec-dock canonical link` は、同じクローンのどのチェックアウトから実行しても、そのクローンのmainのチェックアウトとカタログを見つけ、次を済ませる。何度実行しても結果は同じで、行ったことと、利用者に残る作業（R-B6 の設定）を表示する。
  - カタログがなければ、GitHub の canonical から作り、保護する。
  - Git の除外の設定を足す。
  - mainのチェックアウトと、実行したチェックアウトに、リンクを張る。
  - このPCの定期の同期に、カタログを登録する（定期の実行がなければ作る）。
  - リンクを置く場所に実体のファイルやディレクトリがあるとき（移行前のコミットなど）は、置き換えずに止まり、理由を示す。
- **R-B4 呼ばれる場所**：SpecDock の `worktree create` と `work start` は、中で同じ処理を行う。Orca、Codex、Claude Code、`git worktree add` で作ったworktreeでは、`spec-dock canonical link` を1回実行する。プロジェクトの `make init` などへ組み込むかどうかは、各プロジェクトが必要に応じて決め、SpecDock はそれを前提にしない。
- **R-B5 足りないときの案内**：仕様を使う SpecDock のコマンドは、リンクやカタログがない、または壊れているとき、自分では直さずに止まり、実行すべきコマンドを示す。読むだけのコマンドは、何も書き込まない。
- **R-B6 ツールの設定**：作業用のworktreeから仕様に触れるには、ツールごとに1行の設定が要る（Claude Code の既定の権限モードと acceptEdits では `additionalDirectories`、Codex のサンドボックスでは `writable_roots` に、カタログのパスを加える）。SpecDock は、足りないことを見つけ、そのクローンでの正確な1行を示す。利用者が、その1行を1回だけ手で足す。SpecDock は、導入や更新のときも含めて、ツールの設定を書き換えない。mainのチェックアウトの中で動くセッションは、設定なしで使える。Claude Code の隔離セッション（`--worktree`）では、仕様を読むだけにする。この設定は、使い方の文書にも記録する（R-H3）。
- **R-B7 状態と診断**：状態を表示するコマンドが、カタログ、保護、リンク、除外の設定、このプロセスからの読み書きの可否、未保存・未push・保留・競合、最後に成功した同期の時刻、形式の版、定期の実行の状態を示す。問題ごとに、次の1手を1つ示す。
- **R-B8 取り外し**：未保存と未pushの変更がないことを確かめてから、リンク、カタログ、除外の設定、定期の同期の登録を外せる。破壊的な操作なので、対象と結果を明示した指示がいる。

### C. 保存と同期

- **R-C1 定期の同期**：PCのユーザーごとに1つの定期の実行が、登録されたすべてのカタログについて、変更を保存し、GitHub と統合して push する。誰が書いた変更かは問わない。既定の周期は60秒で、変更のない周期はコミットしない。保存の経路はこの1本だけとする。カタログのコミットでは、リポジトリのコード用のフック（`pre-commit` など）を動かさない。
- **R-C2 書きかけの扱い**：30秒以上変わっていないファイルを保存する。変わり続けるファイルも、5分たてば保存する。
- **R-C3 先着優先**：push の前に必ず取り込み、後から push する側が差分を解消する。同じファイルが競合したときは、先に push された版を元の名前に残し、後から push する側の版を `<名前>.conflict-<PC名>-<時刻>.<拡張子>` として隣に保存する。変更と削除がぶつかったときは、変更を残す。カタログに競合のマーカーやマージの途中の状態を残さず、rebase と強制 push は使わない。
- **R-C4 保留**：大量の削除、秘密情報らしいもの、大きすぎるファイルは、自動では保存しない。保留して知らせる。SpecDock のコマンドが行った削除は保留しない。
- **R-C5 リモートの書き換えを受け入れない**：GitHub の canonical が、最後に確認した版の子孫でなくなったら（強制 push や削除）、同期は取り込まずに止まり、知らせる。
- **R-C6 保存の確認**：push していないコミットが10分を超えると、状態の表示で警告する。`work finish` は、その Scope の仕様の変更が push されたことを確かめてから終わる。確かめられないときは、理由を示して止まる。
- **R-C7 動く環境**：macOS と Linux で、同じ要件を満たす。Windows には対応しない。定期の同期は、環境に合った仕組みで動かす。
  - macOS：launchd。
  - systemd が動く Linux（デスクトップ、SSH で入るサーバーや仮想マシン）：systemd のユーザーのタイマー。ログアウトしている間も動かすのに要る設定（linger）が足りなければ、状態の表示で知らせる。SpecDock は、その設定を変えない。
  - systemd のない Linux（コンテナ、devcontainer）：SpecDock 自身の常駐のプロセス。`spec-dock canonical link` が起動し、1つの環境に1つだけ動く。コンテナを起動し直したときに動かすための1行を示す。
- **R-C8 マウントしたチェックアウト**：コンテナの中では、コンテナの中でクローンしたリポジトリを、別のPCと同じに扱う。ホストのフォルダーをマウントしたチェックアウトでは、SpecDock は、ホストの Git の記録を書き換えずに、理由を示して止まる（この Epic では、それ以上に対応しない）。

### D. 同時に動く操作

- **R-D1 PCの中の排他**：定期の同期と、カタログに書く SpecDock のコマンドは、互いの途中の状態を保存しない。1つのコマンドの変更（ディレクトリの移動とリンクの書き換えなど）は、1つの単位として保存される。排他の中ではネットワークを使わず、ほかの操作を長く待たせない。SpecDock のコマンドは自分ではコミットしないので、サンドボックスで動くエージェントから実行しても、同じ結果になる。
- **R-D2 PCの間**：PCどうしには排他を置かない。調整は R-C3 の先着優先だけで行う。

### E. 名前

- **R-E1 識別**：ID と slug は、英小文字・数字・ハイフンだけにする。ディレクトリ名、ブランチ名、URL に使い、作成したときに固定する。
- **R-E2 表示**：題名（GitHub の Issue の題名）は、日本語を含む任意の言語でよく、いつでも変えられる。題名を変えても、slug、ディレクトリ名、ブランチ名は変わらない。
- **R-E3 日本語の題名で作る**：Scope の作成で、日本語の題名を受け付ける（今の CLI は英数字しか受け付けない）。題名に英数字以外の文字が含まれるときは、slug の指定を必須にする。
- **R-E4 表示に使う**：Scope の一覧と状態を示す CLI の表示（`scope show`、`scope list`、`workspace sync` など）と、ダッシュボード（R-E5）は、GitHub の題名を使う。
- **R-E5 ダッシュボード（今までの形）**：canonical モードでは、定期の同期が、構造のスナップショット（R-I1）から、今までと同じ5つのファイル（`spec-dock/dashboard.md`、`tree.puml`、`tree-all.puml`、`deps-issues.puml`、`deps-raw.puml`）を、mainのチェックアウトに作り直す。形は今までと同じ Markdown と PlantUML で、題名は GitHub の題名（日本語を含む）、作業中は GitHub の作業中の印から示す。構造が変わったときだけ書き直す。今の CLI は、2026-10-01 の変更でこの生成をやめていた（調査の記録）。従来モードでは、今のまま生成しない（R-A6）。HTML のダッシュボードは、次の Epic（epic-00425）で作る。

### F. 既定のブランチの検査

- **R-F1 検査のコマンド**：SpecDock の1つのコマンドが、チェックアウトの追跡されたツリーを調べる。R-A4 のパスがないこと、無視の設定と SpecDock の宣言がそろっていること、SpecDock の配布物が壊れていないことを確かめる。カタログ、GitHub への書き込み、秘密の情報がなくても動き、CIでそのまま使える。
- **R-F2 独立のワークフロー**：SpecDock は、R-F1 を実行する独立した GitHub Actions のワークフローの見本を配る。各プロダクトのテスト、ビルド、デプロイのCIと同じ仕組みで、PRをきっかけに動き、結果をPRに表示する。既定のブランチへの push でも動く。ワークフローの定義は短く保ち、検査の中身は SpecDock のパッケージが持つ。SpecDock の版を上げても、ワークフローを書き換えなくてよい。R-J1 の各リポジトリへは、その切り替えのPRで組み込む（R-J5）。
- **R-F3 マージの条件**：このワークフローの通過を、PRをマージする条件にする。扱いは、退去費用プロダクトのテストやデプロイのCIと同じ運用にする。人は通過を確かめてからマージし、エージェントは通過していないPRを、マージできる状態として渡さない。GitHub の必須の検査（ブランチの保護やルールセット）は前提にせず、spec-dock でも設定しない。

### G. 移行

- **R-G1 使い捨てのスクリプト**：`.meta.json` から GitHub への構造の登録、検証、canonical の作成、既定のブランチからの仕様の切り離しは、直接実行するスクリプトで行う。SpecDock の CLI とパッケージには入れず、保守もしない。R-J1 のすべてのリポジトリの移行の後、撤去（R-J6）のときに消す。
- **R-G2 安全に止めて再開できる**：スクリプトは、既定では予定を表示するだけで、何も書き込まない。何度実行しても同じ結果になり、途中で止まっても続きから再開できる。GitHub には足すだけで消さず、取り消しの一覧を残す。GitHub の書き込みの制限を超えない速さで進む。
- **R-G3 先に登録できる**：GitHub への登録は、切り替えより前に済ませられる。登録しても、今の CLI での運用は壊れない。
- **R-G4 データの異常を見つける**：予定の表示は、循環する依存、種類の規則の違反、閉じた親の下の開いた子、ID と番号の不一致（`init-local-00002` は #39、`init-local-00003` は #31）、GitHub との題名の食い違いを一覧にする。
- **R-G5 移行前のブランチ**：移行前に作ったブランチの仕様は、マージの前に canonical へ取り込める。取り込んだ後、ブランチから仕様のツリーを外し、PRを仕様を含まずにマージできる。
- **R-G6 手順書**：リポジトリを移行するときの手順を、スクリプトの横に短く書く。この Epic の各リポジトリの移行は、この手順書に従って行う。

### H. エージェント向けの規則

- **R-H1 短い規則**：配布するスキル（`.agents/skills/spec-dock/SKILL.md`）と AGENTS.md に、エージェントが守る規則を1つの短い節にまとめる。設計書を読まなくても、その節だけで仕様を読み書きし、検索し、競合を解消できる。節には、次のことを書く。
  - 仕様は `spec-dock/initiatives/` にあり、普通に読み書きする。仕様は Git で扱わない（add、commit、stash、reset をしない）。保存と共有は自動で行われる。
  - 仕様が見えないときは `spec-dock canonical link` を実行する。読み書きを拒否されたときは、状態の表示が示す1行の設定を利用者に伝える。
  - 検索では、パスを明示する（`rg 語 spec-dock/initiatives/`）。
  - 構造（作成、親子、依存、状態、題名）は、SpecDock のコマンドだけで変える。
  - `*.conflict-*` のファイルがあれば、中身を元のファイルに統合し、消す。
  - Claude Code の隔離セッションでは、仕様を読むだけにする。
  - 作業を終えるときは `work finish` を使う。
- **R-H2 次の1手を示す**：SpecDock のエラーの文言は、次に実行すべきコマンドか、足すべき設定を含む。
- **R-H3 使い方の文書**：利用者向けの使い方の文書（README と、配布する `spec-dock/docs/` の導入の文書）に、Claude Code と Codex で設定の変更が要ることを記録する。ツールごとに、次のことを書く。
  - 足す設定（Claude Code は `permissions.additionalDirectories`、Codex は `writable_roots`）と、設定のファイルの場所、書き方の例。
  - 足さないと何が起きるか（拒否されるときの文言）。
  - 要らない場合（mainのチェックアウトの中で動くセッション）と、書けない場合（Claude Code の隔離セッション）。
  - 足りているかの確かめ方（R-B7 の状態の表示）。

### I. GitHub の構造の一括取得

利用者の方針（2026-10-25）は、GitHub への要求を操作のたびに行わず、一括で取得したデータを使い回して、GitHub の負荷（二次のレート制限を含む）と待ち時間を抑えることである。

- **R-I1 一括取得と保持**：SpecDock は、GitHub のリポジトリごとに、Scope の Issue（種類のラベルのある Issue）の構造（番号、種類、題名、状態、ラベル、担当者、slug、親子、依存）を一括で取得し、PCのユーザーごとの置き場に1つのファイル（構造のスナップショット）として持つ。ファイルに書けない環境（サンドボックスの中など）では、そのプロセスのメモリーの上だけで持つ。
- **R-I2 使い回す**：構造を読む SpecDock のコマンドとダッシュボードは、スナップショットから読む。1つのコマンドのために、GitHub の Issue を1件ずつ読み直さない。
- **R-I3 新しく保つ**：定期の同期が、GitHub のレート制限を消費しない「変わったか」の確かめを周期ごとに行い、変わっていたときだけ全体を取り直す。親子と依存だけの変更を見落とさないよう、少なくとも30分に1回は全体を取り直す。SpecDock のコマンドが GitHub に書いた変更は、書いた直後にスナップショットに反映する。表示には、取得した時刻を示す。
- **R-I4 判断は確かめてから**：GitHub に書く判断（着手、完了、依存の追加、親の変更、削除）の前には、「変わったか」を必ず確かめ、対象の Issue を GitHub から読み直す。古いスナップショットだけで書く判断をしない。GitHub につながらないときは、表示は古いスナップショットで続け（古いことを示す）、書く操作は止まる。
- **R-I5 負荷を抑える**：GitHub への要求は、並べずに1つずつ送る。書き込みを続けて送るときは、1秒以上の間をおく。レート制限の応答（`retry-after` など）には、GitHub の文書のとおりに従う。
- **R-I6 次の Epic の土台**：スナップショットの形式は、版を持つ契約として設計書に書く。次の Epic（epic-00425）の HTML のダッシュボードは、このファイルを読んで使う。

## 失敗・境界条件

- **mainで移行前のコミットへ移る**：リンクが実体のディレクトリに置き換わる。カタログは残る。戻ったときに、`spec-dock canonical link` がリンクを作り直す。
- **`git clean -ffdx`**：カタログが消える。保存済みのコミットは `.git` に残る。失うのは、最後の保存の後の編集だけ。`spec-dock canonical link` が作り直す。
- **mainのチェックアウトの移動や改名**：worktree の登録と、作業用のworktreeの絶対パスのリンクが切れる。状態の表示が直し方を示し、`spec-dock canonical link` が張り直す。
- **作業用のworktreeの削除**：リンクだけが消え、カタログは残る（確認済み）。
- **外付けのボリュームが外れている**：定期の同期は何も変えずに失敗し、記録だけを残す。
- **macOS のプライバシーの保護**：外付けのボリュームなどにあるリポジトリは、定期の実行が動かすプログラムに macOS の許可がないと、読むことも拒否される（確認済み。許可はプログラムごと）。定期の同期は何も変えずに失敗し、状態の表示が、許可を与えるプログラムと設定の場所を示す。
- **同じPCに同じリポジトリのクローンが複数ある**：クローンごとにカタログがあり、互いには GitHub を通して同期する。
- **ネットワークの断絶や認証の失敗**：コミットはローカルに積まれ、つながったときに push される。長く続いたら警告する。
- **同じファイルの同時編集**：R-C3 で解決し、編集は失われない。後から push した側で作業中のエージェントには、文書が先着の版に変わって見える。
- **ツールの設定が足りない**：Claude Code の既定の権限モードでは、作業用のworktreeからリンク経由の読み取りも書き込みも、作業ディレクトリの外として拒否される（確認済み）。Codex のサンドボックスでは、書き込みが拒否される（確認済み）。どちらも R-B6 の1行で解決する。
- **サンドボックスからの `.git` への書き込み**：Codex のサンドボックスは、mainの `.git` に書けない。SpecDock のコマンドはコミットしないので影響しない（R-D1）。
- **コード用のフック**：リポジトリの `pre-commit` などは、カタログのコミットでは動かさない（R-C1）。
- **GitHub はマージのボタンを止めない**：ワークフローは失敗をPRに表示するが、マージのボタンは押せるままになる。マージの条件は、既存のCIと同じく、通過を確かめてからマージする運用で守る（R-F3）。退去費用プロダクトのテストとデプロイのCIも、今この形で動いている（確認済み）。GitHub にボタンを止めさせる必須の検査は、非公開のリポジトリでは Pro 以上のプランが要るため、前提にしない。
- **GitHub の canonical の削除や強制 push**：GitHub 側では防げない。R-C5 で検出する。
- **GitHub の題名の手作業の変更**：表示が変わるだけで、識別名は変わらない。
- **コンテナ（中でクローンしたもの）を起動し直した**：常駐の同期のプロセスは止まる。起動の設定の1行か、`spec-dock canonical link` で動き直す。それまでの編集はファイルに残り、動き直したときに保存される。
- **ホストのフォルダーをマウントしたコンテナ**：中のパスがホストと違うため、カタログを Git で扱えない。SpecDock は、ホストの Git の記録を書き換えずに止まる（R-C8）。
- **SSH で入るサーバーで、linger がない**：ログアウトすると、定期の同期も止まる。状態の表示が知らせ、linger を有効にする1行を示す。
- **Git が古い**：`merge-tree --write-tree` のない Git（2.38 より前。Ubuntu 22.04 の標準の Git など）では、`canonical link` と定期の同期が、何も書かずに止まり、新しい Git を入れるよう示す。
- **構造のスナップショットが古い**：GitHub につながらないときは、表示は古いスナップショットで続け、古いことを示す。書く操作は止まる（R-I4）。GitHub の画面で親子や依存だけを変えたときは、表示に出るまで最大30分かかることがある（R-I3。題名や状態の変更は、およそ1〜2分で出る）。SpecDock のコマンドで変えたものは、すぐに出る。
- **移行の間（一部のリポジトリだけが移った）**：0.3.0 は、移したリポジトリを canonical モードで、移していないリポジトリを今のままで扱う。移していないリポジトリは、何もしなくても動き続ける（R-A6）。
- **切り替えの後に、新しい仕組みに重大な問題が見つかった**：撤去の前なら、そのリポジトリだけを、切り替える前の形に戻せる。ほかのリポジトリには影響しない。撤去の後なら、0.3.0 を入れ直してから戻す。戻すかどうかは、利用者が決める。
- **撤去の後に、移していないリポジトリかクローンが見つかった**：0.4.0 は、版3の宣言を読むと、移行の方法を示して止まる（R-J6）。そのリポジトリは、0.3.0 を入れ直し、版のタグ v0.3.0 に残る手順書で移す。
- **各リポジトリのCIの固定の版**：今の各リポジトリのCIは、SpecDock の特定のコミットで `workspace validate` を実行しているので、切り替えのPRでは、仕様のない既定のブランチに対して失敗する。切り替えのPRで、検査のワークフローに置き換える（R-J5）。

## 受け入れ条件

- **AC-01**：移行後の spec-dock の既定のブランチのツリーに、`spec-dock/initiatives` と `spec-dock/.canonical` の下のパスと `.meta.json` が1つもない。
- **AC-02**：作業用のworktreeで書いた仕様が、同じPCの別のworktreeから保存の前にも読め、別のクローン（別のPCの代わり）からはおよそ2分以内に読める。
- **AC-03**：2つのクローンで同じファイルを同時に編集しても、両方の内容が残り（片方は別名ファイル）、どの作業ツリーにも競合のマーカーが残らない。
- **AC-04**：移行の前後で、spec-dock の全Scopeの番号、種類、親子、依存が一致する。移行後、`.meta.json` が1つも残っていない。
- **AC-05**：移行前のブランチの仕様を取り込んだ後、そのPRが仕様を含まずにマージできる。
- **AC-06**：新しいクローンと、ほかのツールで作ったworktreeで、`spec-dock canonical link` を1回実行した後に、仕様を読み書きできる。SpecDock の `worktree create` で作ったworktreeでは、追加のコマンドなしで読み書きできる。
- **AC-07**：利用者が足す設定は、Claude Code と Codex のそれぞれ1行だけで、その内容を SpecDock が正確に示す。同じ設定と確かめ方が、使い方の文書に書かれている。mainのチェックアウトでは設定なしで使える。
- **AC-08**：`git clean -ffdx`、mainのチェックアウトの移動、移行前のコミットへの checkout の後、状態の表示が原因と次の1手を示し、`spec-dock canonical link` で元に戻る。
- **AC-09**：日本語の題名で Scope を作れる。ディレクトリ名とブランチ名は英語の slug になり、`scope show` と `workspace sync` の表示と、ダッシュボードには日本語の題名が出る。
- **AC-10**：大量の削除が、自動では push されない。
- **AC-11**：canonical が強制 push で書き換えられたとき、各クローンの同期は取り込まずに止まり、知らせる。
- **AC-12**：spec-dock で、既定のブランチへ仕様を入れるPRでは、SpecDock の検査が失敗し、その失敗がPRに表示される。エージェントは、そのPRをマージできる状態として渡さない。
- **AC-13**：`work finish` は、その Scope の仕様の変更が push されるまで終わらない。
- **AC-14**：設計書を渡されていない新しいエージェントが、R-H1 の節だけを頼りに、仕様の読み書き、検索、別名ファイルの統合を迷わずにできる（白紙のエージェントでの試行で確かめる）。
- **AC-15**：撤去までの間、0.3.0 を入れた後も、移行していないリポジトリ（宣言の版が3）で、今の回帰テストがすべて通り、今と同じに動く。
- **AC-16**：構造が変わっていないとき、定期の同期の1周期と、`scope show` や `scope list` を続けて実行することは、GitHub の主のレート制限を消費しない（変わったかの確かめが 304 で終わり、全体の取り直しをしない）。GitHub で題名を変えると、およそ2分以内に表示とダッシュボードに出る。SpecDock のコマンドで書いた変更は、次の表示にすぐ出る。
- **AC-17**：canonical モードで、定期の同期が、mainのチェックアウトに、ダッシュボードの5つのファイルを今までと同じ形で作り、日本語の題名と作業中の色が出る。構造が変わらない周期では、書き直さない。
- **AC-18**：systemd の動く Linux と、systemd のないコンテナ（中でクローンしたもの）のそれぞれで、AC-02、AC-03、AC-13 と同じことができる。ホストのフォルダーをマウントしたコンテナでは、ホストの Git の記録を変えずに止まる。
- **AC-19**：R-J1 の5つのリポジトリのそれぞれで、切り替えの前に予行演習（切り替えと、戻す手順）が通った記録があり、切り替えの後に AC-01 と AC-04 と同じことが成り立ち、既定のブランチへのPRで検査のワークフローが動く。spec-dock の後の4つは1回の作業で切り替わり、その後の3日間の運用で、仕様の失われがない。
- **AC-20**：撤去の後の SpecDock 0.4.0 に、`.meta.json` を読み書きするコード、宣言の版3の処理、モードの振り分け、canonical モードで拒否するだけのコマンドと引数が残っていない。`make lint` と `uv run pytest` が通り、撤去の前に共通の契約（R-J7）を確かめていたテストは、canonical モードのテストとして残っている。版3の宣言のリポジトリでは、移行の方法を示して止まる。R-J1 の5つのリポジトリの配布資産が 0.4.0 になり、各リポジトリの検査のワークフローが 0.4.0 で通る。

## 制約・前提

- Linux と macOS、Python 3.10 以上。Windows には対応しない。Linux では、systemd があってもなくても動く（R-C7）。Git は `merge-tree --write-tree` が使える版（2.38 以上）が要る。手元は 2.54.0、Ubuntu 24.04 は 2.43.0。
- GitHub の個人アカウント。Issue types は使えない。GitHub の必須の検査（ブランチの保護、ルールセット）は使わない。
- GitHub の二次のレート制限（公式の文書、2026-10-25）：同時の要求は100まで、REST は1分に900点（GET は1点、書き込みは5点）、GraphQL は1分に2,000点、中身を作る要求は目安で1分に80回、1時間に500回。条件付きの要求の 304 は、主のレート制限に数えない。
- 人がPRをマージする関門を残す。エージェントは、マージできる状態のPRで止まる。
- 今の CLI の契約（直接の選択、StartLock、Artifact の命名、失敗したら止まる境界、読むだけのコマンドは書かない）を壊さない。
- SpecDock は、利用者のツールの設定（`~/.claude/settings.json`、`~/.codex/config.toml` など）を書き換えない。定期の実行は SpecDock 自身のもので、`spec-dock canonical link` だけが作り、取り外しの操作だけが消す。
- dogfooding の規則：提供側のソース（`src/spec_dock/`）を先に変え、配布されたものを `spec-dock/` で確かめる。

## エージェントが決めたこと

利用者から任された細部。異議があれば変える。

- slug を、GitHub の本文の末尾に、画面に出ないHTMLコメントの印として持つ。GitHub だけからディレクトリを作り直せるようにするため。
- テンプレートから `タイトル:` の写しを外す。題名の正本を GitHub だけにするため。
- 定期の実行は、`spec-dock canonical link` が登録する。SpecDock 自身の仕組みで、ツールの設定ではないため。コンテナの常駐のプロセスも、同じコマンドが起動する。起動し直しのための devcontainer などの設定は、1行を示すだけで書き換えない。linger も、示すだけで変えない（約束4）。
- 構造のスナップショットは、周期ごとに、種類のラベルごとの一覧への条件付きの要求で「変わったか」を確かめ、変わっていたときだけ GraphQL で全体を取り直す。304 は主のレート制限に数えないため（確認済み）。親子と依存だけの変更で Issue の更新の時刻が変わるかは確かめていないため、30分ごとにも取り直す。
- スナップショットは、リポジトリの外の、PCのユーザーごとの状態の置き場に置く。読むだけのコマンドも、このファイルだけは更新してよい（リポジトリ、カタログ、`.git`、GitHub には書かない）。今の CLI の「構造をキャッシュしない」方針は、利用者の方針（R-I1）に合わせて、canonical モードでは変える。
- ダッシュボードは、mainのチェックアウトにだけ作る。1つのクローンの構造は1つで、作業用のworktreeごとに作る意味がないため。
- 仕様を読むだけのコマンドは、足りなくても自分では直さず、次の1手を示す。今の CLI の「読むだけのコマンドは書かない」契約を守るため。
- マージの後に Issue を立てる見張りは作らない。同じワークフローを既定のブランチへの push でも動かし、失敗を表示すれば足りるため。
- 移行前の版の SpecDock を止めるには、今あるワークスペースの宣言（`spec-dock/workspace.json`）の版を上げる仕組みを使う。新しい仕組みを足さないため。形式の版を更新するコマンドは、形式を変える必要が出たときに作る。
- canonical にCIの定義を置かない。
- 各リポジトリの切り替えは、次の順で、1回の作業として行う。待ちの大半は、人によるPRのマージで、1つのリポジトリで数十分を見込む。残りの4つは、同じ作業の中で、1つずつ順に行う。
  1. GitHub への登録と検証と、予行演習を、切り替えより前に済ませる（今の運用は止めない。R-J2、R-J3）。
  2. 切り替えを始めたら、終わるまで、ほかのエージェントでそのリポジトリの仕様を編集しない。
  3. canonical を作って push し、既定のブランチから仕様を外し、CIを置き換えるPRを作る（R-J5）。
  4. 人がマージした後、各チェックアウトで `spec-dock canonical link` を実行する。
  5. 作業用のworktreeに残った仕様の変更は、R-G5 の取り込みで canonical に入れる。
- 撤去は、残りの4つの切り替えの後の3日間の運用の後に行う。戻す必要が出たときに、そのリポジトリだけを、0.3.0 のまま戻せるようにするためである。
- canonical モードで拒否するだけのコマンドと引数（`workspace migrate`、`workbench copy` など）は、2つの仕組みが並ぶ間に、すべてのコマンドが答えるために置いた（設計の G7）。撤去で消す。
- 移行のスクリプトは spec-dock のリポジトリにだけ置き、ほかのリポジトリには写さない。対象のリポジトリは引数で選ぶ。
- 各リポジトリの今のCIの手順は、形がそれぞれ違うので、移行のスクリプトで自動では書き換えない。スクリプトが SpecDock を呼ぶ手順を一覧にし、切り替えのPRで手で直し、そのPRのCIの通過で確かめる。
- 予行演習で利用者の定期の実行に触れないよう、`spec-dock canonical link` に、定期の実行を登録しない指定を設ける（設計の3章）。
- この Epic は、親の `init-local-00003`（#31）が別の題名で閉じていたため、新しい Initiative `init-00423` の下に作った。
- 移行していないリポジトリでも新しい SpecDock が動くよう、宣言の版で動きを分ける（R-A6）。SpecDock のパッケージは1つのPCで全リポジトリが共有し、リポジトリごとに切り替える時期がずれるため。2026-10-25 に、利用者が、これを移行の間だけの扱いとし、撤去までこの Epic に含めることを決めた。

## 未解決事項

利用者の判断が要るものは、今はない。spec-dock の別のクローンの扱いは、2026-10-26 に、放棄すると決めた（合意済みの判断）。

要件定義の後に、設計で確かめるとしていた項目は、設計書（`design.md`）で決めた。実装と切り替えで確かめる残りは、次のとおり。

- Codex のサンドボックスの中での排他：macOS では、ディレクトリへの `flock` が、サンドボックスの内と外で互いに効くことを確かめた。Linux のディレクトリへの `flock` も、Ubuntu 24.04 で効いた。Linux の Codex のサンドボックス（Landlock）の中では、実装の Issue で確かめる。
- 定期の実行からの push の認証：macOS の launchd から、利用者の `gh` のログインで認証できることを確かめた。Linux の systemd のユーザーのタイマーが動くことは Ubuntu 24.04 で確かめた。そこからの push の認証は、実装の Issue で確かめる。
- 親子と依存の変更で、Issue の更新の時刻が変わるか：本物の GitHub に書く必要があるので、切り替えの Issue で確かめる。変わるなら、30分ごとの取り直しを減らせる。
- 検査のワークフローでの SpecDock の入れ方と版の固定、新しいコマンドの名前：設計書で決めた。
