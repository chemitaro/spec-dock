# epic-00427 Build Html Spec Dashboard — 要件定義

詳細: [Requirement Guide](../../../../docs/authoring/requirement.md)

表示名：仕様を見渡す HTML のダッシュボード

## 目的

SpecDock が管理する1つのリポジトリの仕様について、人が全体を見渡し、次に何をするかを決め、1つを選んで詳しく確かめられる HTML のダッシュボードを作る。見る対象は、Initiative、Epic、Issue の階層と、作業の順番の依存、状態、進み具合の推移である。

利用者の言葉では、これまでのプログラミングは「点」だった。SpecDock で「面」にし、さらに時間の軸を加えて、立体的に管理できるようにする。

このダッシュボードは、epic-00424 が作るつなぎの Markdown と PlantUML のダッシュボードを置き換える。また、利用者が別に作る company-os の統合ダッシュボードに、情報を渡す。

## 背景

### 解く問題

- 構造（階層、依存、状態、題名）の正本は GitHub Issue にあり、内容（要件、設計、計画、Artifact）の正本はカタログにある（epic-00424）。人が両方を合わせて見る手段がない。
- 今までのダッシュボード（`dashboard.md` と4つの PlantUML のファイル）は、epic-00424 で作り直される。しかし、図を見るには PlantUML を描く道具が要り、スマートフォンでは見にくい。また、図から詳しい内容（なぜ止められているか、文書）へたどれない。
- 次に着手できるものと、止められているものの理由が、一目では分からない。
- モックで spec-dock の実際のデータを描いたところ、片付けが必要な Scope が14件見つかった（2026-10-25）。配下がすべて終わったのに開いている Epic が12件、閉じたのに開いた配下がある親が2件である。今の表示では、これに気づけない。

### 前の Epic との関係

- **epic-00424**（#424、仕様の正本を `spec-dock/canonical` と GitHub Issue に集約する）：構造をリポジトリごとに一括で取得し、PCのユーザーごとの「構造のスナップショット」（設計の2章、契約 C10）に持つ。内容はカタログ（`spec-dock/initiatives/` から開く。Scope ごとに直下の `<ID>/` に平らに並び、親子はディレクトリに表さない。2026-10-29 の epic-00424 の方針の変更）に置く。つなぎとして、今までの Markdown と PlantUML のダッシュボード（R-E5）を、定期の同期が作り直す。このダッシュボードは、スナップショットとカタログを読み、R-E5 のダッシュボードを置き換える。
- **epic-00425**（#425）：仕様の文書を、エージェントが確かめる CUE と、人が読む HTML に移す。人向けの説明の HTML も、仕様書の一部として正式に採用する予定である。このダッシュボードは、その HTML を組み込む側になる。もとは epic-00425 がダッシュボードも扱う予定だったが、2026-10-25 にこの Epic に分けた。

### 利用者の構想（2026-10-25）

- HTML で作る、レスポンシブで使いやすいウェブの画面にする。
- Initiative、Epic、Issue の縦の階層（親子）と、作業の順番の依存（blocked by）を、図で示す。
- 状態を色で示す。実装中のもの、まだ始めていないもの、止められているもの（依存が終わっていない）、終わったもの。
- 終わったものを隠す表示と、終わったものを含めてすべてを示す表示を切り替えられる。
- 1つの Epic や Issue を選ぶと、詳しい画面を開ける。詳しい画面には、GitHub の日本語の題名、依存しているもの、依存されているもの、配下に含むもの、その Scope の中での実行の順番の依存、要件・設計・計画の内容を示す。
- 1か所の正本から、今の要件・設計・計画をその場で描き、一部を画面に組み込んだり、人向けのページを開いたりできる。
- 操作のたびに GitHub に問い合わせない。一括で取得した構造（epic-00424 の構造のスナップショット）を使い、GitHub の負荷と待ち時間を抑える。
- 構造の図は、今までの PlantUML の図（`tree.puml`、`tree-all.puml`）のように、階層と作業の順番の依存を1枚で示す、ツリー状の図にする。それを、今までよりも豊かで具体的な図にする（2026-10-26 の追加の依頼）。図の箱を押すと、その Scope の詳しい内容を出す。

### モックと聞き取り（2026-10-25〜26）

- モックの画面を Artifact [ダッシュボードのモック](artifacts/20261025t220347z--dashboard-mock.html) に置いた。中身は、1つの HTML のファイルである。データは、spec-dock の実際の Scope 248件である。題名、状態、時刻は、GitHub から1回の一括の読み取りで取った。階層と依存は、このブランチの `.meta.json` から取った。データの形は、C10 の版1に合わせた。
- モックには、4つの画面（状態のボード、一覧と詳しい画面、構造の図、時間の軸）と、共通の詳しい画面、機能の一覧（37項目と、それぞれの決定）がある。
- 利用者は、モックを見ながら、聞き取りの質問に答えた。その結果を「合意済みの判断」に記録した。

### 関係者

- **利用者（人）**：PCとスマートフォンのブラウザーで見て、次に何をするかを決める。
- **エージェント**（Claude Code、Codex）：CLI が出す要約の JSON を読む（今の `dashboard.md` の代わり）。
- **company-os の統合ダッシュボード**：利用者が別に作る。SpecDock を使う各プロジェクトの要約を中央に集め、個別のダッシュボードへのリンクを示す。この Epic では作らない。

## 観測可能な要件

### A. 開き方

- **R-A1 サーバー**：利用者がリポジトリのチェックアウトでコマンドを実行すると、そのリポジトリのダッシュボードを配る手元のサーバーが起動する。サーバーは、利用者が止めるまで動く。SpecDock は、サーバーを自動では起動しない（epic-00424 の約束3「自動で動くのは定期の同期だけ」を守る）。
- **R-A2 待ち受け**：既定では、そのPCからだけ開ける。利用者が指定したときだけ、Tailscale の住所でも待ち受け、同じ tailnet のスマートフォンから開ける。
- **R-A3 1つのリポジトリ**：1つのダッシュボードは、1つのリポジトリだけを扱う。ほかのリポジトリの Scope を含めない。複数のリポジトリのダッシュボードを、同時に動かせる。
- **R-A4 見るだけ**：画面の操作で、GitHub、カタログ、リポジトリに書くことはない。代わりに、状態に合った SpecDock のコマンド（例：着手できる Issue の `spec-dock work start <ID>`）を写せる。
- **R-A5 静的な資料**：人向けの説明の HTML などの資料は、静的な HTML のファイルとしてカタログに置く。ダッシュボードのサーバーは、それを配り、画面から開ける。
- **R-A6 端末**：PCのブラウザーと、スマートフォンのブラウザー（iPhone の Safari、幅 390px 程度）で、横にはみ出さずに使える。OS の設定に従って、明るい表示と暗い表示を切り替える。

### B. データと新しさ

- **R-B1 構造はスナップショットから**：構造（番号、種類、題名、状態、親子、依存、作業中の印、担当者、作成と完了の時刻）は、epic-00424 の構造のスナップショットから読む。画面の操作のたびに GitHub に問い合わせない。
- **R-B2 内容はカタログから**：文書と Artifact は、カタログから読む。
- **R-B3 自動で新しくする**：画面を開いている間に、スナップショットかカタログが変わったら、再読み込みをしなくても、画面が新しくなる。そのために GitHub に問い合わせることはない。新しさは定期の同期に従う。目安はおよそ1〜2分で、親子と依存だけの変更は最大30分かかる（epic-00424 の R-I3）。
- **R-B4 取得の時刻と古さ**：構造を取得した時刻を、いつも示す。次のときは、それと分かる表示と、次の1手（確かめるコマンドなど）を示す。スナップショットが30分を超えて古いとき。スナップショットがないとき。読めないとき。知らない版のとき。
- **R-B5 異常**：スナップショットに記録された構造の異常（`anomalies`）を示す。

### C. 状態

- **R-C1 5つの状態**：Scope の状態は、終わった、作業中、止められている、着手できる、不明、の5つとする。Issue の状態は、次の順に決める。
  1. 構造の異常に挙がっていれば、不明。
  2. 閉じていれば、終わった。
  3. 作業中の印（GitHub のラベル）があれば、作業中。
  4. 自分か祖先の依存の先が1つでも終わっていなければ、止められている。依存の先が Scope でない Issue なら、開いていれば止められている。
  5. それ以外は、着手できる。

  4の判定は、`dependency check` の着手の判定（epic-00424 の I-4）と同じ結果になる。
- **R-C2 Epic と Initiative**：Epic と Initiative の状態は、配下も見て決める。閉じていれば、終わった。自分か子孫に作業中の印があれば、作業中。自分か祖先の依存の先が終わっていなければ、止められている。それ以外は、着手できる。配下の進み具合（終わった数と全体の数）は、状態とは別に、帯と数で示す。
- **R-C3 色だけに頼らない**：状態は、色に加えて、記号と言葉でも示す。凡例を示す。
- **R-C4 終わったものの表示**：既定では、終わったものを隠す。利用者が切り替えると、終わったものも含めて示す。隠しているときも、開いた子孫を持つ終わったものは残す（閉じた親の下の、開いた Epic や Issue を見失わないため）。

### D. 画面

- **R-D1 ホーム（状態のボード）**：開いたときに最初に出す画面である。作業中、着手できる、止められている、の列に Scope を分ける。終わったものを含めるときは、終わった、の列を足す。種類（Initiative、Epic、Issue）で絞れる。親ごとにまとめられる。上に、状態ごとの数と、終わった割合を示す。
- **R-D2 一覧**：階層を開いたり閉じたりできる一覧である。一覧の横（スマートフォンでは次の画面）に、選んだ Scope の詳しい内容を出す。何も選んでいないときは、全体の概況を出す。概況は、作業中のもの、着手できるもの、止められているもの（理由つき）、片付けの候補（R-F1）、最近終わったもの、である。
- **R-D3 構造の図**：階層と作業の順番の依存を、1枚の図で示す。
  - 既定の表し方は「入れ子」である。Initiative と Epic を枠にし、その中に Issue の箱を置く。依存のある箱は、左から右へ作業の順番に並べ、矢印でつなぐ。依存が長く続くときは、行を折り返して収める。もう1つの表し方「木」では、すべてを箱にし、親子の線と依存の矢印でつなぐ。利用者は、2つを切り替えられる。
  - 箱の地の色で、状態を示す。箱には、状態の札、ID と番号、題名（2行まで）、補足の1行を示す。補足は、待っているもの、作業中のブランチ、終わった日、配下の進み具合のどれかである。同じ親の中で2段以上の順番があるときは、何段目に進めるかを示す。
  - 依存の矢印は、まだ終わっていない依存（待っている）と、終わった依存とを、見分けられる線で描く。依存の線は、すべて、待っているものだけ、なし、から選べる。
  - 範囲を、1つの Initiative か Epic に絞れる。絞っているときは、その親の道筋を示し、すぐに全体へ戻れる。
  - 拡大と縮小、移動ができる。スマートフォンでは、指でつまむ操作とドラッグでできる。全体を画面に収めるボタンを置く。
  - 箱を押すと、その箱の前に終わるべきもの（依存の先をたどったもの）と、後に続くもの（依存の元をたどったもの）を強調する。同時に、要点を図の横（スマートフォンでは下）に出す。要点を出したまま、ほかの箱を選び直せる。要点から詳しい画面へ移れる。ダブルクリックでは、詳しい画面へ直接移る。
- **R-D4 時間の軸**：次の2つを示す。
  - 進み具合の推移：作られた Scope の数と、終わった Scope の数の累計を、週ごとに示す。数える種類を選べる。点を指すと、その週の数を示す。
  - 最近の動き：作られた Scope と終わった Scope を、時刻の新しい順に並べる。
- **R-D5 画面の切り替え**：4つの画面（状態のボード、一覧、構造の図、時間の軸）を、上の帯で切り替える。
- **R-D6 検索**：ID、番号、題名で Scope を探し、詳しい画面へ移れる。
- **R-D7 URL**：選んだ画面、Scope、タブ、表示の切り替えを、URL に持つ。その URL を開き直すか共有すると、同じ画面に戻る。Scope の詳しい画面の URL の形は、統合ダッシュボードがリンクに使うため、変えない契約とする。

### E. 詳しい画面

- **R-E1 見出し**：GitHub の題名、ID、種類、状態、親の道筋、GitHub の Issue へのリンク、作成と完了の日、担当者を示す。
- **R-E2 状態の理由**：止められているときは、待っているものを示し、親から引き継いだ依存はそれと分かるように示す。作業中のときは、作業中の印と、このPCでの worktree とブランチを示す（R-E6）。終わったときは、閉じた日を示す。
- **R-E3 依存**：待っているもの（依存しているもの）と、待たれているもの（依存されているもの）を示す。
- **R-E4 配下**：配下と、その状態と、進み具合を示す。終わったものを隠しているときは、隠した数を示す。
- **R-E5 配下の実行の順番**：配下を、依存の段に分けて示す（段1 → 段2 → …）。子孫どうしの依存も、配下どうしの順番に数える。同じ段のものは、並べて進められることを示す。その Scope の外への依存は、別に示す。
- **R-E6 作業中の場所**：作業中の Scope の担当者を示す。このPCで、その Scope を選んでいる worktree とブランチがあれば、それも示す。ほかのPCの worktree は分からない（担当者と作業中の印だけを示す）。
- **R-E7 Artifact**：Artifact の一覧を示す。HTML の Artifact は、ダッシュボードのサーバーから開ける。
- **R-E8 写せるコマンド**：その Scope の状態に合った SpecDock のコマンドを写せる。
- **R-E9 文書（epic-00425 の後）**：epic-00425 の後は、要件、設計、計画を、正本の CUE からその場で HTML に描いて示す。前もって作ったファイルは使わない。人向けの説明の HTML（epic-00425 で仕様書の一部として正式に採用する予定のもの）へのリンクも示す。epic-00425 の前は、文書があるかないかと、HTML の Artifact へのリンクだけを示す。

### F. 片付けの候補

- **R-F1 片付けの候補**：次の Scope を一覧にする。配下がすべて終わったのに開いている Epic と Initiative。閉じたのに開いた配下がある親。見るだけで、直すことはしない（直すコマンドは写せる）。

### G. 統合ダッシュボードとエージェントへの情報

- **R-G1 要約の JSON**：リポジトリの要約を、版を持つ JSON の契約として出す。要約に含めるものは、次のとおりである。
  - 契約の版、リポジトリ、構造を取得した時刻
  - 種類ごと・状態ごとの数と、終わった割合
  - 作業中、着手できる、止められている、片付けの候補の一覧（ID、番号、題名、状態、理由）
  - 構造の異常の数
  - 各 Scope の詳しい画面へのパス
- **R-G2 2つの口**：同じ要約を、CLI と、ダッシュボードのサーバーの両方から読める。CLI は、サーバーが動いていなくても動き、GitHub に問い合わせない。
- **R-G3 ダッシュボードの在りか**：統合ダッシュボードが、動いている各リポジトリのダッシュボードの URL（基点）を知る方法を設ける。R-D7 のパスと合わせると、個別の画面へリンクできる。
- **R-G4 統合ダッシュボードは作らない**：この Epic は、情報を渡す側だけを作る。

### H. 今の Markdown と PlantUML のダッシュボード

- **R-H1 生成をやめる**：HTML のダッシュボード（最初の段階）を出した後の版では、定期の同期は、`spec-dock/dashboard.md` と4つの PlantUML のファイル（epic-00424 の R-E5）を作らない。それを作るコードは、この Epic で撤去する。エージェントは、代わりに R-G1 の要約を読む。

## スコープ

### 対象

- R-A〜R-H のダッシュボード、サーバー、要約の JSON。
- epic-00424 の R-E5 のダッシュボードの生成の撤去（R-H1）。
- 提供側のソース（`src/spec_dock/`）と、その配布、spec-dock での dogfooding。

### 段階

- **段階1（epic-00424 の後、epic-00425 の前）**：R-A〜R-D、R-E1〜R-E8、R-F、R-G、R-H。文書については、あるかないかと、HTML の Artifact へのリンクだけを示す。
- **段階2（epic-00425 の後）**：R-E9（CUE からその場で描いた文書と、人向けの説明の HTML へのリンク）。

### 対象外

- company-os の統合ダッシュボードそのもの（R-G4）。
- 複数のリポジトリを1つの画面にまとめること（R-A3）。
- 画面からの操作（着手、完了、依存の変更など）（R-A4）。
- ロードマップ（Epic の始まりから終わりまでの帯）、文書の変更の履歴と差分、ある日の時点の構造の再現。モックの時間の軸と履歴のタブにはあるが、作らない。
- ダッシュボードそのものの静的な書き出し、印刷と PDF、未解決事項と受け入れ条件の抜き出し。必要になったら、別に扱う。
- CUE の形式と、HTML への描き方そのもの（epic-00425）。
- 構造の取得の仕組みそのもの（epic-00424）。
- Windows。

## 失敗・境界条件

- **スナップショットがない**：画面は開き、構造がないことと、次の1手（`spec-dock canonical link` の実行や、定期の同期の確かめ）を示す。要約の CLI は、理由をつけて失敗する。
- **スナップショットが古い（30分を超えた）**：古い内容で表示を続け、古いことと取得の時刻を示す。
- **スナップショットが知らない版**：読まずに、版が違うことと、SpecDock の更新を示す。
- **スナップショットが読めない（壊れている、書き込みの途中）**：最後に読めた内容で表示を続け、読めないことを示す。epic-00424 は `rename` で書くため、書き込みの途中のファイルは読まない前提である。
- **カタログがない（リンクがない、まだ移行していない）**：構造の画面は動く。文書と Artifact の欄には、カタログがないことと次の1手を示す。
- **従来モード（宣言の版3）のリポジトリ**：ダッシュボードは起動せず、canonical モードでだけ動くことを示す。
- **構造の異常（親の欠け、依存の循環、種類の決まらない Issue）**：その Scope を不明として示し、ほかの表示は続ける。
- **閉じた親の下に、開いた配下がある**：終わったものを隠すときも、親を残す（R-C4）。片付けの候補に挙げる（R-F1）。
- **待ち受けの番号（ポート）が使われている**：起動せずに止まり、別の番号の指定方法を示す。
- **Tailscale の住所が得られない**：Tailscale での待ち受けを指定したときは、起動せずに理由を示す。指定しないときの、そのPCからだけの待ち受けには影響しない。
- **Tailscale で待ち受けている**：同じ tailnet の端末は、そのリポジトリの仕様を読める。起動のときに、そのことと URL を示す。
- **HTML の Artifact の中のスクリプト**：開いた Artifact のスクリプトが、ダッシュボードの画面とデータを書き換えたり、読み取ったりできないようにする。
- **インターネットにつながらない**：ダッシュボードの画面は開ける。GitHub へのリンクだけが開けない。
- **大きなリポジトリ**：Scope が250件ほど（spec-dock は248件、退去費用プロダクトは246件）でも、受け入れ条件の速さで動く。

## 受け入れ条件

- **AC-01**：コマンドでサーバーを起動すると、そのPCのブラウザーで、ホーム（状態のボード）が開く。指定しないときは、ほかの端末から開けない。
- **AC-02**：Tailscale での待ち受けを指定すると、同じ tailnet の iPhone の Safari で開ける。4つの画面と詳しい画面が、横にはみ出さずに使え、構造の図を指で拡大し、動かせる。
- **AC-03**：画面のどの操作でも、ダッシュボードは GitHub に要求を送らない。
- **AC-04**：画面を開いたまま、スナップショットかカタログを書き換えると、再読み込みをしなくても画面が新しくなる。
- **AC-05**：構造を取得した時刻がいつも出る。次の4つのときに、それぞれの表示と次の1手が出る。30分を超えて古いスナップショット。スナップショットがないとき。知らない版。読めないファイル。
- **AC-06**：見本の構造で、各 Scope の状態が R-C1 と R-C2 のとおりになる。見本は、次を含む。作業中の印、開いた依存、親から引き継いだ依存、Scope でない Issue への依存、閉じた Scope、異常、配下だけに作業中の印がある Epic。Issue の止められている・着手できるの判定が、`dependency check` と一致する。
- **AC-07**：終わったものを隠す表示で、開いた子孫を持つ閉じた親が残る。
- **AC-08**：構造の図について、次のことができる。入れ子と木の切り替え。範囲の絞り込みと解除。依存の線の3つの切り替え。待っている依存と終わった依存の見分け。作業の順番の段の表示。長い依存の折り返し。箱を押したときの前後の強調と要点。ダブルクリックでの詳しい画面への移動。
- **AC-09**：詳しい画面に、R-E1〜R-E8 の項目が出る。配下の実行の順番が、見本の依存のとおりの段に分かれる。
- **AC-10**：HTML の Artifact をサーバーから開ける。その中のスクリプトが、ダッシュボードの画面とデータに触れられない。
- **AC-11**：見本の作成と完了の時刻から、週ごとの累計が正しく出る。最近の動きが、時刻の新しい順に並ぶ。
- **AC-12**：見本で、片付けの候補の2つの種類が挙がる。spec-dock の 2026-10-25 時点の構造では、14件が挙がる。
- **AC-13**：要約の JSON を、CLI とサーバーの両方から読め、内容が同じで、契約の版を持つ。CLI は、サーバーが動いていなくても動き、GitHub に要求を送らない。
- **AC-14**：Scope の詳しい画面の URL を新しいタブで開くと、同じ画面が出る。統合ダッシュボードの代わりの簡単な試しで、R-G3 の方法で得た基点と R-D7 のパスから、個別の画面へ移れる。
- **AC-15**：Scope が250件ほどの構造で、このPCのブラウザーで、ホームが2秒以内に出る。終わったものを含めたすべての構造の図が、3秒以内に描ける。
- **AC-16**：段階1を出した後の版で、定期の同期が5つのファイル（`dashboard.md` と4つの PlantUML のファイル）を作らず、その生成のコードが残っていない。
- **AC-17**：インターネットにつながらないPCでも、ダッシュボードの画面が開ける。
- **AC-18**（段階2）：CUE からその場で描いた要件、設計、計画が、詳しい画面に出る。人向けの説明の HTML へのリンクがある。

## 制約・前提

- Linux と macOS。Windows には対応しない（epic-00424 と同じ）。
- canonical モード（宣言の版4）のリポジトリだけを扱う。epic-00424 の撤去の後は、canonical モードだけが残る。
- 構造は、epic-00424 の構造のスナップショット（C10）から読む。段階1は、epic-00424 のスナップショット（I-1）、カタログ（I-2）、着手の判定（I-4）と、作業中のラベルができてから実装する。Epic 単位の依存は付けず、実装の Issue を作るときに、epic-00424 の該当する Issue への依存を付ける（今の工程を始められるようにするため）。
- 段階2は、epic-00425 の CUE と HTML の描き方ができてから実装する。
- epic-00424 の約束（自動で動くのは定期の同期だけ、ツールの設定を書き換えない、おかしいときは止まって次の1手を示す）を守る。
- GitHub への要求は、epic-00424 の仕組み（定期の同期）にだけ任せる。ダッシュボードとその CLI は、GitHub に要求を送らない。
- 人がPRをマージする関門を残す。
- dogfooding の規則：提供側のソース（`src/spec_dock/`）を先に変え、配布されたものを `spec-dock/` で確かめる。

## エージェントが決めたこと

利用者から任された細部。異議があれば変える。

- 状態は、色に加えて、記号と言葉でも示す。色の見分けにくい人と、白黒の印刷のため。
- 終わったものを隠すときも、開いた子孫を持つ終わったものは残す。spec-dock では、閉じた `init-local-00003` の下に開いた Epic が12件あり、隠すと見えなくなるため。
- 構造の図の入れ子では、直下の子どうしに依存がある枠だけを、左から右へ作業の順番で並べる。依存のない枠は、詰めて並べる。すべてを作業の順番で並べると、依存のない Epic が縦に1列に並び、図が細長くなるため（モックで確かめた）。
- 画面の部品（図の配置の計算など）は、ダッシュボードのサーバーが配る。インターネットの CDN には頼らない（AC-17）。モックは CDN を使ったが、本番では使わない。
- ボードと構造の図からは、まず要点を出し、そこから詳しい画面へ移る。図やボードを見たまま、次々に選べるようにするため。
- 片付けの候補は、見るだけにする（R-A4 に従う）。
- 作業中の場所の worktree とブランチは、そのPCで観測できるものだけを示す。構造のスナップショットにはPCごとの情報がないため。
- 速さの目安（AC-15）は、モックでの実測を基にした。spec-dock の248件で、構造の図の配置の計算は約0.1秒だった。
- 1つのダッシュボードは1つのリポジトリを扱い、複数を同時に動かせるようにする（R-A3）。統合ダッシュボードが、各リポジトリの個別のダッシュボードへリンクするため。
