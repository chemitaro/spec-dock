SpecDock テスト実行時間の根本原因と再設計案

結論から言うと、4時間級のテストを4 shardへ分けることは根本解ではありません。現在の重さは、巨大化したdistribution機能、同じ契約の重複テスト、process・Git・venv・大規模コピーを何度も通る実行方法から生じています。目標は、必要な契約を一度ずつ証明し、単一のpytest processでも10分以内に終わる構造です。

最初に押さえる結論

問題は「並列数が足りない」ことではありません。

GitHubの4 shard実行は約99分で終わりましたが、4 processの経過時間を足すと約5.51時間です。並列化は総作業量を消さず、CPUとrunner resourceへ押し込んでいます。

  1. production contractが大きすぎます。 install / update / uninstall / purgeが、path identity、journal、retry、crash recovery、historical compatibilityを一つのengineで扱っています。
  2. 同じ契約を何度も証明しています。 managed distribution 575 casesは、同一candidateで最大4回実行されます。
  3. 高価な境界を使いすぎています。 Python subprocess、Git repository、wheel / sdist、venv、pip install、44 MB級dogfood copyを多数のtestが反復します。
  4. 失敗testを維持する仕組みが増えています。 26 failuresをledger照合で成功扱いするため、さらにrunner・evaluator・meta-testsが必要です。

第一推奨: provider-owned immutable payloadとuser-owned spec historyを分離し、通常updateを「stage → validate → activation record一つのatomic swap」へ縮小します。その後、durable invariantを最も安いlayerで一度だけ証明します。

install / update / uninstall testsが多い本当の理由

      
関連する主要4 test filesは合計約35,000行です。これは単にtest authorが細かすぎるからではありません。production側が次の状態を公開契約のように扱っているためです。

      
    
        
  • regular file、directory、symlink、hardlink、FIFOとparent chainのidentity
    • 
        
  • provider manifest、historical identity、version recognition、generated projections
    • 
        
  • preservation witness、closed-set evidence、plan digest、journal、forward guard
    • 
        
  • crash checkpointごとのresume、cleanup、quarantine、predecessor reservation
    • 
        
  • create、upgrade、deprovision、explicit spec-history purgeのintentとcross-intent mismatch
    • 
        
  • same bytes but new inode、path rebind race、malformed markerなどのfail-closed cases
    • 
      

      

        
残すべき安全性: foreign pathを削除しない、symlinkをfollowしない、ownershipやparent identityが変わったら書込み前に止まる、user historyを保護する、candidate artifactをhashで固定する。

      

      

        
Product判断が必要な複雑性: arbitrary checkpointから自動rollback / resumeすること、cross-intent journalを永続互換にすること、通常uninstallとuser history purgeを一つのengineで行うこと、すべてのhistorical workspaceを直接upgradeすること。

      

      
推奨する小さな契約

      
    
        
  1. 所有権を分ける: provider-owned payloadとuser-owned spec-dock/ historyを別のboundaryにします。
    2. 
        
  2. immutable payloadをstageする: 新versionをbounded managed rootの別directoryへ完成させ、manifest、digest、実行可能性を検証します。
    3. 
        
  3. activationを一度だけ切り替える: 同一filesystem上のactivation record一つをatomic replaceします。active payloadをin-place mutationしません。
    4. 
        
  4. cleanupを成功判定から分ける: activation前の失敗では旧versionを使い続け、activation後のold payload cleanup failureでは新versionをactiveのまま保ちます。
    5. 
        
  5. driftは直さず止める: provider ownershipを証明できないfileは上書き・削除せず、診断を返します。
    6. 
        
  6. 通常uninstallはhistoryを保持する: exactly provider-ownedな対象だけを削除します。
    7. 
        
  7. 互換性を有限にする: 第一推奨はcurrent + N-1です。それ以前はone-shot migrationまたはbackup後のre-initへ送ります。
    8. 
      

      
repo-local runtimeが不要ならpackageから実行する構成が最も小さくなります。offline・self-contained要件でcopyが必要なら、一つのversioned managed payloadとthin entrypointに集約します。

    


    

      
四つの選択肢

      

        

          
選択肢product変更wall / CPU改善safety / compatibility判断

          
            
A. shard・cache・runnerだけ改善なしwallのみ。総作業量は残る現行を維持却下

            
B. testだけlower layerへ移す小中程度巨大stateの証明は残る移行手段

            
C. product contractとtestを同時に縮小中〜大wall / CPU双方を根本削減fail closedを残し、自動復旧を縮小第一推奨

            
D. repo-local distributionを廃止最大最も小さいoffline / self-contained要件と衝突の可能性長期候補

          
        

      

      
Option Cは、testを減らすために安全を捨てる案ではありません。「未知の対象へ書かない・消さない」というfail-closed invariantを残し、「あらゆる途中状態を自動復旧する」という別のpromiseを縮小する案です。

「遅いから削除」は禁止します。削除は、現在の契約を廃止した証拠か、より安いlayerのreplacement proofがある場合だけ行います。

      

        

          
判定具体例必要な証拠

          
            
Keepforeign path保護、no-follow、parent rebind block、artifact digest、history保持、再実行収束、OS差current security / public invariantへ直接link

具体的な縮小方法

      
    
        
  • file種別 × checkpoint × intent × driftの完全直積を、equivalence partition、pairwise、property testへ置き換えます。
    • 
        
  • wheelは代表end-to-endを実行し、sdistはbuild・metadata・import proofへ縮小します。behaviorが同じuse caseを双方で繰り返しません。
    • 
        
  • 44 MB級dogfood treeは一つのrelease smokeだけに使い、通常contractは1.6 MB級provider assetsまたはminimal synthetic workspaceを使います。
    • 
        
  • CLI subprocessはpublic commandごとに代表happy pathとfail-closed pathを基本上限にします。parserとrendererはin-processで試します。
    • 
        
  • Issue名testは現在のinvariant名へ置換します。successorができたら旧nodeを同時に削除します。
    • 
      

      
全2,708 nodeの個別削除一覧はまだ断定していません。100% contract mappingは最初の実装Issueの成果です。調査段階で件数だけを目標にすると、安全testを誤って削るためです。

実装前にProduct ownerが決める六つのgroup

      

        

          
1. spec-history purge

          
推奨: 通常uninstallはhistoryを常に保持し、自動 --remove-specs を廃止します。

          
維持する場合は、purge専用security contractとplatform smokeが必要です。

        

        

          
2. lifecycle / recovery

          
推奨: init --forceを廃止またはpayload reinstallに限定し、自動rollback / resumeを外します。current + previousの最大2世代にします。

          
維持する場合は、force・journal・GC・recovery matrixを削れません。

        

        

          
3. compatibility window

          
推奨: direct updateはcurrent + N-1です。それ以前はone-shot migrationまたはre-initとします。

          
実利用versionの情報がないため、これは推奨であって確認済み事実ではありません。

        

        

          
4. repo-local runtime

          
推奨: 不要ならpackage executionへ寄せ、必要ならversioned immutable payload + activation recordへ集約します。

          
offline・self-contained要件を先に確認します。

        

        

          
5. artifact / platform evidence

          
推奨: wheelを通常PR、sdistをrelease、macOSはOS差だけ、dogfood parityはmanifest / hash中心にします。

          
全lifecycleを毎PR・各OSで繰り返すと10分目標を満たせません。

        

        

          
6. public compatibility

          
推奨: 廃止するCLI flagsとJSON fieldsをdeprecationまたはbreaking changeとして明示します。

          
policyがなければ旧adapterとtestを無期限に維持することになります。

        

      

      

        
この六つのgroupは下位Issueが推測で決めてはいけません。回答がない間、EpicのRequirement / Design / Planはdraftを維持し、子Issueを作成・開始しません。
