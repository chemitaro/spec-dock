今回のP1は何が問題だったのか

結論: 今回のP1は、認証情報が漏れたことを観測したという意味ではありません。Issue作成処理の「作成前に公開先Repositoryを確定し、確定した先へだけ書き込む」という契約が、現在の実装許可範囲と受入条件に明示されておらず、実装しても証明できない状態だったことが問題です。

現在の作成経路は、originのfetch URLからread-onlyのRepository identityを確認した後、GitHubのIssue作成へ進みます。しかし、作成前にfetch/pushの公開先整合性を検証する既存のpublication endpointを呼ぶ契約と、gh issue create --repo <owner/repo>で作成先を明示的に束縛する契約が、applicationのcall graphに接続されていませんでした。そのため、認証済み環境で作成を実行した場合に、意図しないRepositoryへの副作用を作成前に止められると、仕様上もテスト上も証明できません。

観測した事実

fetch-only identity resolverは存在します。publication endpointもfetch/push、userinfo、Repository不一致を検証します。ただし、Issue作成経路からpublication endpointへ接続されていません。

まだ確認していないこと

本レビューは実運用での認証情報漏えいや誤Repository作成を報告するものではありません。作成境界の契約欠落を、実装前にP1として扱っています。

なぜ安全性に関係するか

書き込み前のRepository確定がなければ、成功したように見えるIssue作成が別の公開先へ向かう可能性を排除できません。副作用前に失敗させることが必要です。

同時に見直した、Epic #384の簡素化ポイント

  1. 補助履歴: 16件のsupport historyは現在の仕様ではなく、no-diffだけで保全する情報資料です。mode、object type、Git object IDの一致を、実装開始の二重ゲートにしません。
  2. Issue間のSHA結合: Issue #392のProduct gateへ、Issue #395/#396の文書SHAを同期しません。#392のbaseline assertionはP392のimmutable ledger blobで独立して検証します。
  3. Parser: preflightに別のurlsplitやregex parserを持たず、production resolverを一つの正本として利用します。
  4. 重複実行: clean candidateのfull verifierが収集したfull-regression結果を正本とし、同じnodeやsuiteをN3で再実行しません。N3では、別policyのordinary laneを一度だけ実行し、lint、SpecDock validation、手動境界証明を追加します。
修正後の作成経路: create/link_existing → 既存publication endpointを一度だけ実行 → accepted slugをsame-repository validationへ渡す → create時はIssueGatewayへslugを渡す → gh issue create --repo <slug>。importは従来どおりfetch-onlyです。retry、cache、feature flag、二重parserは追加しません。

ユーザーに求める判断

新しいProduct方針や追加のsecurity選択を求めているわけではありません。判断してほしいのは、次の最小方針で仕様レビューを再実施してよいかです。

  1. 既存publication endpointを一度だけcreate境界へ接続する。
  2. Issue作成先を解決済みslugで明示する。
  3. importのfetch-only挙動、既存のsame-repository検証、credential non-exposureを維持する。
  4. Strictスペックレビューがreview_status=pass、P0=0、P1=0になるまでProduct/test変更を開始しない。

現在はこの再レビューが必要な段階です。仕様レビューがpassした後に実装を開始し、実装後には作成前失敗と明示的な--repoをfocused create-boundary testで、4ケースのpublication policy matrixを専用diagnosticで確認します。
