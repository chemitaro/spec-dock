最初に把握するべき4点

1

same-EUID問題は「実装バグ」だけではありません

同じEUIDで非協調なprocessがpathを自由にrename/replaceできる前提では、通常ユーザー権限CLIだけで「自分が作成したinode」を継続的に証明するのは困難です。現在のFirst REDはその境界を実際に再現しています。

2

Option 1 は製品境界に合っています

SpecDockを軽量な文書管理CLIとして維持するなら、privileged broker、daemon、OS policy subsystemを導入するより、協調SpecDock process間の整合性を保証し、同資格情報の非協調actorは境界外と明示する方が責務に整合します。

3

現在、証拠ソース同士に差があります

接続GitHub先端にはFirst REDと設計判断要求が記録されています。一方、今回提供された添付snapshotにはaccepted safe-stop ADRと停止済みR/D/Pがありますが、そのADRは接続GitHub branchには存在しません。実装再開前にこの差を解消する必要があります。

4

full regression問題は別件です

現行Reportは #395 所有baselineに関する ledger-mismatch 10件を記録し、#392起因の新規unexpected failureは0としています。しかしEpic要件はB1でfull-regression pathのGREENを要求しています。この整合問題はOption 1では解消しません。

なぜ停止したのか

観測されたraceは次の形です。

A. SpecDockが mkdir("spec-dock") に成功
→
B. 同一EUIDの非協調actorが作成directory Xを退避
→
C. 同owner/modeの別directory Yを同pathへ配置
→
D. SpecDockがpathをopenし、Yを「作ったdirectory」と誤認
→
E. Yへprovider内容を書き込む

既存のplanned-create EEXIST testは「exclusive create時点で既に競合物が存在する」scheduleを扱います。今回のREDは「create成功後、最初のopen前に置換される」別scheduleです。この差が、単なるEEXIST対応では閉じない理由です。

推奨する脅威境界

推奨文言の要旨: SpecDockが保証するのは、WIR-COORDのlease/handoff/helper-lifetime規約に参加するsupported SpecDock CLI invocations間の協調、および通常のfilesystem/I/O failure・crash/recovery・観測可能なbinding driftに対する定義済み挙動です。同じEUIDでありながらこの協調規約に参加せず、operation中にpath/inode/bytesを任意変更できるactorは脅威モデル外とします。
Actor / failureScope保証
協調するSpecDock CLI / managed helperINrepository-root SH/EX coordination、helper lifetime、release→exec、busy時mutation-zero、generation整合を維持。
通常のI/O failure、fsync/rename failure、process crashINP0/P1/P2、ACTIVE/stage/receipt、forward recovery、protected data preservationを維持。
観測可能なsymlink/type/owner/binding driftIN既存のfail-closed検査を維持。これはcorrectness/defense-in-depthでもある。
同一EUID・非協調processによる任意rename/replace/writeOUTcreator provenance、non-interference、hostile filesystem safetyを主張しない。
異なるcredentialsのactorOS BOUNDARYOS permission/ownership/ACLを信頼境界とし、SpecDockは観測可能な不整合をfail closedする。root/同等capabilityへの耐性は主張しない。

この境界は「チェックを削除する」判断ではありません。既存no-follow、inode witness、owner/type確認、atomic rename、binding再検証は、通常障害・誤操作・協調競合に対する安全性として残します。

Option 1 が変えるもの / 変えないもの

変えるもの

  • same-EUID非協調actorをsecurity/threat requirementから明示的に除外。
  • creator provenanceを「same-EUID hostile actorにも成立する」と読めるRequirement/Design/Wire文言。
  • その攻撃scheduleのみを受入要件とするcreation-replacement test。
  • safe-stop ADRのcurrent authority status（履歴は残す）。

変えないもの

  • protected consumer data preservation。
  • native no-replace/exchange、no-follow、hard-link/special-type rejection。
  • crash recoveryとACTIVE/stage/receipt。
  • cooperating CLIのSH/EX coordinationとmanaged helper lifetime。
  • exact migration / tooling-only uninstall / closed public wire。
  • #392 → #395 → #396 の責務順序とhuman-only merge。
