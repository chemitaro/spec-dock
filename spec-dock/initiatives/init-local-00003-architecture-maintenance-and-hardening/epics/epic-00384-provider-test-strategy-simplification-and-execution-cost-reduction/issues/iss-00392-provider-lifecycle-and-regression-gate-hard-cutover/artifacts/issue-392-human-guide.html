背景

現行0.2.3は、個々のmanaged file、historical manifest、複数のjournal/retry stateを使ってinstall/update/uninstallを進めています。#392はこれを部分改修せず、管理単位を四つのroot、二つのskill slot、一つのinstallation recordへ縮めます。

目的は「更新を常に成功させる」ことではありません。所有権が証明できない物、世代が混じる状態、Gitやfilesystemの実効動作を証明できない状態を、利用者データへ触れる前に停止することです。

中心原則: Provider toolingはreplaceable、利用者のspec・Artifact・Workbenchはopaqueに保護、復旧はexact tupleに束縛したforward recoveryです。

用語

Candidate

0.2.4で公開する四rootと二slotのexact content/type/mode集合です。SHA-256 digestで一つの世代を識別します。

Installation record

spec-dock/spec-dock.versionに置く7-key compact JSONです。ready/incomplete/tooling-absentを公開します。

ACTIVE / STAGE / receipt

Consumer外のprivate stateです。中断位置とcleanup完了を、repository inodeとeuidへ束縛します。

SH / EX lease

同じrepository-root inodeに対する共有・排他flockです。通常runtimeはSH、installerと変更先worktreeはEXです。

Provider closure

四root、二slot、record/markerが同じcandidate generationであることを示す集合です。

B1

#392をEpic integration branchへ人間がmergeした後、そのmerged tipで再度GREENを確認した状態です。

Epic内の実装順序

#392、#395、#396は並列化しません。#392がlifecycleを固定し、#395が既存14 failureの契約を修復し、#396が最後にgate machineryを簡素化します。

Runtime、Git、worktree B、make hook

      
Runtime module自体が交換対象なので、lease取得とready確認はimportより前のfrozen bootstrapで行います。Update/uninstallはold moduleへ戻らず、bootstrapがleaseを閉じて外部installerへexecします。

運用上の注意

      
    
        
  1. 初回0.2.3→0.2.4だけは旧SpecDock writerを止めるmaintenance windowが必要です。
    2. 
        
  2. Private stateを手動削除しません。Unknown objectやforeign ownerはpreserve-and-blockです。
    3. 
        
  3. Recovery中にinstall/update/uninstallを切り替えません。Wireが示すexact continuationだけを使います。
    4. 
        
  4. --remove-specsは互換削除routeではなく、exit2/mutation0です。利用者specをlifecycleがpurgeしません。
    5. 
        
  5. Incident時は新commandを止め、public result、record/ACTIVE/receipt hash、repository inode、OS/native capabilityを保存します。Cleanup tokenを公開ログへ不要に転載しません。
    6. 
        
  6. Unmerged failureはbranchを破棄できます。Merged B1 failureは人間がwhole merge revertを判断し、旧writerの部分復活やpartial cherry-pickを行いません。
