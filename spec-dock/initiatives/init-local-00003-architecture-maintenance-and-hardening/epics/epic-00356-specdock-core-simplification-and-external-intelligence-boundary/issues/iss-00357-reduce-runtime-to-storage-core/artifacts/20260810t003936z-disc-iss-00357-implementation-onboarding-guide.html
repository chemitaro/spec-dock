Runtimeを「Storage Core」へ縮小する

Issue 357 Reduce Runtime to Storage Core の背景、設計上の境界、実装の順番、失敗時の扱いを、実装を担当するメンバーが一つの資料で理解できるようにまとめた解説です。

1. この資料の位置付けと現在地

このHTMLは人間向けの補助Artifactです。長期的な判断・実装契約の正本は、このIssueの要件定義書、設計書、実装計画書（以下、R/D/P）と、採用済みADRです。Reportは実施した証拠、進捗、結果の要約を残す場所であり、計画や品質を自動判定する正本ではありません。この資料が正本と異なる場合は、必ず正本を優先します。

現在の状態：planning-ready R/D/Pは承認済みです。ただし実装、テスト変更、commit、push、PR、merge、issue finishは未実施です。「ready」はE00から着手できることだけを示し、実装完了や終了許可を意味しません。

ここでの「推論」は、正本の複数箇所を分かりやすくつなげるための説明です。新しい製品判断を追加するものではありません。

2. 5分で分かる全体像

SpecDockには、ノード、依存関係、GitHub Issue、現在選択中の対象、成果物を安全に扱うという構造的で決定的な仕事があります。一方、workflow、Profile、Assurance、レビュー合格、Evidence Adoption Ledger（EAL）、特定提供元のAI取込といった組織や案件で変わる認知的な仕事もRuntimeに混在しています。

Issue 357は後者をRuntimeのCurrent surfaceから外し、前者だけを確実に実行するStorage Coreへ縮小します。AI、レビュー、品質評価そのものを禁止するのではありません。それらをRuntimeの必須状態機械から外し、チームが文書と外部の道具を使って選べる仕事へ戻します。

5. CLI surface：何を残し、何を撤去するか

Targetの正本inventoryはR/D/Pに固定されています。実装中に「便利そう」という理由で新しいtop-level command、互換alias、hidden fallbackを足してはいけません。物理ファイルを先に消すのではなく、parser / registry / bootstrap / import graphから到達不能であることを先に証明します。

保持する主要surfaceTargetでの意味

6. activeは「選択のみ」、開始は「依存を確認してから」

6.1 active set はselection-only

active setは、validなInitiative / Epic / IssueをIDまたはrepo-relative pathで選び、選択chainを保存する操作です。GitHub照会、dependency判定、unfinished guard、R/D/P、review、Report、authorityを読みません。したがって依存でblockedなIssueでも、調査・計画のためにactiveにできます。

TargetのActiveManifestEntryはidとpathだけです。legacy JSONの余剰fieldは読めますが、読むだけでは書き換えず、明示的なactive mutationのときだけminimal schemaへ正規化します。

6.2 issue start の真理値表

開始は、target解決後に「別のunfinished active Issueがあるか」をactive manifestとlinked GitHub stateで判断します。現在のbranchは診断情報であり、判定を変えません。--forceが迂回できるのはunfinished guardだけで、dependency、invalid target、checkout失敗、active write失敗は迂回できません。

active IssueGitHub statetargetとの関係forceなしforceあり
なし該当なし任意dependency確認へdependency確認へ
あり任意同じIssuedependency確認へdependency確認へ
ありCLOSED別Issuedependency確認へdependency確認へ
ありOPEN別Issueguardで停止guardのみ迂回しdependency確認へ
ありUNKNOWN、linkなし、取得失敗、解決不能別Issuefinishedと推測せず停止guardのみ迂回しdependency確認へ

7. issue finish はclose → clear → syncの便利操作

終了時にRuntimeが品質を判定してはいけません。R/D/P、テスト、review、Report、EAL、authority、promotion recordは読まず、active IssueとGitHub linkageを解決して、順番に操作します。

  1. linked GitHub Issueをcloseする（すでにclosedなら成功扱い）。
  2. close成功後にだけactiveをclearする。
  3. clear後にpost-syncする。
失敗地点結果復旧の考え方
GitHub close失敗activeを保持、close未完了原因を直してcloseを再試行
すでにclosed成功としてclearへ進む手作業で閉じた場合も二重失敗にしない
close成功後のclear失敗GitHub close済み、active残存、sync未実行というpartial successactive clearを回復してからsync
clear成功後のsync失敗active clear済み、projection stale同期を再実行する

これは「終了の品質を弱める」判断ではありません。品質の判断はチームの正本・レビュー・実装運用で行い、Runtimeは外部状態を壊さず部分成功を隠さない、という責務分離です。

8. Artifact：新規作成、履歴認識、ファイル取込を分ける

8.1 Currentで新しく作れる六種

new artifact [type]のtypeはoptional positionalです。省略と明示blankは同じ契約で、--type構文は増やしません。新規作成可能なのは次の六種だけです。

blank型を先に決めない作業メモ。filenameにblank tokenは入れない。
research根拠付き調査。事実、推測、未検証を分ける。
interview重要判断を一問一答で残す。
disc統合・中間報告・論点整理。
decision-candidate正本/ADRへ採用前の判断候補。
adr意思決定記録。acceptedになるまで非正本。

8.2 Historicalは「読めるが新規に作らない」

既存のpr-repair-batch、draft-requirement、draft-design、draft-plan、scratch、note、連番のADR/disc/note、generic imported Artifact、legacy discussions/はHistorical catalogとして認識します。これらを新規候補へ戻したり、Current navigationやworkflow routingへ自動昇格させたりはしません。一方で、catalog外のtimestamp-intent、duplicate、broken timestamp、symlink、path escapeは引き続き診断します。

8.3 generic file importだけを残す

artifact import fileは、一つの明示regular fileを対象scopeへ安全に保存します。bytesは解釈・変換せずopaqueのまま扱い、path traversal、symlink、unsafe source、collisionを拒否します。外部sourceに失敗した診断でもabsolute path、内容、hashを漏らしません。artifact import chatgpt-outputと提供元固有routingは撤去します。

9. Fresh scaffoldと、validate / doctorの境界

新しいInitiative / Epic / Issueは、既存のcopy mechanismを用いてrequirement.md、design.md、plan.md、report.mdを各一つ作ります。Profile選択、Assurance compose、Report本文解釈、draft routingは行いません。薄いReportや空の利用者記入欄も構造上は有効です。

357が保証するもの357が検査しない/決めないもの

つまりvalidateとdoctorは構造検証です。empty thin Report、heavy Report、EAL文字列、legacy authority metadata、.assurance.jsonの有無や内容だけで結果を変えてはいけません。ただし、同じfixtureに独立した構造破損があれば通常どおり診断します。

rollbackはregistration、active/lifecycle、Artifact、scaffold、module deletion、docsの境界ごとに行います。ユーザー所有のnode文書やmetadataをmigration対象にしないため、rollbackでそれらを書き戻そうとはしません。
