1. 目的と完成像

現状は、R/D/P template に workflow、Grade、reviewer、promotion、EAL、delegated authoring が混在し、Issue Design / Plan は Assurance compose 待ちの placeholder です。Profile、draft routing、重い Report scaffold、Current と Historical の混在により、利用者は仕様を書く前に旧運用を理解する必要があります。

4. R/D/P/Report と scope layering

R/D/P は同じことを三回書くための文書ではありません。質問の種類を分け、後から読む人が「なぜ」「どう作る」「どう進める」を辿れるようにします。

文書主に答える問い置かないもの
requirement.mdなぜ、何を、誰に、どこまで、何をもって成功かmodule 構造、実装順、test の細部
design.md責務、Current / Target、interface、data、failure、migrationbusiness acceptance の再定義、進捗
plan.md順序、依存、検証、rollback、exit / handoff、Planning Level未承認の durable decision
report.mdOutcome、Verification、Residual Risks / Follow-ups、任意の Notesdecision ledger、quality gate、実装許可

Initiative は戦略 problem と投資境界、Epic は coherent な outcome と Issue 間契約、Issue は一つの end-to-end value と実装・test・docs・rollback を所有します。Initiative / Epic に Issue の micro-step や Planning Level を複製せず、Issue が親の方向を再定義しません。

5. Planning Level：承認済み Option A

Option A は、Issue ごとに canonical な plan.md を一つだけ置き、共通の Base Plan Guide と、light / standard / strict / critical の四つの独立 Completion Guide を提供する方式です。plan-light.md のような別の正本計画書は作りません。

Level選ぶ目安強く求める完成像
light影響が局所的で revert が容易direct AC、対象を絞った verification、残作業なし
standard通常の feature / bug fixend-to-end 順序、主要 error、regression、基本 rollback
strictpublic contract、Runtime、data、migration、互換性As-Is / To-Be、failure mode、negative test、rollback / forward recovery
criticalsecurity / privacy、高 blast radius、不可逆・回復困難threat / data、段階 rollout、kill switch、backup / restore、incident response
禁止される選び方：Priority、Severity ラベル、工数、dependency readiness、implementation handoff status だけで level を決めません。失敗時の影響と復旧困難性で選びます。

6. Artifact、Current / Historical、正本の境界

Current の新規作成導線では次の六種だけを説明します。作成しただけで採用済みにはなりません。

Type使う場面durable な反映先
blank型を決めない自由形式 evidence必要な内容を R/D/P または accepted ADR へ再記述
research一つの source に根差した調査facts / constraints を正本へ
interview質問と回答採用回答を正本へ
disc複数根拠の統合・trade-offdurable conclusion を正本へ
decision-candidate未採用の選択肢人間判断後に正本へ
adrarchitecture decision candidate / recordaccepted と明示された ADR のみ authority になり得る

analysis は追加しません。一つの source は research、複数 source の統合は disc を使います。repair、draft-*、Profile 用 surface は Current に置かず、過去のものは Historical として削除・rename・rewrite せず保持します。

authority flow：Artifact evidence → 人または agent の synthesis / review → Requirement / Design / Plan または accepted ADR → implementation → thin Report。Artifact、外部 ZIP、delegated draft、ChatGPT output の存在は自動採用を意味せず、Report も durable decision store ではありません。

10. 担当者の 8 段階通し例

  1. 正本を読む。Requirement / Design / Plan で 358 の所有境界を確認する。
  2. E00 で現物を数える。provider / dogfood path、relative link、copy depth、preservation hash を収集する。まだ asset を変えない。
  3. Guide の骨格を作る。Overview から R/D/P/Report と scope layering に辿れる状態を作る。
  4. 雛形を薄くする。各 scope に R/D/P/Report 一つずつ。完成文書に残らない policy を入れない。
  5. Plan の完成像を分ける。Base Guide と四 Completion Guide を用意し、同じ plan.md に選択理由を書く。
  6. Artifact と Historical を整理する。Current 六種を明示し、過去 evidence を消さず別導線へ置く。
  7. 357 と IC-1 を行う。生成機構を変更せず、生成結果が文書契約と一致するかを確認する。
  8. 保全・handoff・品質 gate を閉じる。hash 不変、359 / 360 manifest、review、test、diff をそろえてから commit 候補を検討する。
