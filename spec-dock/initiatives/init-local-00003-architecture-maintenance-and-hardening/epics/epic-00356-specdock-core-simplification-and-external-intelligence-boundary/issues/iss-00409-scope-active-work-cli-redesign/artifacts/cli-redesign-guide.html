01 / OVERVIEW

新CLIの中心は、三つの入口です。

scopeは管理対象そのもの、activeは現在の選択、workは作業開始・正常終了です。同じ「対象を操作する」ように見えても、変える状態が異なります。

RESOURCE

scope

作成、取込、一覧、表示、title編集、Close、Reopen、Deleteを扱います。

SELECTION

active

show / set / clearです。選択するだけでcheckoutや完了は行いません。

WORKFLOW

work

startはbranchと選択、finishは完了と選択解除を組み合わせます。

GIT ONLY

branch

対応branchのshow / create / switchです。選択や完了を変更しません。

重要な変更は、短い名前への置換ではありません。新しいDeleteはGitHub Issueを閉じません。新しいSyncはactiveを推定しません。Worktree createはmake initを実行しません。

このガイドは新規参加者が会話履歴なしで読むための説明資料です。現在の基準コミットに、新CLIが実装済みという意味ではありません。本文のコマンドは新実装後の文法です。

02 / LANGUAGE & STATE

同じ対象でも、状態は別に持ちます。

用語意味
ScopeInitiative・Epic・Issueの総称です。仕様、依存、Artifact、開始・終了を持つ管理対象です。
Initiative最上位の広い目的です。複数のEpicを束ねます。
Epic一貫した成果を持つ範囲です。Initiativeの下でIssueを束ねます。
Issue具体的なend-to-end作業単位です。Epicの下に置きます。
Active / focus現在のworktreeの選択チェーンです。focusは最下位の選択対象です。作業中を意味する永続statusではありません。
Backend完了状態の権威です。githubならGitHub Issue、localなら追跡するmetadataに保存します。
Canonical branchScopeに一つだけ対応する名前付きGit branchです。タイトル変更では改名しません。
WorktreeGitの独立した作業directoryです。長寿命でもよく、一つのScopeが完了しても削除しません。
Artifact調査・検討・外部fileなどの証跡です。作成や取込だけでは正本や採用済み判断になりません。
Workbench任意の一時的・非正本作業領域です。copyは一回だけで、同期ではありません。
Derived stateindex、tree、dashboard、依存表示などの生成物です。一次仕様や選択を勝手に変更する理由にはしません。
Journal / partial操作のphaseとeffect記録、および部分成功です。クラッシュ後に何が起きたかと再開対象を固定します。
Writer / common directory状態を書き込む実行経路と、linked worktreeが共有するGit管理領域です。write互換性をこの単位で揃えます。
Dogfooding / consumerSpecDock自身のrepositoryに導入した作業用workspaceと、別repositoryの導入先です。配布sourceとは区別します。

localの完了は、別branchへ自動伝播しません。親branchで子の完了を参照するには、通常のGit統合が必要です。全worktreeのwriterが同じ版であることと、別branchの内容が同じことは別です。

業務leafは42、utilityのhelpとcompletionを加えて44です。作成や取込はkindを明示し、既存対象の操作はIDからkindを解決します。対象を省略して現在のIssueを推測しません。

spec-dock scope show "$SCOPE_ID"
spec-dock active show
spec-dock active set "$SCOPE_ID"
spec-dock work start "$SCOPE_ID" --base HEAD
spec-dock work finish "$SCOPE_ID" --yes

上記は入口の対照です。$SCOPE_IDは実際に選定した対象です。既存branchのstartには--baseを付けません。各行を無条件に連続実行する手順ではありません。

04 / TARGETS

明示対象と、選択中の対象を区別します。

指定意味操作例
完全Scope ID指定した対象だけを解決します。scope show "$SCOPE_ID"
@current現在のfocusを解決します。未選択ならエラーです。scope show @current
@initiative / @epic / @issue現在チェーンの該当階層です。focusとkindが異なっても参照できます。work finish @epic
gh:OWNER/REPO#NUMBER同repositoryで既にリンクしたScopeです。通常TARGETで裸番号は使いません。scope show "$GITHUB_REF"
@rootroot Artifact配置先専用です。start/finish/Workbenchでは使いません。artifact import file ./evidence.html --scope @root
wt:ID / 絶対path登録済みのworktreeです。曖昧なbasenameを使いません。worktree show "$WORKTREE_REF"

「表示」「選択変更」「対象変更」は別です。

# 選択を変えずに指定対象を表示します。
spec-dock scope show "$SCOPE_ID"

# 選択チェーンを表示します。
spec-dock active show

# 選択だけを変更します。checkoutしません。
spec-dock active set "$SCOPE_ID"

# 選択中の対象のtitleだけを変更します。
spec-dock scope edit @current --title "更新する仕様名"   --expect-current "$SCOPE_ID" --json

非対話の変更にcurrent系selectorを使う場合は--expect-currentで現在focusの実IDを指定します。@epicを使う場合も、期待値は「現在focus」です。実行直前にrevisionも照合します。

親省略はありません。--parent @epicは明示した動的selectorとして使用できます。Artifactのroot以外では--scopeも同じ規則です。複数のselectorを使う一回の操作は、一つのsnapshotで解決します。

05 / LIFECYCLE

Start・Finish・Close・Deleteは同義ではありません。

操作選択への効果Gitへの効果lifecycle / データへの効果
active set対象と祖先を選択します。なしなし
active clear対象以下または全選択を解除します。なしなし
work start対象と祖先を選択します。作成/checkout開始条件の観測。完了はしません。
work finish対象以下を解除し、祖先を残します。なし対象をcompletedにします。
scope close変更しません。なしcompletedまたはnot-plannedにします。
scope reopen変更しません。なし対象だけopenへ戻します。
scope delete明示許可時だけ対象以下を解除します。branchを残します。remoteは触りません。ローカル所有物を削除します。

Startの処理順

Finish後は、祖先の文脈を残します。

未完了の子がある親をfinishできません。open、not-planned、unknownの子孫を自動で閉じません。親自身のcompletedも、子の進捗集計とは別です。空の親は他の条件を満たせば完了できます。

Closeはactiveを残します。scope close TARGETで理由を省略するとcompletedです。取り止めは--reason not-plannedを明示します。親をcompletedにする際は、既にcompletedで同じ理由を再指定する場合も、現在の子孫が全てcompletedか先に確認します。open・not-planned・unknownの子孫があれば拒否し、全てcompletedの場合だけremote書込みなしのno-opです。取り止めとして親だけをnot-plannedにする場合、子はそのままです。取り止めは前提依存の完了ではありません。終端理由を変更するには明示reopenを挟みます。

06 / WALKTHROUGH

正常系を、実際に返されたIDで操作します。

以下の例は新実装後の隔離演習です。IDは作成結果から取得し、実在しないIssue番号をこの資料で発行済み扱いしません。実行場所は新しいschemaと必要な初期commitを持つ練習projectです。

1. Localで三階層を開始・終了する

# Bashの例です。新CLI導入済みの隔離した練習project内で行います。
# 実データ上で試す指示ではありません。
set -euo pipefail

INIT_ID="$(spec-dock scope create initiative --backend local   --title '操作体系の練習' --slug cli-practice --json   | python3 -c 'import json,sys; print(json.load(sys.stdin)["data"]["scope"]["id"])')"
EPIC_ID="$(spec-dock scope create epic --backend local --parent "$INIT_ID"   --title 'ライフサイクルの練習' --slug lifecycle-practice --json   | python3 -c 'import json,sys; print(json.load(sys.stdin)["data"]["scope"]["id"])')"
ISSUE_ID="$(spec-dock scope create issue --backend local --parent "$EPIC_ID"   --title '正常終了を確認する' --slug finish-practice --json   | python3 -c 'import json,sys; print(json.load(sys.stdin)["data"]["scope"]["id"])')"

# checkout先にも仕様が存在するよう、通常のGit commitを行います。
git add spec-dock/initiatives
git commit -m "Add CLI practice scopes"

spec-dock work start "$INIT_ID" --base HEAD --offline
spec-dock work start "$EPIC_ID" --base HEAD --offline
spec-dock work start "$ISSUE_ID" --base HEAD --offline
ISSUE_BRANCH="$(git branch --show-current)"

spec-dock work finish "$ISSUE_ID" --yes --offline
# local completionはtrackedです。必要なfileだけをstageします。
git add spec-dock/initiatives
git commit -m "Complete practice issue"

# 親branchへ戻ってから、明示Git統合で子の完了を反映します。
spec-dock work start "$EPIC_ID" --offline
git merge --ff-only "$ISSUE_BRANCH"
EPIC_BRANCH="$(git branch --show-current)"
spec-dock work finish "$EPIC_ID" --yes --offline
git add spec-dock/initiatives
git commit -m "Complete practice epic"

spec-dock work start "$INIT_ID" --offline
git merge --ff-only "$EPIC_BRANCH"
spec-dock work finish "$INIT_ID" --yes --offline
spec-dock active show --json

最後のInitiative完了もlocalのtracked変更です。保存する場合は必要なfileだけをcommitします。上の--ff-onlyが失敗したら、Gitの統合方法を確認してください。SpecDockが代わりにreset・force mergeすることはありません。

2. 既存GitHub Issueを取り込む

# GITHUB_REFとEPIC_IDは選定済みの実値です。
spec-dock scope import github issue "$GITHUB_REF"   --parent "$EPIC_ID" --title "採用する仕様名" --slug imported-spec --json

# 新規のGitHub-backed作成はremote書込みを明示します。
spec-dock scope create issue --backend github --parent "$EPIC_ID"   --title "新しく管理する仕様" --slug new-managed-spec --yes --json

ImportはGitHubの読取り確認です。titleは必須で、GitHub側titleをそのまま仕様名にしません。foreign repositoryは拒否します。GitHub backendのfinish/closeはremoteに書き込むため、--offlineでは実行できません。

3. 依存・証跡・作業場を操作する

spec-dock dependency add --from "$ISSUE_ID" --to "$PREREQUISITE_ID"
spec-dock dependency check "$ISSUE_ID" --source github --json
spec-dock artifact create --scope "$ISSUE_ID"   --type research --title "互換性の調査" --slug compatibility
spec-dock artifact import file ./evidence.html --scope @root --json

spec-dock worktree create review --base HEAD --root "$WORKTREE_ROOT" --json
# WORKTREE_REFは上の実出力から取得します。
spec-dock worktree bootstrap "$WORKTREE_REF" --yes --json
spec-dock workbench copy --scope "$ISSUE_ID"   --to-worktree "$WORKTREE_REF" --dry-run --json

これらは個別の利用例です。Dependencyの前提IDは実在する別対象を選定します。Workbench copyには両側の同Scopeとsource Workbenchが必要です。既定衝突は停止し、上書きを行う場合だけ--on-conflict overwrite --yesを追加します。

4. CloseとDeleteを別々に決める

# 完了状態だけを変更します。選択は残ります。
spec-dock scope close "$SCOPE_ID" --yes

# 取り止めにする場合は、別の対象またはopenの対象で明示します。
spec-dock scope close "$CANCEL_SCOPE_ID" --reason not-planned --yes

# ローカル所有物の削除は別の意思決定です。
spec-dock scope delete "$DELETE_SCOPE_ID" --dry-run --json
spec-dock scope delete "$DELETE_SCOPE_ID" --yes --json

親Scopeのdeleteには--recursiveが必要です。activeや境界依存の衝突がある場合は、--clear-activeや--detach-dependenciesを対象と結果を確認して明示します。--yesだけでは通りません。

07 / FAILURE & RECOVERY

失敗したときは、実施済みの効果から判断します。

状況返される意味次の確認
対象省略・activeなし推測せずsyntax/not foundです。active showで確認し、実在IDを指定します。
新branchなのにbase省略Gitを変更する前に停止します。仕様が存在するcommit/refを--baseで明示します。
既存branchへ--base指定無視せず拒否します。既存branchの利用なら--baseを外します。reset目的には使えません。
dirty・他worktree使用checkoutを拒否します。変更を必要な範囲で保存し、所有worktreeを確認します。
親finishで未完了子子を閉じずに停止します。各子の状態と親branchのsnapshotを確認します。
checkout成功・active保存失敗branch変更済みのpartialです。固定IDとoperation IDで再開します。
remote close成功・active解除失敗remoteはcompleted、選択は未解除です。@currentではなく固定IDで再開します。
network timeout・結果不明failedではなくunknown effectを含むpartialです。remoteを再照会し、同じ副作用をblind retryしません。
bootstrap失敗任意の変更が起きた可能性があります。projectの変更を確認します。worktreeを勝手に削除しません。
update/migrate途中停止全体をmaintenanceに保ちます。journalからresumeまたは整合したrollbackを行います。

未完了journalで全変更を止めるのは、明示的な--resumeを備えたScope作成・取込・close/reopen/delete、Work開始・完了、branch作成、workspace移行、installation操作だけです。その他の変更は、対象の状態を確認してから操作別に再実行します。Artifactやworktreeの作成結果が不明な場合は二重作成しません。Workbench copyやbootstrapの部分的な効果は自動で巻き戻したり再実行したりしません。これらの失敗だけで無関係な変更を全体停止しません。

spec-dock active show --json
spec-dock workspace doctor --json

# SCOPE_IDとOPERATION_IDは失敗結果が返した固定値です。
spec-dock work finish "$SCOPE_ID"   --resume "$OPERATION_ID" --yes --json

partialの後にwork finish @currentを繰り返さないでください。最初の処理でfocusが親へ移っていると、別の対象を完了させる危険があります。回復案内は最初に解決した実IDを使います。

共通の終了コード

exit意味
0成功・変更なし・正常なdry-run
1変更未実施を確認できる内部エラー
2構文・selector形式・旧入力の拒否
3前提条件・確認不足・競合・writer不整合
4対象なし・現在未選択
5変更未実施を確認できる外部/環境エラー
6部分成功または副作用の成否不明
7Validate/Doctor等の不整合診断

--jsonは非対話を含意しますが、--yesではありません。--dry-runはmanaged stateやhookを書き換えません。--offlineはSpecDock自身の通信を禁止しますが、任意Makefileをsandbox化する機能ではないためbootstrapと併用できません。

08 / COORDINATED CUTOVER

一回の切替でも、停止・保全・確認は省略しません。

このツールは未公開の利用者専用です。長期の複数releaseは設けません。一つの実装成果を固定し、一回のmaintenance内で順序を付けて切り替えます。複数directoryやrepositoryが物理的に一括commitされる、という意味ではありません。

  1. 対象をすべて記録します。

    provider source、dogfood、各consumerと全worktree、旧agent/task/alias/CI、candidateとbackup先をinventoryに載せます。未確認の導入先を完了扱いしません。

  2. 旧writerを停止します。

    新しいmarkerだけでは古いruntimeを止められません。実行中processと自動起動を停止し、外部Git操作も一時停止します。

  3. バックアップと復元を確認します。

    仕様・Artifact・Workbenchだけでなく、ignored/untracked、index、Git ref、tooling、controlを保全します。隔離した場所へ実際に復元して確認します。

  4. 固定engineを作業場の外に置きます。

    検証済みcandidateの実SHA/digestを固定し、外部entrypointとrepo shimの信頼先を揃えます。更新中に自分のengineが消える構造にしません。

  5. 全作業場のツールをmaintenanceで更新します。

    write対象をdry-runで確認し、同じcandidateのupdate --maintenanceを適用します。途中で一部だけ通常運用へ戻しません。

  6. 全schemaを明示移行します。

    migrateの計画から実inventoryのmappingを作り、backend、active、canonical branchを確認して適用します。foreignや曖昧なbranchは推測しません。

  7. 全対象を検証します。

    show/validate/doctor/sync cache、before/after差分、全writer protocol、旧入力の無変更拒否、pending journalなしを確認します。

  8. 新しい起動経路だけを再開します。

    global inventoryすべてが条件を満たした後で再開します。以後のremote変更はbackupだけでは戻せないため、forward recoveryの境界を記録します。

切替時の新CLI例

# SD / PROJECT / BUNDLE_COMMIT はinventoryの実値です。
"$SD" installation update --target "$PROJECT" --commit "$BUNDLE_COMMIT"   --maintenance --dry-run --json
"$SD" installation update --target "$PROJECT" --commit "$BUNDLE_COMMIT"   --maintenance --yes --json

"$SD" --project "$PROJECT" workspace migrate --to-schema 3 --dry-run --json
"$SD" --project "$PROJECT" workspace migrate --to-schema 3   --mapping-file "$MIGRATION_MAP" --yes --json

"$SD" --project "$PROJECT" installation show --json
"$SD" --project "$PROJECT" workspace validate --json
"$SD" --project "$PROJECT" workspace doctor --json

基準commitと新candidateのcommitは別です。このページに記載した基準SHAは現行sourceの検証値です。新実装の配布SHAとして流用しません。

履歴branchへ戻った場合

古いschemaや旧runtimeが再び現れる場合があります。新外部engineは通常writeを拒否します。読み取り調査として扱うか、停止中の作業場で再導入・明示移行を行い、通常の新commitとして保存します。過去commitを書き換えません。古いPythonを直接実行して保護を迂回しないでください。

切替のチェックリスト

全consumer/worktreeがinventoryにあります。
旧writerと自動起動を停止しました。
ignored/untrackedも復元確認しました。
全対象の固定engineとprotocolが揃いました。
予定外の仕様変更とpending journalがありません。
新しいコマンドだけで運用を再開します。
09 / LEGACY MAPPING

11 / SAFETY & LIMITS

便利な暗黙操作より、対象の保護を優先します。

一Scope、一canonical branch

対応は共有registryへ保存します。未登録の既存branchを勝手にadoptせず、停止中の明示mappingで登録します。タイトル変更で別branchを生やしません。

Gitは必要なときだけ

commit、push、merge、cherry-pick、branch削除をstart/finishの隠れた効果にしません。通常のGit統合は利用者が明示します。

証跡を実行・採用しません

ArtifactとWorkbenchはuntrusted bytesです。filename、拡張子、typeから本文をcommandや正本として解釈しません。

固定sourceでも信頼は別です

pin/digestは同一性の確認です。任意の供給元を安全にする機能ではありません。固定のSpecDock供給元だけを扱います。

Artifact importはsourceを保持し、本文・hash・byte count・リポジトリ外の絶対source pathを結果に出しません。既存の有効なunknown typeのArtifactを一括改名・削除しません。backupにも機密が含まれ得るため、operator-onlyの保管とretention管理が必要です。

copy/bootstrapの任意副作用は自動rollbackできません。update/migrate/deleteのrollbackにも、後続変更を上書きしない条件があります。git reset --hardやgit clean -fdxを万能な回復として使用しません。

今回作らないものは、PR merge/pushの自動化、複数canonical branch、foreign repositoryの透過routing、双方向status同期、Scopeのkind変更/階層move、root Workbench一括copy、履歴commitの書換えです。
