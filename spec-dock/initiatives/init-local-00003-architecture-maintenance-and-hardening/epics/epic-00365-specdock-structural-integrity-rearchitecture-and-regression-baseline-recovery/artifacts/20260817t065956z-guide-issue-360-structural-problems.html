1. 最初に知ってほしい結論

レビューは前半で複数の重大欠陥を正しく発見しました。特に、更新途中の故障回復、symlinkやroot差し替えへの耐性、retry marker、uninstall境界には実在する問題がありました。

一方、終盤では既存の26件のfull-regression failureや、仕様上正しい回復動作までIssue 360のP1として扱われ、レビューが閉じにくくなりました。

整理方針: Issue 360が導入したdistribution cut-overはIssue 360で閉じます。既存runtimeの構造欠陥、26件のbaseline failure、品質ゲートの収束制御は、GitHub Issue #365と連携するEpic 00365で調査・再設計します。

実在した欠陥

最小再現とtestで確認され、実装修正が必要だった問題です。

既存の構造負債

Issue 360より前から存在し、差分回帰ではないものの解消が必要な問題です。

レビュー運用の問題

findingの再探索、偽陽性、evidence driftにより収束が遅れた問題です。

2. Issue 360で実際に見つかった問題

重要なのは、すべてを「レビュー過剰」と片付けないことです。次の問題は最小再現やtestにより確認され、修正する価値がありました。

  • Fresh initが途中で故障した場合のapply markerとforward recovery不足
  • preflight後のroot rebind、symlink、hard-link、directory walk失敗に対するmutation直前再検証不足
  • managed scaffoldのcopy、chmod、cleanupに残っていたpathname依存
  • update / uninstall retry markerのpublication、identity、cleanupのfailure atomicity不足
  • --keep-specs、--remove-specs、reinit、mode mismatch、same-bytes ownershipの境界不足
  • 物理退役したlegacy assetやtestが残り、Current contractと混在していた問題
  • full-regression ledger verifierがwrong checkoutやsetup / teardown failureを見逃し得た問題
注意: Reportに32段階の「Latest P1 repair candidate」があることは、独立したproduction defectが32件あったことを意味しません。同一の巨大な状態機械を別角度から再探索し続けた履歴も含みます。
規模観測値意味
src/spec_dock/cli.py4,945行、147 class / functionCLI orchestrationとfilesystem transactionが集中しています。
src/spec_dock/managed_distribution.py3,220行、95 class / functionadmission、ownership、plan、recoveryが密結合です。
主要test二本合計11,000行超fixtureとscenarioの理解コストが高い状態です。
Runtime package86 Python moduleruntime側は層分割されていますが、installer側との構造差があります。
