結論

SpecDock の init、init --force、update、managed distribution deprovision、explicit spec history purge を、一つの operation model、action grammar、filesystem kernel、journal protocol、typed outcome へ統合します。

安全性の中心: workspace 全体を read-only に評価し、blocker が一件でもあれば最初の write より前に operation 全体を止めます。unknown、modified、user-owned content を「managed path に見える」という理由だけで変更しません。
回復の中心: whole-operation rollback は約束しません。各 action の exact pre-action SHA-256、expected post-state、checkpoint を Operation Journal に記録し、同じ root・intent・authority・plan だけを forward recovery します。

背景：現在どこが分裂しているか

exact commit 51a0586f8eb02f622f386a1fe32f15d90fcac4bc では、すでに高度な safety mechanism と test coverage があります。ただし lifecycle の ownership が二系統です。

managed_distribution.py

  • current / historical catalog と ownership evidence
  • recognized workspace admission
  • read-only DistributionPlan
  • identity-checked apply_distribution_plan()
  • update/init-force 用 retry state

cli.py

  • fresh scaffold callback と operation orchestration
  • _UninstallAction と独自 uninstall plan/apply
  • 独自 recursive filesystem mutation
  • 別の .uninstall-retry.json
  • private rename helper の直接 import

現行 tests は unknown/modified content、symlink、hardlink、root/parent rebind、staging failure、dry-run、spec history preservation、JSON one-object output を守っています。Epic 365 はこれらを弱めず、同じ意味を一つの architecture で実現します。

        exact pre-action SHA: regular file のresume判断はjournalに保存したSHA-256を使います。「historical catalogの何番目か」やpathnameだけで元状態を推測しません。pending actionがexact pre-state、completed actionがexact post-stateに一致しなければ自動処理を止めます。
      

    


    

      
deprovisionとpurgeの境界

      

        

          
操作明示条件削除authority必ず保持するもの

          
            
dry-rununinstallなしすべて。journalも作らない

            
deprovisionuninstall --apply --keep-specsproven-owned tooling/generated/managed assetsspec history、authority外unknown content

            
purgeuninstall --apply --remove-specs上記に加え、exactly defined spec history rootauthority外unknown content、repository外

          
        

      

      
update、init、deprovision、legacy marker、retryだけではpurge authorityを取得できません。deprovision journalをpurgeとしてresumeする要求はwrite前に拒否します。
