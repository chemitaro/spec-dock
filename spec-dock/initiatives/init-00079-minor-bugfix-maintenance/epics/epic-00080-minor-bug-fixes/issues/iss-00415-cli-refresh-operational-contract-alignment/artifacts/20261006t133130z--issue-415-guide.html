01 / なぜ今取り組むのか

実際のCLIと、利用者が読む案内を揃えます

SpecDockは、要件・設計・計画などの仕様をGitHub Issueと結び付け、依存関係や作業対象を管理する道具です。CLIとは、ターミナルにコマンドを入力して操作する仕組みです。

現在のSpecDockは、プロジェクトの外にインストールしたPythonパッケージを実行します。以前の方式から構成が変わった一方で、一部の説明や補完候補に古い前提が残っています。そのため、文書の例をコピーすると失敗する、実行できないオプションが補完される、過去の移行状況を現在の状態と誤解する、といった問題が起こり得ます。

利用者にとっての成果

表示された案内に従って、現在使える操作と、安全に止まるべき場面を判断できます。

今回の変更方針

既存の入力受付やデータ保護を維持し、診断文言・実行例・説明・補完を、その契約に合わせます。

7件はすべて調査でP2に分類された修正候補です。P2という分類は「無害」や「欠陥がこれ以外にない」という保証ではありません。また、7件が同じ関数の不具合なのではなく、同じCLI刷新後の操作案内を整えるという一つの成果として扱っています。

02 / 最初に知る用語

「道具」と「プロジェクトに置くもの」を分けて考えます

用語この資料での意味
Scope仕様をまとめる単位です。Initiative（大きな目的）→ Epic（まとまりのある取り組み）→ Issue（具体的な作業）の階層があります。今回の対象はIssue #415です。
正本文書作業の基準となる文書です。requirement.mdが「何を満たすか」、design.mdが「どう実現するか」、plan.mdが「どの順序で確かめるか」を定めます。
provider／consumerproviderはSpecDockを開発・配布する側、consumerはそれを導入したプロジェクトです。このリポジトリは両方の役割を持ちます。
静的資産導入先へ配置する文書、テンプレート、操作スキル、薄いshimです。CLIの実行コード本体とは別です。shimは外部CLIへ処理を渡す短い入口です。
worktree同じGitリポジトリから作る別の作業ディレクトリです。別のworktreeを更新しても、このworktreeが更新済みになるわけではありません。
直接対象／Sync直接対象は、そのworktreeが取り組む一つのScopeです。Startが取得します。Syncは現在の状態を観測する操作で、古い一覧ファイルの再生成ではありません。
inventory／hashinventoryは配布資産の一覧です。hashはファイル内容から計算する照合値で、既知の内容か、利用者が変更した未知の内容かを区別する材料になります。

03 / 何をどう直すのか

7件を、利用者が困る場面から見ます

ここで示す「修正後」は目標です。現在の製品に反映済みという意味ではありません。

SD-OPS-001

古いmetadataの復旧案内を安全にします

今の困りごと

metadataはScopeの番号や親子関係などを記録した管理情報です。旧名のmeta.jsonを見つけたとき、現在の診断は一律に.meta.jsonへ名前を変えるよう促します。すでに.meta.jsonがある場合、利用者が手作業で上書きしてしまうおそれがあります。

修正後の姿

まずファイルを保全し、同じ場所に.meta.jsonがあるか確認します。両方ある場合は内容を比較し、正本と復旧方法を人が判断する案内へ変えます。名前を変えるだけで内容や形式が移行されるとは説明しません。

重要なのは、CLI自身が上書きする不具合ではないことです。CLIが処理を止める挙動は維持し、案内する文章を直します。

確かめること：公開create/import経路で旧・新ファイルを同居させ、失敗することと、ファイル・Git・GitHubに変更がないことを確かめます。

SD-OPS-002

READMEの作成例をそのまま使える形にします

今の困りごと

JSON形式で結果を返す--json付きの作成例に、非対話での確認に必要な--yesがありません。例を実行すると確認不足で止まります。

修正後の姿

Initiative・Epic・Issueの3つの作成例に--yesを加えます。実際の親番号には、直前の作成結果で返されたIDを使います。

--jsonは出力形式、--yesはCLIの確認省略です。どちらも作成権限や安全検査を置き換えません。

確かめること：掲載された実例を模擬GitHub環境で実行します。--yesを外した対照例は、従来どおり変更前に止まることを確認します。

SD-OPS-003

通常の対象指定とGitHub取込の指定を区別します

今の困りごと

通常のTARGETにも裸のIssue番号やURLが使えるように読める説明があります。また、GitHubから取り込む裸番号の例にはリポジトリ指定が足りません。

修正後の姿

通常操作は完全なScope ID、gh:OWNER/REPO#NUMBER、許可された動的指定を案内します。GitHub取込は別の文法として、裸番号なら--github-repoを明示します。

誤った説明を成立させるために、parser（入力を解釈する処理）の受付範囲を広げません。

確かめること：通常TARGETへのURL・裸番号は拒否し、取込の完全ref・URL・番号とrepoの組合せは条件どおり受け付けることを確認します。

SD-OPS-004

Syncを「現在の観測」として説明します

今の困りごと

古い文書にはcache指定、一覧の再生成、journal（途中操作の記録）を使う旧方式の説明が残っています。

修正後の姿

local観測と、明示的なGitHub観測を分けて説明します。観測できない状態は不明のまま扱います。古い保存物の再構築や操作再開は約束しません。

古い入力を拒否する診断は残します。旧機能を復活させる修正ではありません。

確かめること：Sync前後で直接対象や旧保存物が変わらず、GitHub観測に失敗した場合も不明・不完全を正確に返すことを確認します。

SD-OPS-005

AGENTSの現行規則と過去の移行記録を分けます

今の困りごと

agentへの入口文書に、2026-10-03時点の「0805だけ適用・merge待ち」が現在の状態のように残っています。

修正後の姿

現在の外部CLI利用規則と、日時付きの過去記録への参照を分けます。PR #414は2026-10-04にmerge済みですが、各環境への適用は別に確認します。

当時の試験結果・移行記録・Issue 413の資料は、歴史的な証拠として書き換えずに残します。

確かめること：現在の案内がmerge待ちを断定せず、他worktreeの移行完了も推測しないことと、履歴原本が不変であることを確認します。

SD-OPS-006

shell補完に実行可能な候補を出します

今の困りごと

入力を補助するBash・Zsh・Fishの補完が、読取り操作に--yes、Start以外に--lock-timeoutを提示します。これらは実行すると拒否されます。

修正後の姿

既存のleaf（最終コマンド）分類に沿って候補を絞ります。読取り操作では--yesと-yを除外し、--lock-timeoutはwork startだけに出します。

受付条件そのものや、オプションを前後に置ける性質、値を読み飛ばす処理は維持します。

確かめること：全44 leafの候補と、三つの実shellでの代表入力を確認します。禁止候補が消えるだけでなく、必要な正候補が残ることも確かめます。

SD-OPS-007

GitHub Aboutを現在の製品説明へ合わせます

今の困りごと

GitHubの紹介欄に、uvxでコピーするだけ、.spec-dock/、runtime不要という旧説明が残っています。

修正後の姿

外部インストール型Python CLIであること、Linux/macOSとPython 3.10+、指定プロジェクトへ文書・スキル等を配置することを説明します。

変更するのはdescriptionだけです。READMEのcommitだけでは紹介欄は変わりません。homepageやtopicsなどは対象外です。

確かめること：後続の許可された設定操作後、別のGETで実際のdescriptionを読み直します。未実施や結果不明なら完了にはしません。

入力例を比べてみます

以下は文法の説明例です。実行には実在する対象と、その操作の依頼・承認が必要です。番号やリポジトリをそのまま実環境へ流用しないでください。

# 通常のScope参照：完全なScope IDを使います
spec-dock scope show iss-00415

# GitHubからの取込：裸番号ではリポジトリを明示します
spec-dock scope import github epic 124 --github-repo OWNER/REPO   --parent init-00123 --title "Authentication"

# 承認された非対話の新規作成：出力形式と確認を別々に指定します

04 / 止まるときの振る舞い

失敗を隠さず、元のデータを守ります

このIssueで最も誤解しやすいのは、旧metadataへの対応です。「自動で修復する機能」を追加する計画ではありません。処理を止める現在の検査を維持し、その後に人が取るべき行動を分かりやすくします。

起きたことその場で行うことしてはいけないこと
静的資産が未知の内容に変わっています利用者の変更を保全し、手動で統合する必要があるか判断します。そのhashを既知扱いに登録して、強引に更新を通しません。
静的更新が途中で失敗しました適用済み・不明・未実行の範囲とbackupを保存し、現物を読み直します。全削除や、無条件の再実行で辻褄を合わせません。
About更新の応答が返りません実際の現在値をGETで確認します。成功とも未送信とも断定せず、自動で同じ変更を再送しません。
試験に必要なshellがありませんそのshellの実動作は未検証と記録します。文字列検査だけで三shellの成功とはしません。

05 / 修正を利用者へ届ける

ソースを直した後にも、三つの確認があります

開発側のファイルを直しただけでは、利用者が起動するCLIも、導入済みプロジェクトの文書も更新されません。新しい配布物を作り、別の場所へ導入して検証し、その後に許可された実環境へ適用します。

なぜhashの更新が必要なのでしょうか

installer（導入・更新処理）は、配布するファイルとinventoryに記録された内容が合っているか確認します。本文だけ変更してhashを更新しないと、配布物の不整合として停止します。

今回は配布用のCLI参照文書を変更する予定です。新しい内容のhashをcurrentとして記録し、直前のcurrent hashを既知旧版として保持します。これにより、正規の旧文書を安全に更新できます。利用者独自の内容を勝手に既知旧版へ追加することはしません。

実環境への適用前に見るもの

  1. CLIの実体・版・導入元と、更新するtool環境を確認します。
  2. 更新するworktreeを絶対パスで一つに固定します。
  3. dry-runで、何が変更・退役されるか確認します。本Issue外の削除や更新が含まれる場合は止めます。
  4. 安全な外部backup先と復元条件を確保してから適用します。
  5. 更新後の内容を読み直し、metadata・仕様・成果物・直接対象などが保たれていることを確認します。

戻すときも、ソース、外部CLI、静的資産、Aboutを別々に扱います。ソースを戻しただけで、すべての環境が元に戻るわけではありません。

06 / どの順序で進めるか

小さな修正を統合し、配布を確かめてから適用します

計画の慎重さを示すPlanning Levelはstrictです。公開される診断や補完、backupを伴う資産更新、GitHub上の設定という複数の変更面があるためです。これは文書の完成基準であり、操作許可や「レビュー合格」を意味する状態ではありません。

段階担当者が確かめる内容
S-01 基準確認対象branch・完全なcommit SHA・既存変更・仕様を確認し、通常テストの基準結果を記録します。
S-02〜04 修正診断と補完では、欠陥を捉えるテストがまず失敗することを確認し、最小修正後に同じテストを通します。文書例も公開CLI経路で確認します。
S-05 配布確認inventoryを揃え、新しいwheelを外部の非editable環境へ導入します。開発ソースへの参照に頼らず、新規consumerで内容と動作を確かめます。
S-06 全体確認make lint、uv run pytest、差分確認を行い、必要なLinux/macOS・Python 3.10・三shellの検証を記録します。
S-07〜08 実適用対象・backup・採用文言などの入力を確定し、許可範囲でCLI、静的文書、Aboutを個別に更新して読み直します。
S-09 引渡し全受入条件に実証拠を対応付け、未達、復元方法、残る担当を明示します。人間によるmergeは別の責務です。

07 / 何をもって完了とするか

「文書ができた」と「製品が直った」を分けます

RQは満たすべき要件、ACは受け入れ条件です。今回の正本文書には9組あります。最初の7組は各修正、残る2組は配布と品質を横断して確認する条件です。

対応するRQ / AC完了を示す証拠
001 復旧診断旧・新metadata同居でも変更前に止まり、安全な案内を返します。
002 作成例READMEの実例が模擬GitHub環境で成立し、yesなしは変更せず失敗します。
003 対象指定通常指定と取込指定の正例・負例が、文書とCLIで一致します。
004 Sync文書が観測契約に一致し、不明状態と保存物の不変が守られます。
005 現在と履歴現行入口の時点が明確で、履歴の原文は変わっていません。
006 補完全44 leafと三shellで、必要な候補と禁止する候補が一致します。
007 About対象repositoryの実際のdescriptionを、更新後の独立GETで確認します。
008 配布provider、wheel、導入済みresource、新規consumerが一致し、旧版更新と未知改変時の停止も確認します。
009 品質と記録現在候補の通常検証が通り、未実施・skip・別環境の結果を混ぜずに記録しています。

今確認できていること

仕様作成では、同じChatGPT会話を継続し、指定branchのSHA一致を確認した回答から完全版ZIPを取得しました。ZIP内の3通常ファイル、UTF-8、安全なentry構造、採用先とのSHA-256一致を検査済みです。参照74件とsource/test path 18件を照合し、workspace validateは241 Scopeで問題なしでした。

これは文書の取得・採用の証拠です。今回の製品修正のテスト成功、実環境更新、独立した仕様レビュー合格ではありません。過去の「3 passed」という限定結果も、今回の全件試験成功へ読み替えません。

失敗や未実施は、そのまま引き継ぎます

試験で使うGitHubは原則としてstub（応答を模擬する仕組み）です。実Issueを作成・Closeして試験しません。一方、Aboutの完了確認には実repositoryの読取結果が必要です。Aboutが保留なら、コード試験の成功は記録できても、7件すべてが完了したとはしません。

08 / いま決まっていないこと

実施のための入力と、将来の設計判断を分けます

後続実施の前に確定すること

  • 実装する候補SHAと配布wheel
  • 更新するtool環境と対象worktreeの絶対パス
  • 外部backup先、必要な検証環境
  • Aboutの説明文、実施主体、適用範囲

対象が決まっていない操作を、推測で別の環境へ適用しません。

今回の7件とは別の将来判断

  • rootの./specを廃止するか
  • 配布する薄いshimを廃止するか
  • 共通スキルをglobalへ置く方式を採用するか
  • 同名スキルの扱いや無関係な旧コードの整理

現在のproject-localスキルと現役rulesリンクは維持します。これらの判断を今回の開始・完了条件へ追加しません。

Aboutに載せる説明の候補

GitHub Issueに紐づく仕様・依存・成果物とworktreeごとの作業対象を管理する外部インストール型Python CLI。Linux/macOS・Python 3.10+に対応し、指定projectへ文書・template・project-local skill・薄いshimを静的配置します。

この文章は設計にある候補です。GitHubへ設定済みという意味ではありません。

仕様を確認する方への確認ポイント

  • 7件を「利用者向け操作契約の整合」という範囲にまとめる意図が伝わるか。
  • 危険なrename案内の改善と、CLIの自動修復機能を混同していないか。
  • 文書・CLI・導入先・Aboutの完了が、別々に判断できるか。
  • 互換入口廃止やglobal移行を、今回の必須作業に混ぜていないか。
