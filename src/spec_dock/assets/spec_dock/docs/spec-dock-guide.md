# spec-dock guide（共通原則 / 承認ゲート）

このドキュメントは、`spec-dock/initiatives/` の仕様ツリー（Initiative → Epic → Issue）を  
人間とコーディングエージェント（Codex CLI）が **同じ前提**で運用するための「共通原則」と「承認ゲート（チェックリスト）」の正です。

詳細手順（ワークフロー）は用途別に分割しています:
- ツリー運用: `workflow-tree.md`
- Issue実装: `workflow-issue.md`
- ADR運用: `workflow-adr.md`

補助:
- GitHub連携（`gh`）: `github.md`
- 状態集計（`sync`）: `sync.md`
- 旧版（参考）: `spec-dock-guide-old.md`

## コア原則（全レイヤー共通）

### 1) 99.9%理解ルール（絶対厳守）
常に「99.9%以上理解できている／99.9%以上の確信が持てている」状態になるまで、次に進みません。  
理解が不足している場合は、まず自力で調査し、なお不明な点だけを短く整理してユーザー/レビュアーに確認します。

### 2) 推測で埋めない（空欄を埋めるための発明をしない）
- 不明点は `TBD` に残す（質問/選択肢/推奨案/影響範囲の形）
- 「該当なし」の場合も、`省略/例外メモ` に理由を書いて矛盾を残さない

### 3) レイヤー間の DRY（重複禁止）
- Initiative にコード詳細を書かない（Outcome/指標/制約の固定）
- Epic に関数シグネチャやSQLなどの詳細を書かない（背骨: 契約/移行/観測性/品質ゲート）
- Issue に KPI の再掲を長文で書かない（親へリンクする）

### 4) `状態: draft | approved` は「承認」だけに使う
- `approved` は **ユーザー/レビュアーの明示的承認**を意味する（進捗ではない）
- 重要な変更を入れたら、再承認が必要（原則 `draft` に戻して合意を取り直す）

### 5) 正（source of truth）の置き場所を固定する
原則として各ノード（Initiative/Epic/Issue）で:
- `requirement.md`: WHAT/WHY（成功条件/受入条件/境界）
- `design.md`: HOW の正（固定する契約、背骨、詳細設計、テストの担保方法）
- `plan.md`: 実行順序の正（分解・順序・品質ゲート・ステップ）
- `report.md`: 実行した事実の正（コマンド/結果/変更ファイル/判断の経緯）

### 6) 意思決定は ADR に分離する
- ADR は「議題が上がった時点」で叩き台を起こす（Decision は未決/TBDで開始）
- 最終決定は人間が下し、確定後に Decision を更新して `accepted` にする
- 意思決定が必要なヒアリングを行う場合は、先に「結論未決の ADR」を作り、質問/選択肢/推奨案/影響範囲を整理してから質問する（回答後に ADR を穴埋めして accepted、仕様へフィードバック）

### 7) 図（UML）は “必要ならここに置ける” を優先する
- 図は任意（形式を固定しない）
- 必要な箇所の直下に `### UML（任意）` を追加して差し込む（テンプレはその前提）
- 図/スクリーンショット/ログ断片は Issue の `artifacts/` へ置いてよい

## ディレクトリと成果物（何が正で、何が生成物か）

- `spec-dock/initiatives/`（Git管理する）
  - 仕様ツリー本体（Initiative/Epic/Issue/ADR が常置）
- `spec-dock/active/`（生成物 / gitignore）
  - 現在作業中の initiative/epic/issue への固定入口（symlink または `.path`）
  - `context-pack.md`（エージェントの入口）
- `spec-dock/.agent/`（生成物 / gitignore）
  - `active.json`（SSOT）
  - `index.json` / `tree.json`（`sync` の出力）

## レイヤー別の最小品質ゲート（チェックリスト）

> ここは「承認依頼前に落とすべき最低限」です。  
> テンプレ内の `Definition of Ready` / `Definition of Done` も併用してください。

### Initiative
**Initiative `requirement.md`（承認依頼前）**
- [ ] Outcome（Primary/Secondary）が明記されている
- [ ] 成功指標が Baseline/Target/計測方法/計測期間まで定義されている
- [ ] スコープ境界（MUST/MUST NOT/OUT OF SCOPE）と（Always/Ask/Never）がある
- [ ] 制約/前提、リスク/依存が書けている
- [ ] `TBD` が「質問/選択肢/推奨案/影響範囲」の形
- [ ] `省略/例外メモ` が `該当なし` または理由つき

**Initiative `design.md`（承認依頼前）**
- [ ] ガードレール（互換性/セキュリティ/観測性/品質ゲート）が明文化されている
- [ ] 移行/ロールアウト方針（原則）がある
- [ ] ADR index があり、意思決定は本文に散らしていない
- [ ] `TBD` と `省略/例外メモ` が整っている

**Initiative `plan.md`（承認依頼前）**
- [ ] マイルストーンと Epic 分解（狙い/依存/順序）がある
- [ ] 計測計画とロールアウト計画がある
- [ ] ブロッカー/依存が列挙されている
- [ ] `TBD` と `省略/例外メモ` が整っている

### Epic
**Epic `requirement.md`（承認依頼前）**
- [ ] Initiative のどの Goal/Metric に効くかが明記されている
- [ ] E-RQ と E-AC があり、E2Eとして観測可能な形になっている
- [ ] NFR とスコープ境界（MUST/MUST NOT/OUT OF SCOPE + Always/Ask/Never）がある
- [ ] 依存/影響範囲が書けている
- [ ] `TBD` と `省略/例外メモ` が整っている

**Epic `design.md`（承認依頼前）**
- [ ] 契約（API/イベント/データ境界）、データモデル、移行戦略の背骨がある
- [ ] 失敗設計、観測性、セキュリティ/監査の要件がある
- [ ] テスト戦略があり、E-AC と対応づいている
- [ ] ADR index がある
- [ ] `TBD` と `省略/例外メモ` が整っている

**Epic `plan.md`（承認依頼前）**
- [ ] Issue 分割（縦切り方針）と、順序付き一覧（目的/成果物/依存/対応E-RQ/E-AC）がある
- [ ] 品質ゲートとロールアウト/移行方針がある
- [ ] Issue の DoR（着手可能条件）が明文化されている
- [ ] `TBD` と `省略/例外メモ` が整っている

### Issue
**Issue `requirement.md`（承認依頼前）**
- [ ] 目的（To-Be）が1〜3行で明確
- [ ] As-Is が「再現手順/観測点/実観測結果/根拠」で書かれている
- [ ] スコープ境界（MUST/MUST NOT/OUT OF SCOPE + Always/Ask/Never）がある
- [ ] AC/EC が観測可能（テスト可能）で、必要な観測点が書けている
- [ ] `TBD` が「質問/選択肢/推奨案/影響範囲」の形
- [ ] 用語（ドメイン語彙）がある
- [ ] `省略/例外メモ` が整っている

**Issue `design.md`（承認依頼前）**
- [ ] `design.md` を正として、固定する IF 契約 / 変更計画 / マッピングが集約されている
- [ ] 既存実装/規約の調査（99.9%理解）があり、採用/不採用パターンが書けている
- [ ] 要件→設計→テスト（AC/EC→テスト）の対応がある
- [ ] 非交渉制約の検証方法（テスト/計測/運用確認）がある（該当なしは理由がある）
- [ ] `TBD` と `省略/例外メモ` が整っている

**Issue `plan.md`（承認依頼前）**
- [ ] 対象 AC/EC/制約が明記され、要件↔ステップ対応表でカバーされている
- [ ] 各ステップが「1ステップ=1つの観測可能な振る舞い」になっている
- [ ] 各ステップに Given/When/Then（または入力→出力）がある
- [ ] 各ステップに `update_plan` / `report.md` 記録 / ステップ末尾チェックが残っている
- [ ] `TBD` と `省略/例外メモ` が整っている

**Issue `report.md`（セッション記録の最低限）**
- [ ] 開始/終了時刻がある
- [ ] 対象ステップ（Sxx）と AC/EC がある
- [ ] 実行コマンドと結果（失敗も含む）がある
- [ ] 変更ファイルが列挙されている

### ADR
**ADR（叩き台 → 決定 → accepted）**
- [ ] Context / Options / Consequences が埋まっている（Decision は未決のままでも良い）
- [ ] （意思決定ヒアリングの場合）ユーザーに投げる「質問（決めたいこと）」と選択肢/推奨案（あれば）/影響範囲が整理されている
- [ ] Decision を確定するのはユーザー/レビュアー（確定後に `accepted`）
- [ ] 仕様（requirement/design/plan/report）や PR へのリンクが貼られている

## 変更が出たときの原則（矛盾を残さない）

- 学び/仕様変更が発生したら、まず対象ノードの `requirement.md → design.md → plan.md` の順で差分を反映する
- 影響が親（Epic/Initiative）に及ぶなら、親の仕様や ADR にフィードバックし、下位だけで握りつぶさない
