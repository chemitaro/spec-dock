**推奨は、候補Bを中核、候補Cを実行機構として採用し、候補Dを「同一parent directory・非破壊fresh create」に限定して段階導入する `descriptor-bound incremental transaction` です。候補A単独、全action横断cache、journalの無条件batch化は採用しません。**

対象branch `iss-00369-fresh-distribution-provisioning` のfull tipは、指定された `6f0ea0d535cfb86a522851a4ce4f87bb16c509c9` と完全一致しています。以下はこのcommitを固定して確認した結果です。

# 1. 最終判断

採用構成は次の三層です。

1. **候補B: immutable authority graph + incremental revalidation**

   * preflight snapshotを「省略可能なcache」ではなく、変更権限を定義するimmutable authorityとして保持する。
   * actionごとに全pending targetを再観測せず、そのactionのroot・ancestor・parent closed set・target・stage・sourceだけを再検証する。
   * operation自身が行った変更だけを、exact postcondition付きstate transitionとしてgraphへ反映する。

2. **候補C: phase-scoped directory capability**

   * rootとmutation parentを`O_DIRECTORY | O_NOFOLLOW`で開き、`dir_fd`相対の`stat/open/rename/link/unlink/mkdir`を使用する。
   * FDを保持していても、それだけではrenameされた孤立directoryを誤って変更し得るため、**各namespace mutation直前にvisible pathとheld FDのbindingを再検証する**。
   * Linux固有の`openat2`には依存せず、現行が既に前提としているLinux/macOSの`dir_fd`、`renameat2` / `renameatx_np`境界を維持する。

3. **候補D: dependency-derived namespace transaction group**

   * action数による任意chunkではなく、同一held parent directory、同一action class、同一journal authorityを持つactionだけをgroup化する。
   * fresh createでは、group単位でstage-name reservation、stage materialization、exact lease確定、canonical publish、checkpointを行う。
   * `upgrade`、`prune`、predecessor quarantine、backup、GC transitionは当初batch対象外とし、既存の即時write-ahead transitionを維持する。

この順序にする理由は、現状の約34秒中、まずO(A²)再観測と全created-parent再走査を除かなければ、journalだけを変更しても安全性リスクに見合う成果が得られないためです。逆にB/Cだけでは、提示された`OperationJournalStore` write累積約8.675秒が下限として残る可能性が高く、最終的な5〜8秒目標にはDも必要です。

`apply_distribution_plan()`は、開始時に全actionを再観測した後、各actionについてmutation前に残り全actionを再観測し、mutation後にも残り全actionを再観測します。これは明示的な二重の三角ループです。

`_open_distribution_parent_chain()`もrootから各componentを開き直し、各段でsnapshot照合とvisible-path対held-FD照合を行います。安全上必要な照合自体ではなく、**同じchainを一つのtransaction内で数万回開き直していること**が問題です。

journal側では、`record_staging_lease()`、`record_created_parent_bindings()`、`mark_verified()`、`mark_completed()`などがすべて`OperationJournalStore.write()`へ進みます。`_write()`はfull journalをserializeし、guard anchorを書き換え、O_EXCL stageへwrite/fsyncし、atomic rename/swap、parent fsync、held/visible identity照合まで行います。これは正しいdurability protocolですが、action transitionごとにfull payloadを書き直す構造です。

`checkpoint_published()`も、persisted journalのread、cleanup resume、parent-chain open、lease更新、successor identity更新、checkpoint更新、backup GC、最終lease除去を行い、途中で複数回journalをpublishし得ます。

## 2.3 反復回数から導ける推論

action数を`A = 213`とすると、後続actionの三角走査は一回につき、

[
\frac{A(A-1)}{2}
= \frac{213 \times 212}{2}
= 22,578
]

です。

mutation前後に同じ走査があるため、

[
2 \times 22,578 = 45,156
]

となります。

実測の`_observe_target = 46,860`との差は、

[
46,860 - 45,156 = 1,704 = 8 \times 213
]

です。

したがって実測値は、**二つの三角走査45,156回に、preflight、current-action refresh、assessment/post-assessment等の約8回分の全action相当走査が加わった値**と算術的に整合します。

ただし、「追加8回」の内訳を完全に確定するにはcall-site counterが必要です。trusted manifest参照やrecovery branchによる追加観測を含み得るため、現時点では内訳を断定しません。

## 2.4 現在の計算量

記号を次のように置きます。

* `A`: action数
* `D`: 最大path depth
* `B`: created-parent binding数
* `E_b`: binding `b`直下のentry数
* `V`: mutation-boundary callback回数
* `W`: durable journal publication回数
* `J`: journal payload size

現在の主要コストは概ね次です。

* pending target再観測: **Θ(A² × D)**
* parent-chain reopen: **Θ(V × D)**
* created-parent closed set:
  **Θ(V × (A + B × D + ΣE_b))**
* journal durability:
  **Θ(W × J)**に加え、各writeのguard更新、stage write、複数fsync、atomic swap

Issue 368/369の安全契約そのものではなく、それを「全体走査としてactionごとに何度も再実行する」構造が根因です。Issue 368はexact identity、write-ahead lease、forward-only recoveryを要求し、Issue 369はfresh provisioningを同じjournaled kernelへ統合しています。これらは維持対象であり、削除対象ではありません。

# 4. 推奨設計

## 4.1 Invariant

### I1. Authority monotonicity

preflightの`DistributionTargetSnapshot`とjournal preconditionは変更権限の起点です。

runtime observationが異なっていた場合にsnapshotを最新値へ置換してはなりません。stateを更新できるのは、次の全条件が成立したoperation-owned mutationだけです。

* mutation直前のpreconditionが一致
* mutation syscallがheld parent FD相対
* mutation後のexact identityが確認済み
* parent fsync済み
* 必要なjournal authorityがmutation前にdurable
* transitionがjournal/state machineで許可されている

### I2. Visible-to-held binding

各namespace mutation直前に、rootからmutation parentまで次を確認します。

* `fstat(held_fd)`のdevice/inode/type
* 親FDから`stat(child_name, follow_symlinks=False)`したvisible node
* child held FDの`fstat`
* visible nodeとheld FDが同一device/inode/type
* root pathnameの`lstat`とheld root FDの一致

held FDが有効でも、visible pathから切り離されたdirectoryへのmutationは禁止します。

### I3. Local closed set

created parentについて、mutation対象のancestor chain上だけを直前に走査します。

* 現在のentry name集合が、journal action、created binding、stage、quarantine、backup、GC transitionから事前構築したallowed setに含まれる
* 各既知entryのidentityが該当conditionまたはleaseと一致する
* unknown childが一件でもあればfail closed

phase start/end、resume、final verificationでは全created-parent bindingを完全走査します。

### I4. Exact leaf identity

* regular target/stage: device、inode、`ctime_ns`、type、`nlink`、digest、mode
* symlink: no-follow structural identity、`nlink`、normalized link target
* directory: device、inode、type、visible binding、closed set
* 通常target/stageは`nlink == 1`
* `nlink == 2`を許すのは、既存journal role graphで明示されたbackup/GC transitionのみ

### I5. Durable-before-visible

canonical targetを変更する前に、少なくとも次がdurableでなければなりません。

* operation/plan/root/contractをbindしたguard+journal
* private stage nameのreservation
* canonical publishをrecoveryできるexact stage leaseまたは既存protocolが許す同等のauthority
* destructive transitionではpredecessor quarantine/backup authority

### I6. Source binding

provider sourceはtransaction-localにcaptureできますが、global cacheにはしません。

publish前に次を再確認します。

* source parent chainのvisible/held binding
* visible leafとheld source FDのdevice/inode/ctime/type一致
* read前後のsource snapshot一致
* captured bytesのSHA-256とplan identity一致
* mode一致

source pathが同じbytesの別inodeへ置換されても失敗させます。

### I7. Failure invalidation

次のいずれかが起きたsessionは`INVALID`とし、in-processでsnapshotを取り直して継続しません。

* visibility mismatch
* unknown child
* unexpected `nlink`
* syscall permission/error
* partial publishでcanonical/stageの役割が一意に証明できない
* journal write/anchor mismatch
* source mismatch
* unclassified exception

以後は既存のforward recovery entrypointからjournalとfilesystemを再構築します。

### I8. External compatibility

次は変更しません。

* `DistributionApplyError`等の既存failure message/code
* `DistributionProcessResult`
* CLI success/blocked/recovery mapping
* retry command
* journal schema/protocol version
* guard/journal pathname
* source manifest/contract digest
* full-regression ledger semantics

## 4.2 Proposed in-memory state model

以下は**新設候補のprivate symbol**であり、現commitに存在するとは主張しません。

```python
_DistributionMutationSession
_DirectoryCapability
_TargetCapability
_SourceCapability
_OperationJournalIndex
_CreatedParentClosedSetIndex
_MutationImpact
_DistributionPhase
_NamespaceTransactionGroup
```

### `_DirectoryCapability`

保持する情報:

* `relative_path`
* `fd`
* `parent_relative_path`
* `basename`
* original `PathIdentitySnapshot`
* current operation-owned structural identity
* `created_by_operation`
* `state`: `BOUND | DIRTY | INVALID | CLOSED`
* dependent action paths
* precompiled closed-set rule

FDはjournalへserializeしません。resume時は必ず再構築します。

### `_TargetCapability`

保持する情報:

* `path`
* `action`
* parent capability key
* original precondition
* expected postcondition
* expected source capability key
* current operation-owned exact successor identity
* `state`:

  * `PLANNED_PRE`
  * `STAGE_RESERVED`
  * `STAGE_EXACT`
  * `PUBLISHED`
  * `VERIFIED`
  * `FAILED`

### `_OperationJournalIndex`

一度だけ構築し、journal replacement後に差分更新します。

* `actions_by_path`
* `bindings_by_path`
* `leases_by_path`
* `leases_by_parent_and_name`
* `originally_missing_paths`
* `allowed_created_parent_children`
* `pending/published/verified paths`

これにより、現在各callbackで行っている全journal actionの再走査を除きます。journal wire dataは変更しません。

### `_MutationImpact`

一つのmutation後に更新する対象を明示します。

* changed canonical path
* changed private names
* changed parent directories
* newly bound created directory
* exact successor/predecessor identity
* journal transitions required before/after mutation
* invalidated phase/global checks

## 4.3 Algorithm

## Phase 0: recovery admission

1. existing guard/journalを現行`OperationJournalStore`で読み、digest、root、workspace、intent、authority、planを検証する。
2. GC graph、stage lease、created bindingを現行意味論で再検証する。
3. incomplete transitionを既存recoveryで完了する。
4. recovery後に新しいmutation sessionを構築する。

recovery途中のFDやin-memory graphを再利用しません。

## Phase 1: full baseline validation

1. 全action、target、required directory、sourceを一度観測する。
2. rootとunique existing directoryをphase-scoped FDとして開く。
3. immutable precondition graphを構築する。
4. journal indexとcreated-parent closed-set indexを構築する。
5. 全visible/held bindingを一度確認する。
6. 全created parentをclosed-set検証する。

これはO(A×D)であり、actionごとの全体再走査ではありません。

## Phase 2: `ensure-directory`

top-down dependency順に処理します。

各mkdir直前:

1. root/ancestor visible binding
2. current created ancestorsのclosed set
3. exact target missing
4. journal上のmissing binding authority
5. parent FD相対`mkdir`
6. parent fsync
7. exact created directory binding capture
8. durable binding publication

created directory bindingは、descendant publish前にdurableでなければなりません。初期段階ではdirectory bindingを無条件batch化しません。

## Phase 3: fresh stage materialization

`_NamespaceTransactionGroup`は、少なくとも次が同じactionだけを含みます。

* same held parent directory
* fresh `create`
* non-destructive
* same regular/symlink stage protocol
* ancestor directory dependencies完了済み

group処理:

1. group start full/local validation
2. 全stage nameを一回のjournal updateでreservation
3. 各stageをO_EXCL、no-followで作成
4. source bytes write、file fsync、mode/digest確認
5. stage FDとvisible stage nameのbinding確認
6. group内stageのexact leaseを一回のjournal updateで確定
7. ここまではcanonical targetを変更しない

stage exact leaseのbatch化は、zero-reservation crash matrixが既存recovery意味論でfail closedになることを確認してから導入します。確認できなければ、exact leaseだけはstage単位で即時publishし、それ以外のreservation/checkpoint batchだけを採用します。

## Phase 4: canonical publish

各actionについて個別に行います。

1. root/ancestor visible binding
2. current action chainのcreated-parent closed set
3. exact target precondition
4. exact stage leaseとheld stage FD
5. source bindingの最終確認
6. no-replace renameまたはatomic swap
7. parent fsync
8. exact canonical successor確認
9. `_MutationImpact`をoperation-owned evidenceだけで反映

**group化してもnamespace mutation直前の検証は省略しません。**

## Phase 5: destructive cleanup

`upgrade`、`prune`、quarantine、backup、GCは当初current implementationを維持します。

* reservation
* exact transition lease
* canonical successor/absence validation
* hardlink backup
* parent fsync
* journal transition

これらは一つのinodeが複数private name間を移動するため、fresh createと同じbatch規則を適用しません。

## Phase 6: phase reconciliation/checkpoint

groupまたはphase終了時に:

1. 全completed actionのcanonical exact identityを検証
2. pending actionに変更がないことをphase-wideに検証
3. created-parent full closed set
4. exact stage/predecessor lease cleanup
5. `checkpoint_published()`をcompleted path集合で一回呼ぶ
6. journal stateを次phaseへ進める

現在の`checkpoint_published()`は複数`completed_paths`を受け取れるため、wire変更なしでgroup checkpointへ寄せられます。

## Phase 7: final verification

1. 全targetを一回再観測
2. 全actionが`adopt/preserve`相当のpost-state
3. 全created parent closed set
4. stage/backup/GC leaseなし
5. source contract/manifest identity一致
6. `mark_verified`
7. `mark_completed`
8. guard removal
9. journal removal

各finalizationの間でもroot/workspace/guard/journal identityを現行どおり検証します。

# 5. 完全検証・局所検証・invalidate

## 5.1 完全検証を行う時点

* executable authorityを発行する直前
* mutation session構築時
* journal resume直後
* 各phase開始時
* 各phase終了時
* ambiguous exception後の新規recovery attempt
* `mark_verified()`直前
* `mark_completed()`直前
* guard removal直前
* journal removal直前

通常fresh initでの全plan validation回数は、recoveryなしなら**10〜20回以下**にします。

## 5.2 局所検証を行う時点

次の各syscall直前です。

* `mkdir`
* regular stage `open(O_CREAT|O_EXCL)`
* `write`の最初と継続write
* `fchmod`
* `symlink`
* `rename no-replace`
* `rename exchange`
* `link`
* `unlink`
* quarantine rename
* backup/GC rename
* journal/guard canonical swap

検証範囲:

* root
* current actionのancestor chain
* current mutation parent closed set
* exact target
* exact stage/predecessor
* 必要なsource
* journal authority

## 5.3 Snapshot/capabilityをinvalidateするevent

* root pathnameのreplacement/rebind
* ancestor directoryのreplacement
* directory renameでvisible pathとheld FDが不一致
* symlink化またはfile type変更
* unknown childの出現
* exact targetのdevice/inode/ctime/type/nlink変化
* hardlink増加
* target/stageのpermission/mode mismatch
* provider sourceのvisible replacement
* source bytes、mode、snapshot変化
* mkdir/create/symlink/link/unlink/rename/swap
* stage、quarantine、backup、GC transition
* journal/guard publication
* created-parent binding追加
* journal object replacement
* phase遷移
* permission error、`ESTALE`、unexpected `ENOENT/EEXIST`
* partial journal/stage write
* callback/recorder例外

operation自身の正常mutationでは、関係するcapabilityを`DIRTY`にしてexact postcheck後にのみ`BOUND`へ戻します。無関係なcapabilityを再観測値で更新しません。

| Event                               | 検出・防御                                                                                                            | Cleanup / result                                                            |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **symlink swap**                    | parent FD相対no-follow stat/readlinkを前後で行い、structural identityとtargetを比較。createはno-replace、upgradeはatomic exchange | unknown canonical entryをstageへ移動して削除しない。証明不能なら両方保持し`recovery_required`      |
| **parent replacement**              | parent visible entryとheld child FDのdevice/inode/typeをmutation直前に比較                                               | syscall前に停止。replacementをoperation-ownedとして採用しない                             |
| **directory rename**                | held FDが生存していてもrootからのvisible chain不一致を検出                                                                        | renamed/orphan directoryへmutationしない。session invalid                        |
| **hardlink**                        | regular/symlink targetとstageは`nlink == 1`。`nlink == 2`は明示されたbackup/GC role graphだけ                               | unexpected hardlinkは保持して既存failure codeでblock/recovery                       |
| **permission change**               | modeがcontract対象ならexact mismatch。対象外でもsyscall errorを吸収せずsession invalid                                           | permissionを自動修復・authority refreshしない                                        |
| **source replacement**              | visible provider path、held source FD、snapshot、digest、modeをpublish前に照合                                            | target mutation前ならwrite 0。stage作成後ならprivate stageだけをexact ownershipでcleanup |
| **crash**                           | reservation/lease/journalをcanonical mutationより前にdurable化し、各namespace transition後にparent fsync                    | 次回entrypointでjournal+FSからsession再構築。in-memory stateへ依存しない                   |
| **partial journal write**           | 現行のO_EXCL stage、full write、file fsync、atomic swap、parent fsync、digest/guard anchorを維持                            | canonical journal以外のpartial stageをexact ownershipで除去。ambiguousなら保持          |
| **partial stage write**             | write-ahead reservation、O_EXCL、held FD、type/nlink、visible binding                                                | exact ownershipが証明できるprivate stageのみcleanup。canonical publishは禁止            |
| **concurrent mutation**             | cooperative CLI writerは既存exclusive lock。非協調writerはcurrent actionのlocal check、phase-wide checkで検出                 | 既に完了したactionはjournaled stateとして保持し、以降はforward recovery                      |
| **same bytes / different inode**    | digestだけでなくdevice/inode/ctimeを比較                                                                                 | replacementとして拒否                                                            |
| **unknown child in created parent** | current action chainのclosed-set scanをnamespace mutation直前に実施                                                     | childを削除せずfail closed                                                       |

## 7.2 Wall time

### 中間gate

B/C完了時:

* real fresh init p95: **12秒以下**
* `_observe_target`: **1,500以下**
* `posix.open`: **40,000以下**

この時点で12秒を超える場合は、journal batchへ進む前に未除去のglobal scanを再調査します。

### 最終gate

基準runnerで、warm-up 1回後の5回測定:

* median: **5.0秒以下**
* engineering target: **3.5〜4.0秒**
* 5回のmax: **8.0秒以下**
* 2回以上が8秒を超えた場合は失敗
* cProfile付きtimeはgateに使わない

約216のdirect init箇所を4 shardへ均等に分散した粗い上限では、

[
216 \times 8 / 4 = 432\text{秒}
]

です。非init test、collection、artifact処理を加えると、max 8秒は10分gateを満たすためのほぼ上限です。したがってp95を5〜6秒へ下げる必要があります。

### Full-regression

* engineering target: **480秒以下**
* hard SLO: **600秒以下**
* collectionからledger統合までのend-to-end wall time
* timeout延長による合格は禁止

現在のverifierはcollect-only後に4 shardを実行し、JUnit、log、result、node coverage、ledger signatureを統合します。

ただし現行実装の`elapsed_seconds`計測はcollection完了後に開始されているため、**10分SLOはcollectionを含むoverall deadlineとして追加する必要があります**。workflowの12分job timeoutは、600秒でverifierを失敗させた後にartifactを保存するための余裕として維持します。

# 9. Benchmark protocol

## 9.1 実行条件

* exact Git SHAを記録
* clean Python processごとに一つのfresh temp target
* provider assetは同じworking treeから読む
* warm-up 1回、measurement 5回
* target directoryは毎回新規
* OS cacheの強制dropは行わず、first runと後続runを別々に記録
* cProfileは別の1回だけ
* benchmark中にtemplate fixtureを使わない
* xdistを使わない
* production safety env flagを追加しない

## 9.2 保存artifact

* `environment.json`

  * SHA、OS、kernel、Python、uv、CPU、RAM、filesystem/mount
* `benchmark-result.json`

  * per-run wall time、median、max、action数
* `operation-counts.json`

  * function/call-site別counter
* `journal-counts.json`

  * guard/journal publications、bytes、fsync
* `profile.pstats`
* `collection.log`
* collected node list
* shard logs
* shard JUnit
* verifier `result.json`

## 9.3 Flake判定

### Init benchmark

失敗:

* median >5.0秒
* max >8.0秒
* 5回中2回以上が8.0秒超過
* counter gate超過
* safety test failure

一回だけ8秒を超えた場合:

* runner/environment evidenceを保持
* 一回だけ再計測可能
* 最初のartifactを削除しない
* merge acceptanceには再計測を含めて2系列連続passを要求

### Full-regression

次は即失敗で、手動成功扱いしません。

* total >600秒
* shard timeout
* exit 3
* missing/duplicate node
* setup/teardown error
* missing JUnit
* ledger mismatch
* signature mismatch
* unexpected failure

SLOだけの単発failureをrunner incidentとして再実行する場合も、最初のartifactを保存し、その後**2回連続pass**をmerge条件にします。

# 10. Fixture・sharding・verifierの最終判断

## Session-built real-init fixture

**維持します。**

理由:

* init実装を検査しないtestに限定されている。
* exact manifestとreal init由来templateを使っている。
* 根因を隠す全体mockではない。
* performance改善後も重複setup削減として有効。

条件:

* allowlistを性能対策として増やさない。
* init output、journal、race、failure、filesystem mutationを検査するtestには使用しない。
* provider asset inventoryが変わった場合にmanifest mismatchで再構築する。
* 3回連続GHA pass後、二つのconftest間の重複だけを共通helperへ移す。

## 4-shard verifier

**永久に維持します。**

4 shardは根本解決ではありませんが、次を保証するverification infrastructureです。

* deterministic node assignment
* full node coverage
* missing/duplicate検出
* JUnit/log/result
* ledger signature integration
* hung processのhard termination

shard数を増やしてSLOを満たす方法にはしません。

## 600秒timeout

**延長しません。**

現行のper-shard 600秒に加えて、collectionを含むoverall 600秒deadlineへ強化します。

# 11. Issue 369本体へ戻る前のexit criteria

## 必須checklist

### Safety

* [ ] symlinkをfollowするmutation pathがない
* [ ] 各namespace mutation直前にvisible/held ancestor bindingを検証

* [ ] init max ≤8秒

### Regression evidence

* [ ] ordinary `uv run pytest -q` pass

## Stop conditions

次のいずれかが成立した場合は、そのStepで停止し、後続のbatch化やrolloutへ進みません。

* safety testを弱めなければ性能目標に届かない
* snapshotをunexplained current observationで更新する必要がある
* unknown childを許可する必要がある
* exact leaseなしでcanonical successorを認定する必要がある
* journal protocol bumpが必要
* destructive upgrade/prune/GCをbatchしなければSLOに届かない
* Linux/macOS双方でvisible-to-held bindingを証明できない
* Step 8後もinit p95が12秒を超える
* Step 12後もinit maxが8秒を超える
* full-regressionが600秒を超える
* shard数、timeout、skip、approved failure追加が必要
* retained skillの正本を確定できない

SLO未達時に採ってはならない対応は、worker増加、timeout延長、fixture allowlist拡大、safety validation bypass、approved failure追加です。残存call graphを再計測して次のhot pathを特定します。

# 12. Implementation Brief

> `src/spec_dock/managed_distribution.py`の安全契約を維持したまま、fresh initのO(A²)再検証をO(P×A + A×local-chain)へ変更する。
> 中核はimmutable authority graphとphase-scoped held directory FDであり、各namespace mutation直前にvisible/held chain、created-parent closed set、exact target/stage/sourceを局所検証する。
> operation-owned exact postconditionだけをsession stateへ反映し、外部観測によるsnapshot refreshは禁止する。
> 最初にbenchmark、counter、race/journal/recovery contractを固定する。
> 次にjournal index、mutation session、capability graph、local validationを導入し、`apply_distribution_plan()`の二つのpending-action三角ループを削除する。
> regular/symlink/directory actionをheld capabilityへ移し、sourceもtransaction-local held capabilityとして扱う。
> B/C完了時のgateはinit p95 12秒、`_observe_target ≤1,500`、open ≤40,000。
> その後、同一parentのfresh createだけをnamespace transaction group化し、reservation、exact lease、checkpointを安全なgroup boundaryへ寄せる。upgrade/prune/quarantine/GCは即時journal transitionを維持する。
> 最終gateはinit median 5秒以下、max 8秒以下、`_observe_target ≤1,000`、open ≤25,000、journal publication ≤80、full-regression end-to-end 600秒以下。
> 4-shard verifierと限定template fixtureは維持し、skip、xfail、approved failure、timeout延長、worker増加を解決策にしない。
> retained skill hash mismatchは独立commitで正本を確定し、resolved failureをledgerから除去する。
