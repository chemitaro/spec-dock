# iss-00456 Flatten Specs In Canonical Migration Script — 要件定義

詳細: [Requirement Guide](../../../docs/authoring/requirement.md)

表示名：移行のスクリプトで、入れ子の仕様を区切りのある平らなカタログに写し、slug の印をやめ、戻すときは入れ子を作り直す（Epic の I-15）

## 目的

移行のスクリプト `scripts/migrate-to-canonical/migrate.py` が、R-J1 の5つのリポジトリの入れ子の仕様を、区切りのある平らなカタログ（`<区切り>/<ID>/`）に写し、仕様の中の相対のリンクを切らずに移し、slug の印を使わずに GitHub に登録でき、戻すときは GitHub の親子から入れ子を作り直せる。I-10（spec-dock の切り替え）と I-12（残りの4つの切り替え）の前提である。

- 材料：Epic の `plan.md` の「I-15 Flatten Specs In Canonical Migration Script」の節（価値、担当する設計、作るものの表、テスト、受け入れ、注意）と、Epic の `design.md` の11章（`register`、`verify`、`undo`、作った Issue の見つけ直し、平らにする写し、戻すときの入れ子と slug、予行演習）、2章の「内容の置き場」、「移行・互換性・rollback」。方針の理由は Epic の `design.md` の「設計の判断」の最後の行（2026-10-29 の利用者の決定）にある。
- 区切りの決まり（2026-10-29 の利用者の決定。統括の依頼が正本。Epic の文書は並べて進む I-16 が直す）：canonical のカタログの Scope のディレクトリは `spec-dock/initiatives/<区切り>/<ID>/` に置く。区切りは番号を1,000で割った範囲で、名前は `<下端>-<上端>`。下端と上端の桁は ID の番号と同じ幅（5桁未満は0で埋める）。Epic の `plan.md` の I-15 の節の写し先 `<ID>/` は、この決まりにより `<区切り>/<ID>/` と読む。
- 依存：I-14（`iss-00455`。マージ済み、閉じた）。Planning Level：strict（理由は `plan.md`）。
- この Issue は、契約 C1（ID の正規表現と種類のラベル）、C3（置き場と区切り、無視の3行）、C5、C7 の写しを持つ使う側である（Epic の `plan.md` の「Issue をまたぐ契約」の後の段落）。持ち主の公開の形は変えない。

## 背景

- 2026-10-29 に、利用者が、カタログの置き場を平らにし、slug を廃止し、ID・ディレクトリ名・ブランチ名を `<種類>-<番号5桁>` にそろえ、題名は GitHub の題名だけを正とすると決めた。同じ日に、Scope のディレクトリを、番号の1,000ごとの区切りの下に置くと決めた（1つのディレクトリの項目が増えすぎないため）。
- I-14 は runtime の部品（ID の正規表現 `CANONICAL_ID_RE`、本文の印の廃止、平らな置き場）を直した。I-16（`iss-00460`）は、区切りを CLI 本体に入れる（並べて進む）。
- マージ済みの移行のスクリプト（I-8）は、まだ前の方針で動く。
  - `register` が、Issue の本文に slug の印（`<!-- spec-dock:slug=… -->`）を足す。`verify` が印を照らし、`undo` が印を外す。作った Issue の見つけ直しが印を使う。
  - `build-canonical`、`move-local`、`adopt-worktree` が、入れ子のまま写し、ローカルの ID の名前だけを置き換える（`rename_path`）。
  - `export-legacy` が、入れ子のまま戻し、slug を本文の印から読む。
- spec-dock の仕様のツリー（`origin/main`、2026-10-29）には、相対のシンボリックリンクが293個（`artifacts/rules.md`、`discussions/rules.md`、`epics/rules.md`、`issues/rules.md`。すべて `spec-dock/docs/rules/` を指す）、相対のリンクを持つ Markdown が216個（Scope の中、`spec-dock/docs/`、リポジトリのルートの `docs/` を指す）ある。深さが変わると、多くが切れる。
- 関係者：
  - 統括のエージェントと利用者：I-10 と I-12 で、このスクリプトだけで、各リポジトリを安全に切り替え、必要なら戻せること。予行演習で、リンクが切れないことを確かめられること。
  - 移行の後の利用者とエージェント：移した仕様の中のリンクを、そのまま開けること。
  - 移行していないリポジトリ（版3）：今と同じに動くこと（AC-15）。

## 観測可能な要件

### R-456-01 区切りと ID（C1、C3 の写し）

- canonical のカタログの Scope のディレクトリの相対の場所は `<区切り>/<ID>` である。区切りは、番号 n（1以上）について、幅 w = max(5, n の桁数)、下端 = n − n mod 1000、上端 = 下端 + 999 で、名前は「下端と上端をそれぞれ w 桁に0で埋めて `-` でつないだもの」である。例：1 と 454 と 999 は `00000-00999`、2114 は `02000-02999`、99999 は `99000-99999`、100000 と 100454 は `100000-100999`、1000000 は `1000000-1000999`。
- 新しい ID は、種類の接頭辞と番号から作り（5桁未満は0で埋め、超えたらそのまま）、Epic の2章の正規表現 `^(init|epic|iss)-(?:[0-9]{5}|[1-9][0-9]{5,})$` に合う。
- スクリプトはパッケージを読み込まない。区切りの計算と ID の正規表現は写して持ち、テストでパッケージの値と比べる（区切りは I-16 のマージの後）。

### R-456-02 登録は本文を変えない（`register`、`verify`、`undo`）

- `register --apply` は、Issue の本文を変えない。本文に印を足す書き込み（本文の `PATCH`）を送らない。作る Issue（ローカルの Scope の置き換え）には、題名と種類のラベルだけを送り、本文を送らない。
- `plan` の登録の予定と `verify` の照らし合わせに、印の項目がない。`plan` は `SLUG_MARKER_CONFLICT` を出さない。
- `undo` は印を外す操作を持たない。

### R-456-03 作った Issue の見つけ直し（印を使わない）

- `register` は、Issue を作る前に、作る予定（種類のラベル、題名、時刻）を作業の記録 `undo.jsonl` に記録する（今のとおり）。
- 作成の結果が分からないとき（応答が失われたとき）と、作成の後に止まって作成の結果を記録できなかった後の再実行では、次の条件にすべて合う Issue を探す：その種類のラベルを持つ、題名が同じ、作成者が `gh` の今の利用者（`GET /user`）、作成の時刻が基準の時刻の5分前と同じか後、ほかの Scope に使われていない。基準の時刻は、その Scope の、結果の記録のない作成の予定のうち、最も古いものの時刻である（2回目の中断の後も、1回目に作った Issue が見えるようにするため）。5分の幅は、手元の時計と GitHub の時計のずれのためである（幅の中に同じ利用者の同じ題名の Issue が2つあれば、下のとおり止まるので、重複して使わない）。
  - ちょうど1つなら、それを作った Issue として記録して続け、新しい Issue を作らない。
  - 2つ以上なら、番号の一覧を付けて止まり、新しい Issue を作らない。次の1手は「残す1つのほかから種類のラベルを外す（か `not_planned` で閉じる）。その後、同じ `register --apply` を実行する」である。
  - 0なら、新しく作る。
- `undo` が、作成の結果が記録されていない作成の予定を外すときも、同じ条件（基準はその予定の時刻）で、開いている Issue を探す。2つ以上なら番号の一覧を付けて止まる。

### R-456-04 平らにする写し（`build-canonical`、`move-local`、`adopt-worktree`）

- パスの対応：Scope のディレクトリは、名前の形ではなく置き場で決める。`spec-dock/initiatives/` の直下と、Scope のディレクトリの直下の `epics/` と `issues/` のすぐ下にあり、`.meta.json` を持つディレクトリだけが Scope である（`discussions/` の下などの、ID の形の名前のディレクトリは Scope ではない）。各ファイルを、それを含む最も深い Scope のディレクトリからの残りのパスで、`<区切り>/<ID>/<残り>` に写す。
  - ID は `.meta.json` の `type`、`id`、`github.issue_number` だけから決める（ほかの項目は見ない）。`id` がローカル（`<種類>-local-<数>`）なら `idmap.json` の `id`。そうでなければ、`type` が種類で、`id` が Epic の2章の正規表現に合い、その番号が `github.issue_number`（1以上の整数）と同じとき、その `id`。
  - Scope の中の `epics/` と `issues/` は持ち込まない（子はそれぞれの `<区切り>/<ID>/` に移る）。`epics/rules.md` と `issues/rules.md` は捨てる。`.meta.json` は持ち込まない。
- 平らにできないもの：(a) `epics/` と `issues/` の直下の、`rules.md` でも子の Scope でもないもの、(b) どの Scope にも入らないファイル（仕様のツリーの直下のファイルなど）、(c) ID を決められない Scope（`.meta.json` が JSON として読めない、上の3つの項目が条件に合わない、ローカルの ID で `idmap.json` にも `plan` の置き換えの予定にもない）、(d) 同じ ID になる2つ以上の Scope のディレクトリ。
- リンクの書き換え：写したファイルのうち、相対のシンボリックリンクと、Markdown の相対リンク（`[…](相対パス)` と `[…]: 相対パス`）と、HTML（`.html`、`.htm`）の `href` と `src` の相対パス（URL、`#` で始まるもの、絶対パス、Markdown のコードの中（``` と ~~~ の囲み、` の個数によらないコードの範囲）は除く）で、元の位置から解決した先がリポジトリの中にあるものを、新しい位置から同じ先を指すように書き換える。
  - 先が仕様のツリーの中なら、先も写した後の位置にする。先が捨てる `rules.md` なら、そのリンクの最後の先（`spec-dock/docs/rules/…`）に向ける。先がなくなる `epics/` と `issues/` のディレクトリなら、その親の Scope の `<区切り>/<ID>/` に向ける。
  - 新しい位置から元の文字列のままで同じ先を指すリンク（Scope の中のリンクなど）は、書き換えない。`#` の後と末尾の `/` は残す。
- 書き換えられないリンク（移行の前は解決できたのに、写した後に解決できないもの）は、書き換えずに残し、一覧にする。移行の前から切れているリンクは、別の一覧にする（数えない）。

### R-456-05 `plan` が写しの結果を示す

- `plan` は、既定のブランチの仕様のツリーに平らにする写しを当てた結果として、平らにできないもの（R-456-04 の (a)〜(d)）、書き換えるリンクの数、書き換えられないリンクの一覧、移行の前から切れているリンクの一覧を示す。平らにできないものがあれば、終了コード1（問題を見つけた）で終わる。書き換えられないリンクは一覧にするだけで、終了コードを変えない。
- 登録の前（`idmap.json` がまだない）のローカルの Scope は、`plan` の置き換えの予定で写す。結び付いた Issue に置き換える予定のものはその番号の ID で、新しく作る予定のものは「`register` で決まる」仮の場所（`pending/<ローカルの ID>`）で写し、`data.flatten.pending` に示す。仮の場所は平らにできないものに数えず、終了コードを変えない。
- `plan` は読むだけで、対象のリポジトリ（作業ツリー、`.git` のオブジェクトと参照）に何も書かない。写した中身は、メモリーの上で比べる。

### R-456-06 `build-canonical` の履歴（2026-10-29 の統括の判断）

- `build-canonical` は、`git subtree split` の各コミットのツリーに、同じ平らにする写しを当てて履歴を作り直し、その上に管理ファイル（形式1）を足すコミットを作る。作り直したコミットは、元のコミットの作成者、日時、メッセージを保つ。同じ入力からは同じコミットができる（もう一度実行しても同じ結果）。
- 結果の、どのコミットのツリーも平らで（Scope のディレクトリは `<区切り>/<ID>/` だけ、`epics/` と `issues/` がない）、`.meta.json` がない。
- 既定のブランチの今の仕様のツリー（先端）に平らにできないものがあれば、何も push せずに、一覧を付けて止まる（終了コード2）。
- 履歴のコミットでは、平らにできる Scope だけを写し、平らにできないパスは、そのコミットからだけ落とす。落としたコミットの数と、落としたパスの数を種類ごとに、例とともに出力に示す（元のリポジトリの履歴は書き換えないので、落としたものは既定のブランチの履歴に残る）。
- 先端の結果のファイルの中身は、リンクの書き換えのほかは元と一致する。書き換えられないリンクと、移行の前から切れているリンクを、`plan` と同じ形で示す。

### R-456-07 `move-local` と `adopt-worktree` は平らにした位置へ移す

- `move-local` は、チェックアウトの `spec-dock/initiatives/` の下の追跡されていないファイルと無視されたファイルを、平らにする写しのパスの対応で求めたカタログの位置へ移し、移した Markdown、HTML、シンボリックリンクのリンクを書き換える。Scope は、切り替え前のコミットの `.meta.json` と、そのチェックアウトのブランチについて `adopt-worktree` が記録した `.meta.json` だけから決める。両方が同じディレクトリで違う ID を示すときと、位置を決められないファイルがあるときは、何も移さずに一覧を付けて止まる。
- `adopt-worktree` は、分岐点 M の仕様のツリーに同じ写し（履歴のコミットと同じ扱い）を当てたツリーを持つ canonical のコミット C を見つけ、作業ツリーの今の状態に平らにする写しを当てたツリーを、C を親として取り込む。作業の状態に平らにできないものがあれば、何も書かずに一覧を付けて止まる。消す前の一致の確かめは、写した後の中身（リンクを書き換えた後）と canonical を比べる。消す直前の「途中で変わっていないか」の確かめは、今のとおり元の中身で行う。

### R-456-08 戻すときの入れ子と slug（`export-legacy`）

- `export-legacy` は、GitHub の親子から入れ子のパス（Initiative は `<ID>-<slug>/`、Epic は `<親>/epics/<ID>-<slug>/`、Issue は `<親>/issues/<ID>-<slug>/`）を作り、カタログの `<区切り>/<ID>/` をそこへ写し、リンクを平らにする写しの逆に書き換える。各 Initiative に `epics/rules.md`、各 Epic に `issues/rules.md` を、従来の作成と同じ先（`spec-dock/docs/rules/initiative/epics.md`、`spec-dock/docs/rules/epic/issues.md`）への相対のシンボリックリンクとして置き直す。
- slug は、切り替え前の `.meta.json` の値を使う。切り替えの後に作った Scope は、題名（前後の空白を除く）が従来の規則 `^[A-Za-z0-9]+(?: [A-Za-z0-9]+)*$` に合えば、小文字にして空白をハイフンにしたもの、合わなければ `untitled` にする。
- 戻した結果は、従来モードの `workspace validate` を通る。`.meta.json` は、移行前のものと、`revision` と `lifecycle`、置き換えた ID、GitHub で変えた題名のほかは一致する（I-8 の判断）。
- 書き換えたリンクの数、戻せないリンク（カタログの中の決まらない先を指すもの）の一覧を、`plan` と同じ形で示す。往復で元の文字列に戻らないリンクは、次の3種類だけである：正規化していない元の文字列（`./a/../b` など）、捨てた `rules.md` へのリンク（`spec-dock/docs/rules/…` を指したまま戻る）、`epics/` と `issues/` のディレクトリへのリンク（親の Scope のディレクトリを指したまま戻る）。どれも同じ先を開く。
- 入れ子に戻せないものがあれば、`--apply` の有無によらず、何も書かずに一覧を付けて止まる（終了コード2）：親のない Epic と Issue、親の種類が規則に合わない Scope、種類のラベルが2つ以上の Issue、`<ID>/` のない Scope、Issue のない `<ID>/`、種類の付け替え（`SCOPE_KIND_CHANGED`）、区切りの外れ（直下の ID、区切りの違う ID、区切りの中の ID でない名前）、`<区切り>/<ID>/` の外のファイル、`<ID>/` の下の `epics/`・`issues/`。

### R-456-09 `verify` が置き場を確かめる

- `verify` は、今の照らし合わせ（種類、親、依存。印を除く）に加えて、origin の canonical（使い捨てのクローンに取って読む。origin になければ手元のカタログ）で、`.meta.json` がないことと、`.meta.json` の各 Scope の `<区切り>/<新しい ID>/` があり、Scope のディレクトリが `<区切り>/<ID>/` だけであることを確かめ、違えば不一致にする（AC-04）。canonical がまだなければ、今のとおり「確かめていない」と示す。

### R-456-10 手順書

- `README.md` から本文の印の説明を消し、平らにする写し、区切り、書き換えられないリンクの一覧の見方、`build-canonical` の履歴で落としたものの見方、`export-legacy` が止まる条件と直し方、往復で字面が戻らないリンクの種類を書く。作った Issue の見つけ直しは作成者の名前を比べるので、`gh` は利用者自身のトークンで使うこと（GitHub App のトークンでは名前の形が違う）を書く。

## スコープ

- 対象：`scripts/migrate-to-canonical/migrate.py` と `README.md`、そのテスト（`tests/unit/infra/test_migration_contract_copies.py`、`tests/integration/migration/`、`tests/support/migration_repo.py`）、テスト用の偽の `gh`（`tests/support/fake_github.py`。作成者と作成の時刻を足す）、この Issue の文書。
- 対象外：
  - SpecDock の CLI 本体（`src/spec_dock/`）。区切りを CLI に入れるのは I-16。カタログの検査、作成、読み取りは変えない。
  - Epic の文書（`E/` の直下）。区切りの決まりを Epic の文書に入れるのは I-16。
  - 本物の5つのリポジトリと本物の GitHub への書き込み（読むだけの `plan` はよい）。I-10、I-12 の本番の切り替え。
  - 従来モード（宣言の版3）のコードと、その振る舞いのテスト（AC-15）。
- 親の契約として維持する境界：C1、C3、C5、C7 の写しは、持ち主の公開の値と同じにする。I-8 の統括の判断（足すだけの `register`、消す前の一致の確かめ、`undo` は作ったものだけ、読み取り元は `origin/<既定のブランチ>`）を守る。

## 失敗・境界条件

- 番号が0以下で区切りを求めることはない（スクリプトの入力は正の番号だけ。作るときに検査する）。
- 番号が5桁ちょうど（99999）と6桁（100000）の境、1,000の境（999 と 1000）で、区切りが R-456-01 のとおりになる。
- 同じ Markdown のファイルに、書き換えるリンクと、書き換えないリンクと、切れたリンクが混ざっていても、書き換えるものだけが変わる。
- Markdown のコードの中（``` と ~~~ の囲み、` の範囲）のリンクの形の文字列は変えない。4つの空白で始まるコードのブロックは見分けない（一覧の項目の続きの行と区別できないため。中のリンクも、ほかと同じ規則で、同じ先を開くように書き換わる）。
- 履歴のコミットに、ローカルの ID で `idmap.json` にない Scope、同じ ID の2つのディレクトリ、`epics/` の下の仮置きのディレクトリがあっても、`build-canonical` は止まらず、そのコミットからだけ落とす。
- `register` の中断が、作成の予定の記録の後、作成の前なら、条件に合う Issue はなく、新しく作る（重複しない）。
- ほかの利用者が作った同じ題名の Issue、作成の予定の記録より前に作られた同じ題名の Issue は、作った Issue として拾わない。
- `export-legacy` で、日本語の題名の Scope の slug は `untitled` になり、同じ親の下に `untitled` が2つあっても、ID が違うので名前は重ならない。
- `export-legacy` の止まる条件に当たるときは、`--apply` がなくても終了コード2で止まり、何も書かない。
