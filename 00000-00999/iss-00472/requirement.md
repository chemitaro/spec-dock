# iss-00472 Define CUE Spec Schema V1 — 要件定義

詳細: [Requirement Guide](../../../docs/authoring/requirement.md)

表示名：CUE の仕様の型の版1を作る

## 目的

CUE で書く Scope（Initiative、Epic、Issue）の要件・設計・計画が従う型の版1（`specdock/v1`）を、SpecDock のパッケージに入れる。

- 保証レベル（`assurance.level`）で、必須の項目が変わる。
- 要件、設計、手順、テスト、子の Scope への切り分けのつながりの抜けが、型の計算する `findings` に、規則ごとに出る。
- 3つの種類の雛形の CUE が、置き換えの印に値を入れれば、そのまま型に通る。

この型は、親の Epic（epic-00425）の要である。出した版は、後から互換を壊して変えられない（契約 K6）。

## 背景

- 親の Epic は、仕様の正本を Markdown から CUE に移す。型がなければ、検査（I-2、iss-00473）も、作るときの一式（I-3、iss-00474）も、描画（I-5、iss-00476）も作れない。
- 型の骨組み（契約 K1、K2、K6）は、Epic の `design.md` の「責務・Interface」の1、2、6で決まっている。この Issue は、その骨組みの上に、具体の項目と規則を作り込む。
- 統括が `cue` 0.17.1 で試作した（統括の scratchpad の `cue-proto/`）。この Issue は、試作を写さず、K2 に合わせて作り直す。
- `cue` は、今の利用者の PATH にも、CI にもない。

## 観測可能な要件

番号は、この文書の中だけで使う（CUE の文書の `R-01` などとは別）。

### 型の置き場と評価の単位（K1、K6）

- **RQ-01 版の置き場**：型は、パッケージの `spec_dock/cue/v1/` に、`package spec` の `.cue` のファイルとして置く。新しく作る wheel と、sdist から作る wheel の両方に、同じ内容で入る。
- **RQ-02 版の名前と置き場の対応**：`requirement.cue` の `schema` の値（`"specdock/v1"`）から、型のディレクトリを決める部品を、パッケージが持つ。持っていない版や、形の違う値には、ディレクトリを返さない。
- **RQ-03 評価の単位**：K1 のとおりに、型のファイル、リポジトリの型のファイル（任意）、Scope の3つのファイルを並べて `cue export --out json -t kind=<種類>` にかけると、1つの評価にまとまり、JSON が出る。Scope のファイルは `import` を書かなくてよい。

### 型の項目（K2）

- **RQ-04 共通の項目**：`schema`（必須、`"specdock/v1"`）、`kind`（タグで渡す）、`assurance`（`level` と `reason` が必須）を持つ。保証レベルは、隠した項目 `_rank`（light=0、standard=1、strict=2、critical=3）に変わる。
- **RQ-05 番号の項目**：要件（`R-`）、失敗の条件（`F-`）、設計（`D-`）、手順（`S-`）、テスト（`T-`）は、番号をキーにした構造で持つ。番号の形が違うキーは、形の誤りになる。Epic と Initiative の切り分け（`slices`）は、子の Scope の ID をキーにする。
- **RQ-06 種類ごとの違い**：Issue の計画は手順とテストを持ち、切り分けを持たない。Epic と Initiative の計画は切り分けを持ち、手順とテストを持たない。違う種類の項目を書くと、直し方を示す形の誤りになる。
- **RQ-07 実行の割り当て**：計画は、任意で `execution`（セッションとレビュー）を持てる。モデルと推論の名前は、どんな文字列でもよい。
- **RQ-08 柔らかさ**：本当に要る項目だけを必須にする。各項目と、各ファイルのトップレベルには、型にない項目を足せる。

### 保証レベルと検査（R-B2、R-B3）

- **RQ-09 レベルで必須の項目が変わる**：`design.md` の「保証レベルごとの必須の項目」の表のとおりに、レベルを上げると必須の項目が増え、下げると減る。
- **RQ-10 つながりの規則**：Epic の `design.md` の規則の表（8つの規則と、出す段階）のとおりに、`findings` に規則ごとの一覧を出す。出す段階より低いレベルでは、その規則の一覧を出さない。Epic と Initiative では、Epic の `requirement.md` の R-B3 の注のとおりに、切り分けで読み替える。
- **RQ-11 指摘の形**：`findings` の各指摘は、問題のある項目の番号（`id`）、何が問題か（`message`）、直し方（`hint`）を持つ。直し方には、直すファイルと項目を書く。

### リポジトリの型（R-B6）

- **RQ-12 型を重ねる**：`package spec` のリポジトリの型のファイルを評価に加えると、その制約と規則が加わる。リポジトリの型は、`_rank` を使える。SpecDock の型のファイルは変えない。

### 雛形（K4 の中身）

- **RQ-13 雛形の中身**：3つの種類（Initiative、Epic、Issue）の `requirement.cue`、`design.cue`、`plan.cue` の中身を作る。保証レベルの値と理由には、置き換えの印 `{{ASSURANCE_LEVEL}}` と `{{ASSURANCE_REASON}}` を置く（印の置き換えは I-3）。
- **RQ-14 雛形が型に通る**：印に値を入れた雛形は、4つのレベルのすべてで、形の誤りがなく、`findings` の指摘もない。

### 版の固定（K6、AC-07 の土台）

- **RQ-15 見本の結果の固定**：v1 の型で書いた見本の Scope の評価の結果を、テストで固定する。型を変えて結果が変わると、テストが失敗する。

### 道具と CI

- **RQ-16 CI の `cue`**：Provider CI のテストのジョブが、版を固定した `cue` を、checksum を確かめてから入れる。
- **RQ-17 `cue` がないときは失敗**：`cue` を要するテストは、`cue` がないときに飛ばさず、入れ方を示して失敗する。

### 既存のものを壊さない（AC-12 の一部）

- **RQ-18 Markdown の Scope の回帰**：今の回帰のテストを変えずに通す。今の `spec-dock/templates/<種類>/` の `.md` の雛形は変えない。

## スコープ

### 対象

- パッケージの `src/spec_dock/cue/v1/`（型）と、版の名前から置き場を決める部品。
- パッケージのデータの設定（`pyproject.toml`）。
- 雛形の CUE の中身（置き場は `design.md` の「変更対象」）。
- 見本の Scope と、型のテスト。
- Provider CI（`.github/workflows/provider-ci.yml`）への `cue` の導入の手順と、そのテスト。

### 対象外

- `cue` を呼ぶ製品の部品、`scope check`、`work finish` の検査、`scope show` の `assurance`、`workspace validate`・`doctor`（I-2）。`cue` の最低の版の決定（I-2）。
- 置き換えの印を値に変える処理、配布資産 `spec-dock/templates/cue/<種類>/` の置き場、`static-inventory.json`、dogfood の写し（I-3）。
- 説明資料とデザインシステム（I-4）、CUE の描画（I-5）、ガイドとスキル（I-6）、spec-dock での導入（I-7）。
- 前の版の Scope を新しい版に上げる道具（Epic の `design.md` の K6 で、この Epic では作らない）。
- 利用者の環境への `cue` の導入。

### 親の契約として守る境界

- K1 の評価の単位（ファイルの並べ方、`-t kind`、`schema` による版の選択、`_rank`）。
- K2 の骨組み（番号のキー、`findings` の形、8つの規則の名前と段階、`slices`、`execution`）。
- K6 の版の置き場（`cue/v1/`）と、リポジトリの型の置き場（`spec-dock/cue/*.cue`）。

## 失敗・境界条件

- **保証レベルがない、4つ以外の値、理由がない・空**：形の誤りになり、誤りの文が、その項目（`assurance.level` など）を名指しする。循環などの、原因を隠す誤りの文にしない。
- **`schema` がない、または `"specdock/v1"` 以外**：形の誤りになる。
- **種類のタグがない、または3つ以外の値**：形の誤りになる（SpecDock は必ずタグを渡す）。
- **番号の形が違うキー**（`R1`、`r-01`、`S-1` など）：形の誤り（その項目は許されない）になる。
- **違う種類の項目**（Epic の `steps`、Issue の `slices` など）：直し方を示す形の誤りになる。
- **存在しない番号への参照**：形の誤りにせず、`findings` の `unknown-reference` に出す。
- **手順の状態が4つ以外**：形の誤りになる。
- **リポジトリの型が SpecDock の型と食い違う**：CUE の衝突として、評価が誤りになる（どちらのファイルかが位置で分かる）。
- **`cue` がない（テスト）**：テストが、入れ方を示して失敗する。飛ばさない。
- **CI で `cue` の取得や checksum が合わない**：その手順が失敗し、テストのジョブが失敗する。

## 受け入れ条件

- **AC-01（Epic の AC-03）**：規則（8つ）× 4つのレベル × 3つの種類のすべての組で、その規則だけに違反する見本が、出す段階以上のレベルでは、その規則の `findings` に出て、ほかの規則には出ない。出す段階より低いレベルでは、どの規則にも出ない。Epic と Initiative では、切り分けで読み替えた規則で確かめる（`execution-reference` と `unknown-reference` は、種類ごとの参照で確かめる）。
- **AC-02（Epic の AC-04）**：standard で通る見本の `assurance.level` を strict に変えると、strict で必須の項目がないことが形の誤りになる。その項目を書き足すと通る。light から standard でも同じ（standard で必須の項目）。レベルを下げると、誤りにならない。
- **AC-03（Epic の AC-06）**：`execution` で、存在しないセッションを指す手順（切り分け）や、存在しない手順（切り分け）を指すレビューが、`findings` の `execution-reference` に出る。モデルと推論の名前は、空の文字列、日本語、記号を含む、どんな文字列でも誤りにならない。
- **AC-04（Epic の AC-08）**：見本のリポジトリの型（`package spec`）を加えると、その型が必須にした項目がない文書が誤りになり、その型が足した規則が `findings` に出る。`_rank` を使った条件が、レベルに応じて働く。
- **AC-05**：3つの種類の雛形に、見本の値（引用符、改行、バックスラッシュ、`\(` を含む理由）を CUE の文字列の書き方に変えて入れたものが、4つのレベルのすべてで、誤りなく評価でき、`findings` のすべての一覧が空である。
- **AC-06**：「失敗・境界条件」の形の誤りの各場合で、評価が失敗し、誤りの文が、問題の項目の道筋（例 `assurance.level`、`requirements.R1`、`steps."S-01"`）を含む。`cycle` を含む誤りの文にならない。
- **AC-07（Epic の AC-07 の土台）**：v1 の見本の Scope（3つの種類、4つのレベルを含む）の評価の結果（JSON、または形の誤り）が、保存した期待の結果と一致する。
- **AC-08**：新しく作った wheel と、sdist から作った wheel に、`spec_dock/cue/v1/` の `.cue` のファイルが、ソースと同じ内容で入る。版の名前の部品が、`"specdock/v1"` に `cue/v1/` を返し、持っていない版と形の違う値に何も返さない。
- **AC-09**：Provider CI の `provider-tests` のジョブが、`uv run pytest` の前に、固定した版の `cue` を、Linux の amd64 と arm64 のそれぞれの checksum で確かめてから入れ、PATH に足す。テストが、ワークフローのこの手順を確かめる。`cue` を要するテストは、`cue` が PATH にないとき、飛ばさずに失敗する（テストで確かめる）。
- **AC-10（Epic の AC-12 の一部、AC-15）**：`make lint` と `uv run pytest` が通る。既存のテストのファイルと、`spec-dock/templates/<種類>/` の `.md` の雛形は、この Issue で変えない。

## 制約・前提

- Linux と macOS、Python 3.10 以上。
- テストと手元の確かめの `cue` は v0.17.1（2026-07-16 公開）。この worktree の無視される場所（`.workbench/bin/`）に入れ、利用者の環境には入れない。
- テストは外のネットワークを使わない（CI の `cue` の取得は、テストの前の手順で行う）。
- 本物の GitHub に試しの Issue を作らない。本物のカタログに CUE の Scope を作らない。
- Epic の目的、Issue の分け方、契約 K1〜K6 は変えない。変える必要は、統括に聞く。
- 文書の正本は、この Scope の Markdown（Epic の `requirement.md` の対象外）。
