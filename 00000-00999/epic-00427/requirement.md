# epic-00427 Build Html Spec Dashboard — 要件定義

詳細: [Requirement Guide](../../../docs/authoring/requirement.md)

表示名：仕様を見渡す HTML のダッシュボード

> この文書は、要件整理を始める前の下書きである。利用者から聞いた構想（下の「背景」）を出発点に、モックの画面を作り、必要な機能と追加したい機能を取りまとめて、要件を固める。決まったことから、この文書を書き直す。

## 目的

SpecDock が管理する仕様（Initiative、Epic、Issue と、その要件・設計・計画など）を、人が全体を見渡し、1つを選んで詳しく確かめられる、HTML のダッシュボードを作る。

利用者の言葉では、これまでのプログラミングは「点」だった。SpecDock で「面」にし、さらに時間の軸を加えた立体的な管理ができるようにする。

## 背景

### 今の工程（2026-10-25 に利用者が依頼）

ダッシュボードの開発を、epic-00424 と並行して、仕様の策定まで進める。この工程では、次のことまでを行う。

1. モックの画面を作る。
2. モックを見ながら、必要になりそうな機能と、追加したい機能を取りまとめ、整理する。
3. 利用者に確かめ、要件（この文書）を固める。

設計、計画、実装は、要件が固まった後に、改めて利用者と決める。

### 前の Epic との関係

- **epic-00424**（#424、仕様の正本を `spec-dock/canonical` と GitHub Issue に集約する）：仕様の内容の正本を各PCのカタログ（`spec-dock/initiatives/` から開く）に、構造の正本を GitHub Issue に置く。GitHub の構造をリポジトリごとに一括で取得して、PCのユーザーごとの「構造のスナップショット」（`~/.local/state/spec-dock/github/github.com/<owner>/<repo>/snapshot.json`）に持つ。つなぎとして、今までの Markdown と PlantUML のダッシュボード（`spec-dock/dashboard.md`、`tree.puml` など）を、定期の同期が作り直す。このダッシュボードは、それを置き換える。
- **epic-00425**（#425）：もとは HTML のダッシュボードと CUE の両方を扱う予定だった。2026-10-25 に、ダッシュボードをこの Epic に分けた。epic-00425 は、仕様の文書を CUE（エージェントが確かめるためのもの）と HTML（人が読むもの）に移すことを扱う。このダッシュボードは、その HTML を組み込む側になる。

### 利用者の構想（2026-10-25）

- HTML で作る、レスポンシブで使いやすいウェブの画面にする。
- Initiative、Epic、Issue の縦の階層（親子）と、作業の順番の依存（blocked by）を、図で示す。
- 状態を色で示す。実装中のもの、まだ始めていないもの、止められているもの（依存が終わっていない）、終わったもの。
- 終わったものを隠す表示と、終わったものを含めてすべてを示す表示を切り替えられる。
- 1つの Epic や Issue を選ぶと、詳しい画面を開ける。詳しい画面には、次を示す。
  - GitHub の日本語の題名。
  - 依存しているもの、依存されているもの。
  - 配下に含むもの。
  - その Scope の中での、実行の順番の依存。
  - その Scope の要件、設計、計画の内容。
- 1か所の正本から、今の要件、設計、計画をその場で描き、一部を画面に組み込んだり、人向けのページを開いたりできる。
- 操作のたびに GitHub に問い合わせない。一括で取得した構造（epic-00424 の構造のスナップショット）を使い、GitHub の負荷と待ち時間を抑える。

## 制約・前提

- 対応するのは Linux と macOS（epic-00424 と同じ）。
- 構造は、epic-00424 の構造のスナップショット（`design.md` 2章、契約 C10）から読む。内容（要件、設計、計画など）は、カタログのファイルから読む。
- 実装は、epic-00424 の構造のスナップショット（I-1）とカタログ（I-2）ができてからになる。Epic 単位の依存は付けず、実装の Issue を作るときに、epic-00424 の該当する Issue への依存を付ける（今の工程を始められるようにするため）。

## 未解決事項（要件整理で確かめる）

- 画面をどこで、どう開くか（手元のサーバー、静的な HTML のファイル、Tailscale での公開、スマートフォンでの閲覧など）。
- 見るだけか、画面から操作もするか（着手、完了、依存の変更など）。
- 1つのリポジトリだけか、利用者の5つのリポジトリをまとめて見るか。
- 「時間の軸」で何を見るか（仕様の変更の履歴、Issue の状態の移り変わり、進み具合の推移など）。
- 「リアルタイム」の新しさ（構造のスナップショットの新しさは、およそ1〜2分。親子と依存だけの変更は最大30分）。
- 要件・設計・計画を、Markdown のまま描くか、epic-00425 の HTML を待つか。
