Storage Core + Authoring Kitへ、製品境界を引き直す

epic-00356「SpecDock Core Simplification and External Intelligence Boundary」を、今日参加したメンバーが一冊で理解するための統合説明資料です。

Epic #356 OPEN 4 Issues / 2 parallel lanes Planning draft Requirement review: fail Implementation: not started
このHTMLの位置づけ このファイルは理解支援用のEpic-local Artifactです。仕様の正本は、同じEpic直下の requirement.md、design.md、 plan.md、現在地はreport.mdです。 テキスト中心で読む場合はMarkdown版を参照してください。

1. 5分で分かる要約

SpecDockを、開発を細かく指揮するワークフロー製品から、仕様と作業構造を安全に保存する小さな基盤へ戻します。

Product Core
Storage Core

node階層、正本文書、Artifact、依存関係、active、GitHub linkageを決定的に管理します。

Writing Support
Authoring Kit

Requirement / Design / Planを、特定モデルに依存せず良く書くためのtemplateとguideです。

Replaceable Client
External Intelligence

ChatGPT、Codex Goal、外部Skill、将来のAgentは製品外からCoreとKitを利用します。

変える理由

  • モデル、ブラウザ、Agent harness、レビュー手法の変化がSpecDock本体へ波及している。
  • 多数のSkill、command、状態、証跡、testを同時に保守する必要がある。
  • 完全自動化がIssueの過剰分割や低価値な文書を生みやすい。
  • 安定した構造管理と、変化の速い認知・実行workflowが混在している。
中心判断 自動化を捨てるのではありません。自動化の選び方をSpecDockが固定せず、どの自動化からも使える保存・構造基盤になります。

混同してはいけない三つの状態

状態2026-08-08時点の実態
Current Product多数のmanaged Skillと、assurance、authoring、workflow、delegated-authoring等のRuntime surfaceがまだ存在。軽量化は未実装。
Current PlanningEpicと4 Issue、依存edgeは作成済み。Requirement Reviewはfail、Design / Plan Reviewは未実施、Issueはscaffold。
Target ProductStorage Core + Authoring Kit + 2 Skill。旧workflowを削除し、外部インテリジェンスを交換可能にする目標状態。

2. なぜ軽量化するのか

Stable responsibility

長期的に安定している責務

  • Initiative / Epic / Issueとstable ID
  • GitHub Issueとの対応
  • Requirement / Design / Plan
  • Scope-local Artifact
  • dependency DAGとcycle検査
  • active、projection、managed asset管理
Fast-changing responsibility

変化が速く、外へ出す責務

  • Planning / Review / Execution workflow
  • phase promotion、fresh reviewer gate
  • assurance grade、specialist、delegation
  • ChatGPT-first orchestration
  • PR creation / observation / merge preparation
  • named agent role、host adapter

認知的自由と構造的安全を分離する

操作担当理由
Markdown本文の読取り・編集人間 / Agent内容には文脈と判断が必要
node作成・close・deleteSpecDock CLIidentityと階層を壊さない
dependency変更SpecDock CLIcycleや不正edgeを保存前に拒否
GitHub linkage / projectionSpecDock CLI決定的で再生成可能にする
仕様作成・レビュー・実装方法Operator最適な外部能力を交換可能にする

4. 新しい利用イメージ

Scopeを決める
人間とCodexが対象nodeと目的を確認
論点をArtifact化
必要ならgrill-with-docsを明示起動
外部能力で作成・実装
ChatGPTや別Skillを交換可能に利用
Coreで構造検証
Codexが反映し、validate / sync

2つのmanaged Skill

Model-invoked

spec-dock

Scope、parent、正本文書、Artifact、dependency、CLIを案内します。PlanningやImplementationの進め方は規定しません。

User-invoked only

spec-dock-grill-with-docs

一つのScope-local ArtifactへFacts、Decisions、Alternatives、Open Questions、Authoring Briefを残します。三文書は自動変更しません。

外部能力が利用不能な場合 spec-dock-grill-with-docsの該当処理だけが明確に停止します。Storage Coreと通常のspec-dockは影響を受けません。

Coreに保存しないもの

model名、provider設定、browser profile、cookie、wrapper path、session ID、Prompt version、provider固有result schemaは保存しません。

6. Migrationとデータ保護

Workflow compatibilityは残さずhard cutoverします。ただし、利用者の仕様データは守ります。

保持するデータ

  • node directoryと.meta.json
  • dependency edgeとGitHub linkage
  • Requirement / Design / Plan / Report
  • Artifact / Discussion / accepted ADR
  • Workbenchのunmanaged content

削除するmanaged surface

  • planning / execution / clarification Skill
  • PR workflow Skill
  • host adapter / named agent role
  • product-owned ChatGPT runtime
  • obsolete workflow docs / templates / tests

安全境界 user-owned assetをpruneしない、historical documentを一括書換えしない、旧workflowを別名で再実装しない、provider固有情報をCore schemaへ入れない、という4点が重要です。

Rollback: 新Coreに旧workflow fallbackを残さず、Git revert、旧releaseへの明示的version rollback、backupからのmanaged asset復元を使います。

9. 実装時の判断ルール

  1. Provider sourceを先に直す。 src/spec_dock/assets/が配布物のauthorityで、spec-dock/はdogfood projection。
  2. Coreとworkflowを混同しない。 構造invariantは残し、認知的workflowは製品へ戻さない。
  3. データ互換性を優先する。 workflow互換性のために旧aliasを恒久維持しない。
  4. managed / user-ownedを識別する。 prune対象はSpecDock管理と証明できるassetだけ。
  5. 外部providerをschemaへ入れない。 接続はRepo-local / Operator-owned Skill側。
  6. I1〜I4の契約境界を守る。 技術レイヤーごとの過剰分割を避ける。
  7. projectionをauthorityにしない。 provider sourceを変更し、dogfood側で確認する。
  8. 未解決事項を暗黙に決めない。 Epic正本へ戻して解決する。
