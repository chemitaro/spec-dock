Epic #384 / Accepted Architecture

SpecDockのテストを根本から軽くする設計

4時間規模のテストを並列化だけで10分に見せるのではなく、巨大化した配布更新の契約そのものを小さくします。結論は、利用者データを完全に分離し、SpecDock内部の4つのrootを更新時に丸ごと交換する方式です。

採択済み Option C2 — Disposable Root Replacement / Fixed Skill Slots

図を読み込んでいます。

まず押さえる結論

残すもの

Initiatives、そこに含まれるArtifacts、Workbench、未知の利用者ファイル、他のskills。

丸ごと交換するもの

spec-dock/docs、templates、system、scripts。

別扱いするもの

共有領域にある2つのSpecDock skill。固定slotと小さなowner markerで管理します。

やめるもの

ファイルごとの過去hash、操作journal、全checkpointからの自動復旧、通常uninstallからのspec削除。

安全性の焦点を変えます。 Provider内部の変更を保存することではなく、利用者データと共有領域を絶対に巻き込まないことを安全契約にします。

なぜテストがここまで長くなったのか

現行テストは、単に書きすぎたのではありません。配布更新機能が「過去のあらゆるファイル状態を識別し、失敗位置から自動復旧する」という大きな責務を持つため、その状態の組合せをかなり忠実に検査しています。

updateはどう動くか

      
新しい4 rootを先に全部作って検証し、その後に固定順で交換します。複数root全体を「完全に原子的」とは約束しません。途中停止ではtoolingが一時的に混在・欠落しても、外部installerから同じversionを再実行すれば収束する設計です。


      
      
更新シーケンス図を描画しています。

      
PlantUMLソースを確認する


      

        重要な制約: Provider rootやmanaged skillの内側を直接編集しても、次回updateでは保存されません。独自変更が必要なら、配布copyではなくSpecDock自体をforkして管理します。
      

    


    

      
途中で失敗したらどうなるか

      
以前の設計は、全checkpointをjournalへ記録して自動再開しようとしていました。新設計は状態を増やしません。利用者データを守ったうえで、desired versionをもう一度適用します。

      

        

          
失敗位置残る状態回復方法

          
            
stage / validate中旧installationがそのままcandidate修正後に再実行

            
root削除後・rename前一つのprovider rootが欠落外部installerで同versionを再実行

            
root間old / new rootが混在、ready markerは旧4 rootをdesiredへ再置換

            
scripts置換後・ready前repo-local commandが使えない可能性installed packageまたはuvxから再実行

            
ready後のcleanup新versionはready、stagingだけ残る成功扱い。限定cleanupを後で実施

            
symlink / marker不正targetは未変更人間が境界を確認して修復

          
        

      

      
この設計はtoolingの一時availabilityを完全保証しません。その代わり、Initiatives / Artifactsを巻き込むrollbackや、自動復旧engineが新たな破壊経路になることを避けます。

    


    

      
skillを安全に更新・削除する方法

      
.agents/skills は共有領域なので、親全体を交換できません。そこで「SpecDockが所有すると証明できる固定slot」だけをleaf root単位で扱います。


      
      
skill lifecycle図を描画しています。

      
PlantUMLソースを確認する


      
markerはowner、slot、schema version、distribution versionだけを持ちます。過去の全file hash、任意の削除path、checkpointは持ちません。現在のmarkerなし2 skillsは一度だけexact treeを確認して移行し、そのmigration adapter自体にも終了期限を設けます。

    


    

      
uninstallの意味も小さくする

      
通常uninstallが削除できるのは、4 provider roots、owner markerが有効なSpecDock skill slots、小さなinstallation recordだけです。

      
    
        
  • spec-dock/initiatives/** とArtifactsは残ります。
    • 
        
  • .workbench/**、生成物、未知path、他のskillsも残ります。
    • 
        
  • --remove-specs に相当する利用者データ削除は通常uninstallから外します。
    • 
        
  • 本当にpurgeが必要なら、別command・別authority・別Issueとして設計します。
    • 
      

      
考え方: 「ツールを外す」と「利用者の履歴を消す」は、同じ操作であってはいけません。

    


    

      
テストはどう減らすか

      
新しいテストを足してから旧テストを残すのでは、実行時間は減りません。production contractの切替と同じchangeで、退役したcontractのtestを削除します。

      

        

          
残す証明廃止できる証明

          
            
allowlist外へ書かない・消さないprovider root内のfileごとのmodified / unknown判定

            
symlink root / parent rebindでwrite前停止過去versionごとのfile hash catalog

            
Initiatives / Artifacts / 他skillsがbyte-identical全checkpointからのjournal resume

            
staging failureではtarget未変更cross-intent recoveryとquarantine復元

            
root間failure後の再実行収束通常uninstallとspec purgeの組合せmatrix

            
fixed skill markerのowned / foreign境界同じnodeのordinary / parity / full重複実行

          
        

      

      
最終portfolioはpure contract、filesystem service、CLI mapping、built-artifact lifecycle、OS固有差分に分けます。ただしtechnical layerごとにIssueを分割せず、一つの利用者behaviorをproductionからtest削除までend-to-endで受け入れます。

    


    

      
実装の分け方

      
    
        
  1. Disposable provider root lifecycle: 4 rootのinit / update、ready marker、one-shot migration、旧per-file route削除。
    2. 
        
  2. Fixed skill slot lifecycle: 2 slotsのowner marker、update / retirement、他skillsの保持。
    3. 
        
  3. Tooling-only uninstall and compatibility: user data不変、purge分離、workflow / CLI ownership判断。
    4. 
        
  4. Test portfolio and CI cutover: 旧tests・ledger・timing weights・4-shard runnerを撤去し、単一process10分gateへ移行。
    5. 
      

      
これはIssue候補の粒度評価結果であり、まだIssueは作成・開始していません。legacy support期間、.github/workflows/ci.ymlの所有者、purge CLIの移行などは、影響するIssueを開始する前にProduct判断を確定します。

    


    

      
成功条件

      
    
        
  • canonical regressionを単一pytest process、worker 1で5回実行し、全回600秒以内。
    • 
        
  • child process込みの平均論理core使用数が全回1.1以下。
    • 
        
  • zero failure、zero policy skip、same candidate / OSのduplicate nodeが0。
    • 
        
  • active failure ledger、timing weights、4-shard runnerが残っていない。
    • 
        
  • root間failure、symlink、marker mismatch、allowlist外削除などのseeded faultを100%検出。
    • 
        
  • Initiatives / Artifactsとunrelated skillsがupdate / uninstall前後でbyte-identical。
    • 
      

      
wall timeだけ速くてもCPUを使い切る設計は合格ではありません。時間、CPU、process数、workspace copy量、duplicate実行を同時に測ります。
