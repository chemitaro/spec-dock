1. まず結論

このEpicは「テストを速くする」だけの計画ではありません。
大量のテストを生んでいるproduct contractそのものを小さくし、その後で、残すべき契約を一度だけ・正しい層で証明するテスト構成へ変える計画です。

並列化は待ち時間を隠せますが、実行量、CPU消費、重複、保守対象は減りません。Epic #384は、per-file identity、historical digest、journal、checkpoint、retry、cross-intent recovery、purgeを一つのengineへ積み上げてきた状態を見直します。

安全性は弱めません。安全の置き場所を、膨大な履歴状態の組合せから、固定root、固定skill slot、no-follow binding、unknown時のpreserve-and-blockへ移します。

4. 最初に知る用語

      

        
用語このEpicでの意味

        
          
candidate一回の検証対象となる同一source SHA・同一artifact bytesの候補。

          
contract利用者へ約束するbehavior、またはsecurity / safety invariant。実装詳細や過去Issue名そのものではない。

          
disposable rootproviderが内部customizationを保存せず、candidate全体へ置換できる固定root。

          
fixed skill slot共有parent配下でSpecDockが所有できるexact leaf。owner markerがauthorityになる。

          
ready marker4 rootsとaccepted skill slotsの配置がすべて終わったcandidateだけをreadyと示す小さな記録。

          
removal receipt何を、どのauthorityで、どのsuccessorへ置き換え、どのSHA・commandで検証したかを残す削除証拠。

          
policy skipcollection後にpolicyでtest bodyを実行しない状態。targetではlane ownershipで対象外にし、merge-required selected nodeのskipを0にする。

          
fail closedownershipや証拠を確認できないとき、推測して書換え・削除・成功認定をせず停止すること。

        
      

    


    

      
5. Epic全体のRequirement

      

        
R1: 一つの実行時間予算
single pytest process、worker 1。固定条件の5回すべてが600秒以内。child-inclusive CPU / wall比は各回1.1以下。

        
R2: 重複実行ゼロ
同一candidate・OS・contractを複数laneで証明しない。artifact build invocationは1回。

        
R3 / R3A: 追跡可能性
全nodeをbaseline SHAへ束縛し、contract、owner、lane、cost、dispositionを持たせる。削除にはsuccessorまたはretirement authorityが必要。

        
R4: 層ごとの証明責務
pure/domain、filesystem/service、CLI adapter、artifact lifecycle、platform deltaを分け、同じmatrixを各層で反復しない。

        
R5 / R5A: distribution簡素化
4 disposable roots、2 fixed skill slots、one ready markerへ縮小。user dataとshared contentは境界外。

        
R5B: Product decision gate
#388〜#390を先にacceptし、legacy、purge、workflow / artifact policyを実装者が推測しない。

        
R6: failureを成功扱いしない
active failureをexact nodeごとにfix / retire / successorへ処置し、blanket approvalを残さない。

        
R7: 実行量の可視化
wall / CPU、node、subprocess、workspace、copy bytes、duplicate、build countをcandidate SHA付きで報告し、budget超過をfailureにする。

分類対象lifecycle contract

        
          
durable user dataspec-dock/initiatives/**、nested Artifactsinit / update / tooling uninstall / retry / cleanupは変更しない。

    2. 
        
  2. tree digest、required entrypoint、marker、allowlistをtarget mutation前にvalidateする。
    3.

7. なぜ10個のIssueへ分けるのか

      
4 rootsと2 slotsは同じstaging・writer・ready markerを共有するため、一つのproduction Issueに統合します。一方、Product判断、inventory、failure disposition、test再編、CI切替、長期安定性は、受入れ可能な成果と失敗時の戻り先が異なるため分けます。

      
      
Issue依存図を描画しています。

      
PlantUMLソースを確認する

      
順序の核心は、判断 → inventory → production contract cutover → test削除 → CI切替 → 長期証拠です。テスト削除を先行させないことが安全性の中心です。

Planning Level: strict。後続: E384-04、E384-06。

        

          
Requirement

E384-02 / iss-00389 / GitHub #389

        
正規作成済み・decision未受理 Tooling Uninstall Spec History Purge And Public CLI Compatibility

        
Planning Level: critical。不可逆なuser data削除authorityを扱う。

        

          
Requirement

Design
tooling uninstall contractとhistory purge authorityをcommand levelで分離する。normal uninstall、update、retryからpurgeへ到達できない構造にする。

          
Plan

10. 失敗時にどう振る舞うか

      

        
失敗期待する状態次の行動

        
          
candidate stage / validate失敗target旧stateを維持。mutation 0。candidateを修正して再実行。

          
root削除前の失敗target旧stateを維持。same desired versionを再実行。

          
delete後・rename前一root欠落。user data不変。ready markerは旧。外部installerから再実行。

          
root間停止old/new/missingの混在。new readyではない。全root / slotをsame versionへ再置換。

          
scripts後・ready前repo-local commandが使えない可能性。installed packageまたはuvxから再実行。

          
symlink / rebind / marker mismatchwrite前block。人間がownership boundaryを修復。

          
test selector omissionmergeをblock。single-process全correctness gateへ戻す。shardやapproved failureは復活させない。

          
5回 / 20回seriesで失敗Epic acceptance未達。E384-08または09へ戻り、修正後にseriesをreset。

        
      

      
禁止される近道: unknown ownershipへの書込み、silent purge、old engineへのautomatic fallback、budget達成のためのworker追加、失敗をapproved ledgerでGREEN扱い、Issue #372への横入り。

unexpected_failures = 0

policy_skips = 0
