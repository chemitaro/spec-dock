# epic-00425 Switch Spec Documents To CUE And HTML Explanations — 要件定義

詳細: [Requirement Guide](../../../docs/authoring/requirement.md)

表示名：仕様の文書を、エージェントが確かめる CUE と、人が読む HTML の説明資料に分ける

## 目的

SpecDock の Initiative、Epic、Issue の要件・設計・計画を、エージェントが厳密に扱える CUE で書く形に変える。人には、HTML の説明資料で同じ内容を説明する。

- 要件、設計、計画の手順、テストのつながりを、型で検査する。LLM のレビューに頼らず、安く、速く、機械的に抜けを見つける。
- 何をどれだけ確かめるかを、Scope ごとの **保証レベル**（Assurance Level）で決め、型の必須の項目を切り替える。
- 計画を、作業しながら更新する台帳にする。ダッシュボード（epic-00427）が、進み具合を図で見せられる形にする。
- 人には、Markdown を1本書けば作れる HTML の説明資料を用意する。SpecDock が、テンプレートとデザインシステムを配る。

利用者の言葉では、今の Markdown の仕様は「人にとっては複雑すぎ、エージェントにとっては柔軟すぎる、どっちつかずの存在」になりつつある。この Epic は、役割を人向けとエージェント向けに分けて、これを解く。

## 背景

### 解く問題

- 今の要件・設計・計画は、1本の Markdown である。人には長く、細かすぎる。エージェントには、書き方が自由すぎて、抜けや食い違いを機械的に見つけられない。
- 要件を満たす設計、手順、テストがあるかは、今はレビュアー（LLM）が読んで確かめるしかない。費用と時間がかかり、見落としもある。
- 計画の進み具合は文章でしか分からず、ダッシュボードで図にできない。
- 今の Planning Level は、文章で `plan.md` に書くだけで、SpecDock は値を知らない。エージェントのモデルと推論を選ぶ前に、機械的に読めない。

### 関係者

- 利用者（人）：説明資料で議論し、判断する。ダッシュボードで進み具合を見る。
- エージェント（Claude Code、Codex）：CUE の仕様を書き、検査し、計画を更新しながら実装する。統括は、保証レベルを読んで、worker のモデルと推論を選ぶ。
- epic-00427（HTML のダッシュボード）：この Epic の文書と描画の部品を使う側。
- 利用者のモデルと推論の policy：保証レベルを読む側。SpecDock は、policy に依存しない。

### 親の Initiative と、ほかの Epic との関係

- epic-00424 で、仕様の内容の正本はカタログ（`spec-dock/canonical`）、構造の正本は GitHub Issue になった。この Epic の文書もカタログに置く。
- 順番は、この Epic の後に epic-00427（見るだけのダッシュボード）、その後に epic-00471（Orca との連携）である（2026-10-30、GitHub の blocked by に登録済み）。
- epic-00427 からの依頼（2026-10-26）：説明資料の置き場と見分け方を決めること、CUE から HTML を描く部品をダッシュボードのサーバーから呼べるようにすること（epic-00427 の R-E9）。

### 前提とする材料

利用者への聞き取り（2026-10-30、5回）の記録と、議論用の説明資料（版 0.4）は、この Scope の `.workbench/` と `explanation.html` にある。説明資料は下書きで、この要件定義書が正本である。

## 観測可能な要件

### A. 文書の種類と正本

- **R-A1 CUE が正本**：新しく作る Initiative、Epic、Issue の要件・設計・計画は、`requirement.cue`、`design.cue`、`plan.cue` に書く。これらが、その Scope の要件・設計・計画の正本（SSOT）である。
- **R-A2 説明資料**：人向けの説明は、各 Scope の直下の `explanation.html` に書く。HTML の中の Markdown を書く場所に、Markdown を1本書けば資料になる。説明資料は、CUE を人に説明するものである。人との議論が先に立つときは、説明資料が下書きとして先に進んでよい。CUE を書いた後は、CUE が正本で、説明資料は CUE に合わせて直す側になる。
- **R-A3 Markdown のままの文書**：報告（`report.md`）と ADR は、今と同じ Markdown で書く。
- **R-A4 Artifact**：Lean（厳密なロジックの定義）、PlantUML（クラス図、ER 図など）などのファイルは、任意で、今の `artifacts/` に置く。専用のディレクトリは作らない。PlantUML のファイルは、PlantUML のまま残す。
- **R-A5 作る時に一式を置く**：`scope create` と `scope import github` は、新しい Scope の直下に、既定で `requirement.cue`、`design.cue`、`plan.cue`、`explanation.html`、`report.md` を雛形として置く。

### B. 型と検査

- **R-B1 型を配る**：SpecDock は、文書の種類（要件、設計、計画）と Scope の種類（Initiative、Epic、Issue）ごとの CUE の型と雛形を配る。型は硬くしすぎず、本当に要る項目だけを必須にする。それ以外は任意にし、必要に応じて項目を足せるようにする。
- **R-B2 保証レベルで必須の項目を変える**：型は、その Scope の保証レベル（R-C1）に応じて、必須の項目を変える。
- **R-B3 つながりの検査**：要件、設計、計画の手順、テストは、それぞれ番号を持ち、互いを番号で指す。SpecDock の検査は、次の表のとおりに、つながりを確かめる。

  | 検査 | light | standard | strict | critical |
  |---|---|---|---|---|
  | 番号の重複と、存在しない番号への参照がない | 必須 | 必須 | 必須 | 必須 |
  | すべての要件に、それを満たす手順がある | 必須 | 必須 | 必須 | 必須 |
  | すべての要件に、それを満たす設計がある | 任意 | 必須 | 必須 | 必須 |
  | すべての要件に、確かめるテストがある | 任意 | 必須 | 必須 | 必須 |
  | すべての手順が、いずれかの要件に結び付く | 任意 | 任意 | 必須 | 必須 |
  | 失敗の条件ごとに、確かめるテストがある | 任意 | 任意 | 必須 | 必須 |
  | 戻し方（ロールバック）を定義している | 任意 | 任意 | 任意 | 必須 |

  Epic と Initiative の計画は、自分では実装の手順とテストを持たず、子の Scope への切り分けを持つ。そのため、Epic と Initiative では、「手順がある」「テストがある」「失敗の条件ごとのテストがある」は、その要件を任せた子への切り分けがあることで満たす。「どの要件にも結び付かない手順」は、どの要件も任されていない切り分けに読み替える。設計の検査は、Issue と同じに行う。

- **R-B4 検査のコマンド**：SpecDock の1つのコマンドで、1つの Scope の CUE の文書を検査できる。インターネットにつながっていなくても動く。結果は、誤りごとに、ファイル、項目、直し方を示す。JSON でも出せる。
- **R-B5 型を磨き続ける**：型は一度決めて終わりにせず、使って、レビューして、直すことを繰り返す。型を変えても、前の型で書いた Scope が壊れないように、CUE の文書は、どの版の型に従うかを持つ。SpecDock は、その版の型で検査する。
- **R-B6 型を重ねられる**：利用者のリポジトリは、SpecDock の型の上に、自分の制約を足せる（例：特定の項目を必須にする）。SpecDock の型は変えずに足す。
- **R-B7 終わる時の検査**：`work finish` は、その Scope の CUE の文書と説明資料を検査する。誤りがあれば、仕様の保存の確かめと同じく、終わらずに止まり、誤りを示す。Markdown の Scope では、今と同じに動く。

### C. 保証レベル

- **R-C1 名前と値**：Scope ごとに、保証レベル（英語名 Assurance Level、CUE の項目名 `assurance`）を持つ。値は `light`、`standard`、`strict`、`critical` の4つである。レベルは、失敗した場合の影響と回復の難しさで選び、工数や作業の難しさでは選ばない（今の Planning Level の定義を引き継ぐ）。
- **R-C2 正本は1か所**：保証レベルの正本は、その Scope の `requirement.cue` の `assurance` ブロック（値 `level` と理由 `reason`）だけである。GitHub のラベル、親の計画、そのほかの場所には写しを持たない。同じ Scope の `design.cue` と `plan.cue` の型も、この値を使う。
- **R-C3 作る時に必須**：`scope create` と `scope import github` は、保証レベルとその理由の指定を必須にする。既定の値は持たない。SpecDock は、指定を雛形の `requirement.cue` に書き込む。Initiative も同じである。
- **R-C4 一段上で決める**：Issue の保証レベルは、Epic の計画で Issue に切り分けるときに決める。Epic の保証レベルは、Initiative の計画で決める。Initiative は、作るときに決める（多くは standard）。親の計画には、子の Scope の ID を書き、子の保証レベルは書かない。
- **R-C5 途中で変えてよい**：保証レベルは、具体化や作業の途中で、上げても下げてもよい。担当のエージェントが、`level` と `reason` を書き換える。専用のコマンド、変更の履歴の項目、承認の仕組みは置かない。値を変えると、検査が求める項目もそれに合わせて変わる。変えた記録は、カタログの版の履歴に残る。
- **R-C6 起動の前に読める**：`spec-dock scope show <ID> --json` は、`requirement.cue` の保証レベルの値と理由を返す。手元のカタログだけを読み、インターネットは要らない。CUE の文書がない Scope（R-H1）では「未設定」と返す。
- **R-C7 モデルの対応表は持たない**：保証レベルから、モデルと推論を選ぶ対応表は、SpecDock に置かない。利用者のワークフローの policy が、SpecDock の保証レベルを読む（依存の向きは、利用者の設定から SpecDock へ）。

### D. 計画と実行の割り当て

- **R-D1 作業の台帳**：`plan.cue` の手順は、それぞれ状態（例：まだ、作業中、済み）を持つ。エージェントは、作業しながら `plan.cue` を直接書き換えて、手順の追加、変更、状態の更新を行う。手順を操作する専用のコマンドは作らない。
- **R-D2 進み具合を読める形**：手順の順番、依存、状態は、ダッシュボード（epic-00427）が、何をどの順番で進め、今どこまで進んだかを図にできる構造で持つ。
- **R-D3 実行の割り当て（任意）**：`plan.cue` には、任意で `execution` ブロックを書ける。その中に、作業のセッション（何をするか、モデル、推論、選んだ根拠）と、レビュー（役割、どの手順の後か、モデル、推論）を書く。推論は手順ごとではなく、セッションごとに書く。各手順は、どのセッションで行うかを指せる。
- **R-D4 値の意味を持たない**：SpecDock の型は、`execution` のつながり（手順が、あるセッションを指す。レビューが、ある手順を指す）だけを検査する。モデルと推論の名前は文字列として扱い、SpecDock は値の意味を持たない。

### E. 説明資料

- **R-E1 テンプレートとデザインシステム**：SpecDock は、説明資料のテンプレートと、それを描くデザインシステム（今の japanese-explanatory-html の形式。デザインの部品、PlantUML の図の描画と拡大）を配る。新しい Scope の `explanation.html` は、このテンプレートから作る。
- **R-E2 中身は柔軟**：SpecDock が決めるのは、形と仕組みだけで、書く内容は決めない。抽象的な Initiative（バグ修正の集まりなど）なら、短い説明でよい。
- **R-E3 基本は必須**：説明資料は、基本は必ず作る。Epic では、必ず雛形から書き換える。
- **R-E4 説明資料の検査**：説明資料の形の検査（テンプレートの形を保っているか）は、CUE の検査と一緒に、R-B4 の検査のコマンドと `work finish`（R-B7）で行う。既定のブランチの CI では行わない（仕様は既定のブランチになく、canonical には CI を置かないため。epic-00424）。ブラウザーでの描画の検査は、手元で任意に行う。
- **R-E5 書き方のガイド**：説明資料の書き方は、独立したスキルにしない。`spec-dock` スキルから、ガイドへつなぐ。

### F. 描画

- **R-F1 CUE を HTML に描く**：1つの Scope の CUE の文書（要件、設計、計画）を、人が読める HTML に描く部品を、SpecDock が持つ。ダッシュボードのサーバー（epic-00427）が、前もってファイルを作らずに、その場で呼べる形にする。インターネットは要らない。
- **R-F2 図の部品を同梱する**：SpecDock は、PlantUML の図をブラウザーの中で描く部品（`@plantuml/core`）と、コードの色付けの部品（highlight.js）を、版を固定して同梱する。ダッシュボードのサーバーから配れば、インターネットがなくても図を描ける。説明資料のファイルを単独で開いたときは、今と同じく CDN から読み込む。

### G. 道具

- **R-G1 `cue` は必須**：`cue` を、SpecDock を使うのに必須の道具にする。SpecDock は、`cue` がない、または版が古いことを見つけ、入れ方を示して止まる。
- **R-G2 Lean と PlantUML は任意**：Lean と PlantUML の道具は必須にしない。

### H. 既存の文書との共存

- **R-H1 既存の文書はそのまま**：既存の Scope の Markdown の要件・設計・計画は、移さずに残す。SpecDock の既存のコマンドは、Markdown の Scope でも今と同じに動く。保証レベルは「未設定」として扱い、今までどおり `plan.md` の文章で扱う。
- **R-H2 同じリポジトリに両方ある**：1つのリポジトリに、Markdown の Scope と CUE の Scope が並んでいても、検査、表示、`workspace validate`、`workspace doctor`、`work start`、`work finish` が正しく動く。
- **R-H3 版の食い違い**：新しい版の SpecDock を入れたが、リポジトリの配布資産をまだ上げていないとき、`scope create` と `scope import github` は、GitHub に何も書かずに止まり、`installation update` を示す。前の版の SpecDock は、新しい配布資産を入れたリポジトリでも、今までどおり Markdown の Scope を作る。

### I. ガイドとスキル

- **R-I1 書き方のガイド**：CUE の文書の書き方（型、番号、つながり、保証レベル、計画の台帳、実行の割り当て）と、説明資料の書き方を、`docs/authoring` に置く。
- **R-I2 スキル**：`spec-dock` スキルに、CUE の文書と説明資料の扱いを短く整理し、詳しくはガイドへつなぐ。今の Planning Level の記述（Issue Plan Guide など）を、保証レベルに直す。

### J. dogfooding

- **R-J1 spec-dock で使う**：SpecDock の新しい版を spec-dock リポジトリに入れ、新しく作る Scope を CUE で作る。実際の Issue を、CUE の仕様で始めから終わりまで回し、実用に耐えるかを確かめる。見つかった問題は、型とガイドの改善として返す。

## スコープ

### 対象

- 上の要件を満たす SpecDock の変更（CUE の型と雛形、検査のコマンド、`scope create`・`scope import github`・`scope show` の変更、CUE を HTML に描く部品、図の部品の同梱、説明資料のテンプレートとデザインシステム、ガイド、スキル、配布資産）。
- spec-dock リポジトリでの導入と、実際の Issue での確認（R-J1）。

### 対象外

- HTML のダッシュボードそのもの（epic-00427）。ダッシュボードでの `.md` と `.cue` の表示、報告の HTML の表示、進み具合の図、Artifact の一覧、Tailscale での公開は epic-00427 で行う。
- Orca との連携（epic-00471）。
- 既存の Markdown の文書の CUE への移行。
- 保証レベルから、モデルと推論を選ぶ対応表（利用者の policy が持つ）。利用者の policy の書き換え（利用者が行う）。
- GitHub のラベルでの保証レベルの表示。
- 利用者のほかの4つのリポジトリ（company-os、input-devices、housing-lifecycle、退去費用プロダクト）への導入。利用者の判断で `installation update` する（2026-10-31 の決定）。
- Lean と PlantUML の道具の導入。
- この Epic とその Issue 自身の仕様の CUE 化（R-H1 のとおり、Markdown で書く）。

### Issue へ渡す境界（候補）

計画書（`plan.md`）で確定する。要件の段階での候補は、次のとおり。

1. CUE の型と雛形（要件・設計・計画、3つの Scope の種類、保証レベルによる切り替え、型の版）。この Epic の要（利用者の方針。2026-10-30）。
2. 検査のコマンド（つながりの検査、`cue` の確認、説明資料の形の検査）。
3. `scope create`・`scope import github` の一式の配置と保証レベルの必須化、`scope show` の保証レベル。
4. 説明資料のテンプレートとデザインシステム、図の部品の同梱。
5. CUE を HTML に描く部品。
6. ガイドとスキル。
7. spec-dock での導入と、実際の Issue での確認。

## 失敗・境界条件

- **`cue` がない、または古い**：CUE を扱うコマンドは、何も書かずに止まり、入れ方を示す（R-G1）。
- **CUE の文書の文法の誤り**：検査は、ファイルと位置を示して失敗する。`scope show --json` は、保証レベルを読めないことを示し、構造の情報は今までどおり返す。
- **保証レベルがない、または4つ以外の値**：検査は誤りにする。`scope show --json` は「読めない」と示す。
- **保証レベルを下げた**：下げたレベルの型で検査する。求める項目が減るだけで、誤りにはしない。
- **保証レベルを上げた**：上げたレベルで必須の項目がないと、検査が誤りを示す。エージェントは、その項目を書き足す。
- **前の版の型で書いた Scope**：その版の型で検査する（R-B5）。SpecDock が、その版の型を持っていないほど古いときは、理由を示して止まる。
- **Markdown と CUE の両方がある Scope**：どちらが正本かを決められないので、検査は止まり、片方にするよう示す。
- **`work finish` で検査が誤りになった**：終わらずに止まり、誤りと直し方を示す。直してから、もう一度 `work finish` を実行する（R-B7）。
- **説明資料がない、または雛形のまま**：検査で知らせる。Epic では誤り、Initiative と Issue では警告にする。
- **インターネットがない**：検査、`scope show`、CUE の描画は動く。説明資料のファイルを単独で開いたときの図だけは描けない（ダッシュボードの中では描ける。R-F2）。
- **同梱した図の部品の版を上げる**：上げる前に、SpecDock のテストで、図が描けることを確かめる。`@plantuml/core` は 2026年5月に最初の版が出た新しい部品である。

## 受け入れ条件

- **AC-01**：`scope create` で、保証レベルと理由を指定して Issue を作ると、直下に5つの雛形のファイルができ、`requirement.cue` に指定した値と理由がある。指定しないと、何も作らずに止まる。
- **AC-02**：作った直後に、`scope show <ID> --json` が、インターネットなしで、保証レベルの値と理由を返す。Markdown の Scope では「未設定」を返す。
- **AC-03**：R-B3 の表の各行について、その検査に違反する CUE の文書を、必須のレベルでは誤りに、任意のレベルでは誤りにしない（テストで、表の全ての組を確かめる）。
- **AC-04**：`requirement.cue` の保証レベルを standard から strict に書き換えると、strict で必須の項目がない文書が、検査で誤りになる。項目を書き足すと通る。
- **AC-05**：検査は、インターネットなしで動き、誤りごとに、ファイル、項目、直し方を示す。JSON でも出せる。
- **AC-06**：`plan.cue` の `execution` で、存在しないセッションを指す手順や、存在しない手順を指すレビューが、検査で誤りになる。モデルや推論の名前は、どんな文字列でも誤りにならない。
- **AC-07**：型の版を上げた後も、前の版で書いた Scope の検査が、前と同じ結果になる。
- **AC-08**：リポジトリの側で足した型の制約が、SpecDock の検査に加わる。
- **AC-09**：CUE を HTML に描く部品が、インターネットなしで、1つの Scope の要件・設計・計画を HTML に描く。ダッシュボードのサーバーから呼べる形の、文書化された入口を持つ。
- **AC-10**：同梱した図の部品を手元から配ったとき、インターネットのない状態で、説明資料の PlantUML の図が描ける。
- **AC-11**：新しい Scope の `explanation.html` が、ブラウザーでの描画の検査に通る。
- **AC-12**：Markdown の Scope と CUE の Scope が並ぶリポジトリで、今の回帰テストがすべて通る。同じリポジトリで、`workspace validate` と `workspace doctor` が、CUE の Scope を文書の欠落の誤りにしない。
- **AC-13**：設計書を渡されていない新しいエージェントが、`spec-dock` スキルとガイドだけを頼りに、CUE の要件・設計・計画を書き、検査に通し、計画を更新できる（白紙のエージェントでの試行で確かめる）。
- **AC-14**：spec-dock リポジトリで、少なくとも1つの実際の Issue を、CUE の仕様で作ってから閉じるまで回した記録がある（R-J1）。
- **AC-15**：`make lint` と `uv run pytest` が通る。
- **AC-16**：CUE の Scope で、検査に誤りが残っていると、`work finish` は終わらずに誤りを示す。直すと終わる。Markdown の Scope では、今と同じに終わる。
- **AC-17**：説明資料がない Scope と、雛形のままの説明資料を持つ Scope を、検査が知らせる。雛形のままのとき、Epic では誤り、Initiative と Issue では警告になる。形を壊した説明資料（Markdown を書く場所がない、デザインシステムを読む指定がない）は誤りになる。
- **AC-18**：新しい版の SpecDock で、配布資産を上げていないリポジトリに `scope create` を実行すると、GitHub に何も書かずに止まり、`installation update` を示す。前の版の SpecDock は、新しい配布資産を入れたリポジトリでも、Markdown の Scope を作る。

## 制約・前提

- Linux と macOS、Python 3.10 以上。Windows には対応しない。
- `cue` は、利用者が自分で入れる（今のPCの PATH には、まだない。2026-10-30 確認）。`java` は前提にしない。
- 今の CLI の契約（直接の選択、StartLock、Artifact の命名、失敗したら止まる境界、読むだけのコマンドは書かない、canonical モードの規則）を壊さない。
- `scope create` と `scope import github` の保証レベルの必須化は、配られる CLI の契約の変更である。
- SpecDock は、利用者のツールの設定と、利用者の policy を書き換えない。
- dogfooding の規則：提供側のソース（`src/spec_dock/`）を先に変え、配布されたものを `spec-dock/` で確かめる。
- 人がPRをマージする関門を残す。
- 用語の衝突：SpecDock には、過去の「Assurance」（`.assurance.json`、旧 Profile）の証跡が残っている（`docs/authoring/historical.md`）。新しい保証レベルは、それとは別のものとして、ガイドで区別する。

## エージェントが決めたこと

利用者から任された細部。異議があれば変える。

- 説明資料の置き場は、各 Scope の直下の `explanation.html` の1つにする。ダッシュボードは、この名前で見分ける（epic-00427 の依頼への答え）。
- 保証レベルの理由（`reason`）も、作る時に必須にする。親の計画に理由を書かない代わりに、値と一緒に残すため。
- Markdown と CUE の両方がある Scope は、検査を止める。正本が2つになるため。
- 説明資料が雛形のままのとき、Epic では誤り、Initiative と Issue では警告にする（「Epic は必ず作る」に合わせた）。
- 型の版を CUE の文書に持たせる（R-B5）。型を磨き続ける方針と、既存の Scope を壊さないことを両立するため。
- リポジトリの側で型を足せるようにする（R-B6）。`execution` を必須にしたいなど、利用者のワークフローの決まりを、SpecDock に持ち込まずに表せるため。
- 計画の手順の状態の名前と、`execution` の項目の名前は、設計で決める。
