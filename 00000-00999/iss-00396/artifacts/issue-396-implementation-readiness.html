1. 目的とEpic全体の位置づけ

Epic #384は、provider testの重複と実行コストを減らしながら、テスト失敗を弱めずに最終qualificationを証明します。実施順はIssue #392、#395、#396です。#396は、candidateを一度だけbuildし、同じwheelとsdistを各roleで再利用する最終Provider Gateへの切替を担当します。

前任者からの報告時点では、#395を閉じただけでB1/B2が未実施だったため、依存グラフ上のreadyとEpic計画上の開始条件がずれていました。その後、Epic Planとentry receiptで確認したところ、B1/B2は#395のpost-merge exact SHA fd5df1d64b5d7ebf7bd4b41bb35fd8760d17e65d、tree 37eabc1aa250838dcd9f61d627309b0ff27e0db7で別途実行され、#396のentry evidenceとして記録されています。したがって、#396の入口条件は満たされています。

B1/B2の完了は、#396やEpic全体の完了ではありません。 B1/B2は#395の受入証拠です。#396のreplacement gate、required-context切替、post-merge B3、Epic main受入はこれからの別ゲートです。B2の古いshard/skip結果をB3の証拠に流用しません。

3. 候補の識別と一回のrole graph

event resolverはGitHub eventごとにsourceを一意に決めます。pull requestではPR head SHAとsource repository、workflow dispatchでは必須のinputs.source_sha、merge queueではmerge-group SHAを使います。PRのraw GITHUB_SHAはmerge commitを表すため、PR head candidateの代わりに使いません。

各workflow attemptは自分のSourceIdentityV1を作成します。同じattemptの全roleはproducer jobが保存した同じidentity bytesを使います。後続attemptではrun IDとattemptが変わりますが、source SHA/treeは元candidate manifestに一致させます。後続attemptで同じcandidateを再buildすることはありません。

7. 失敗時の動作

      

        
検出した状態動作続行してはいけない理由

        
          
repository / source SHA / tree / run attemptが一致しないcandidateまたはattemptをreject異なるsourceの結果を同一候補へ混ぜないためです。

          
artifact欠落、重複producer、hash/実bytes不一致build fallbackせずreject同じsourceの再buildは「一度だけ」の証明を壊すためです。

          
owner欠落、重複、未知node、policy skipcollection/attemptをreject検証母集団とowner集合が確定しないためです。

          
runner環境や有効quotaを証明できないadmissionをreject別環境の結果を性能qualificationに使えないためです。

          
pytest root終了後にdescendantが残る全processのreapまで計測し、未回収ならrejectwall/CPU値の測定窓が閉じていないためです。

          
started runの結果/evidenceが欠落・cancel・interruptionhistory memberとして残し、成功で置換しない欠測を成功扱いにできないためです。

          
new required contextのREDがmergeをblockしないsettings before-stateへ戻して停止no-gap切替の安全性が証明できないためです。

          
old context removal後のreadbackがU + newでないold emitter/providerを削除せず停止必須checkの欠落や範囲変更を隠さないためです。

        
      

      
すべてのstopはStopReturnV1だけで記録します。PlanやHandoffに別の停止JSON形式はありません。PacketもExecutionPacketV1だけを使い、一回に一checkpointだけを認可します。

    


    

      
8. 実装者がたどる場所と確認方法

      
Issueの正本はこのrepository内のRequirement、Design、Planです。人間向けHTMLは説明用で、closed schemaや親qualification契約を置き換えません。実装開始前に最新のStrict reviewがpassであること、Issue body projectionのreadback、ユーザーの明示dispatch、同時writerがいないことを確認します。

      

        
読む場所用途

        
          
requirement.md目的、境界、親とのauthority、受入条件。

          
design.md各moduleの責務、identity/hash graph、role ownership、transition seam。

          
plan.mdP00–P22の順序、具体的なtest commands、evidence、stop条件。

          
Luna Max handoff実装担当のpacket、path envelope、CLI契約、戻り値。

          
closed schemaすべてのruntime/evidence/packet wire shape。

          
role ownership2,214 nodeの実装前owner baseline。

          
B1/B2 entry receipt#395から引き継いだentry evidenceとその非主張。

          
Strict review remediation analysis初回P1指摘の証拠照合と修正理由。

        
      

      
中心となる実装先はscripts/quality/provider_gate/、生成policyはscripts/maintenance/generate_provider_qualification_policy.py、新規unit testsはtests/unit/provider_gate/です。Provider-side scaffold、lifecycle Product source、installed consumer workflowはprotected/no-touch scopeです。

      
Planの最終確認には、schema validation、provider-gate unit/integration tests、provider lifecycle / distribution non-regression、make lint、ordinary pytest、SpecDock validate、consumer-zero scan、retained workflow byte comparisonを含みます。各checkpointの実行結果を別々のEvidenceIndexへ保存します。

      
GitHubのeventでsource SHAが変わる点はGitHub Actions公式event仕様に従います。PR eventのGITHUB_SHAはmerge branch commit、merge_groupはmerge-group SHA、dispatchではrequired source_sha inputを使います。
