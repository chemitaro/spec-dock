# epic-00424 Centralize Specs On Canonical Branch And GitHub Issues — 要件定義

詳細: [Requirement Guide](../../../docs/authoring/requirement.md)

表示名：仕様の正本を `spec-dock/canonical` ブランチと GitHub Issue に集約する

## 目的

仕様の最新の状態を、どのPC・どのworktree・どのエージェントからも、同じ1か所で読み書きできるようにする。その仕組みを SpecDock に加え、spec-dock 自身で使い始める（dogfooding）。

- 仕様の内容（要件・設計・計画・報告・Artifact）の正本を、コードと履歴を共有しない1本のブランチ `spec-dock/canonical` に置く。
- 仕様の構造（番号・種類・親子・依存・状態・題名）の正本を GitHub Issue に置き、`.meta.json` を廃止する。
- 保存と同期を、人やエージェントが意識しない SpecDock の定期の仕組みに任せる。
- 既定のブランチ（main など）とその系列には、仕様を一切置かない。

ほかのプロダクトへの導入は、この Epic に含めない。各プロジェクトで、それぞれ進める。

## 背景

### 解く問題

今は、仕様のツリー `spec-dock/initiatives/` を、既定のブランチとすべての作業ブランチが追跡している。そのため、次のことが起きている。

- 仕様の最新の状態が、worktreeとブランチごとに分かれ、中央で全体を把握できない。
- ほかのworktreeの書きかけや、マージ前の更新が見えない。反映にはPRのマージが必要になる。
- ブランチを消すと、そのブランチにしかない仕様が失われる（孤児のScope）。
- 構造の情報が `.meta.json` にだけあり、GitHub と食い違っている。GitHub には親子も依存も登録されていない。spec-dock では、`.meta.json` の題名が GitHub の題名と36件食い違う。

### 利用の実態（このPC、2026-10-25 時点）

- 仕様の編集は286回。そのうち263回が、Orca や Codex の作業用worktreeの通常のセッションによるもので、mainのチェックアウトからは23回、隔離されていないサブエージェントからは3回だった。
- Claude Code の隔離セッション（`--worktree`）は、一度も使われていない。

### 関係者

- 利用者（人）：仕様を確認し、判断し、PRをマージする。HTMLの説明資料で議論する。
- エージェント（Claude Code、Codex。Orca から起動されることが多い）：仕様を読み書きし、コードを実装する。
- SpecDock を使うリポジトリ：この Epic で移行するのは spec-dock だけ。ほかの利用者の個人のプロジェクト（退去費用プロダクト、housing-lifecycle、company-os）は、後で各プロジェクトで移行する。SpecDock の仕組みは、それらでもそのまま使えるようにする。
- 複数のPC：同じリポジトリを、別々のPCで同時に扱う。

### 使いやすさの約束

利用者の方針（2026-10-25）は、複雑にしすぎず、簡単に使え、エージェントが迷わず、複雑な設定が要らないことである。これを次の5つの約束にする。以下の要件は、すべてこの約束に従う。

1. **仕様はいつもの場所にある**：仕様は今と同じ `spec-dock/initiatives/` にあり、普通のファイルとして読み書きする。仕様のために Git を操作することはない。
2. **用意はコマンド1つ**：`spec-dock canonical link` を実行すれば使える。何度実行しても同じ結果になる。
3. **自動で動くのは定期の同期だけ**：保存、取り込み、push は、PCごとの定期の同期が行う。Claude Code や Codex のフックには頼らない。
4. **ツールの設定を書き換えない**：要るのは、作業用のworktreeから仕様に触れるための、ツールごとに1行の設定だけ。SpecDock は、その1行を正確に示すだけにする。
5. **おかしいときは止まり、次の1手を示す**：推測で直さず、実行すべきコマンドか、足すべき設定を示す。

### 前提とする検証

検証した事実は、Artifact [検証済みのGitとGitHubの挙動](artifacts/20261025t080353z-research-verified-git-github-behaviors.md) にまとめた。先行の分析と設計の草案（v0.8）は、同じ `artifacts/` にある3つのHTML資料で、証拠として扱う。

## 観測可能な要件

### A. 正本の置き場

- **R-A1 内容の正本**：仕様の内容は、`spec-dock/canonical` ブランチだけに置く。このブランチは、既定のブランチと共通の祖先を持たず、仕様のツリーと、SpecDock が管理する少数のファイル（無視の設定、正本であることを示す README、形式の版）だけを含む。
- **R-A2 構造の正本**：番号、種類、親子、依存、状態、題名は、GitHub Issue だけに置く。親子は sub-issue、依存は blocked by、種類はラベル（`spec-dock:initiative`、`spec-dock:epic`、`spec-dock:issue`）、識別名（slug）は本文の印で表す。種類のラベルのない Issue は、Scope として扱わない。`.meta.json` は廃止する。
- **R-A3 入れ子は写し**：canonical のディレクトリの入れ子は、GitHub の親子を見やすく写したものとする。両者がずれたときは GitHub に合わせる。人やエージェントが手でディレクトリを動かしても、正本の変更とは見なさない。
- **R-A4 既定のブランチに仕様を置かない**：既定のブランチと、そこへ入るPRのツリーには、`spec-dock/initiatives` と `spec-dock/.canonical` の下のパスと `.meta.json` が1つもない（ファイル、リンク、gitlink を含む）。canonical と既定のブランチの間では、同期も、コピーも、マージもしない。
- **R-A5 版の違う SpecDock から壊さない**：移行したリポジトリに、移行前の版の SpecDock が書き込もうとしても、書き込む前に止まる。canonical は形式の版を持ち、SpecDock は自分より新しい形式には書き込まない。

### B. 用意と診断

- **R-B1 カタログ**：クローンごとに1つ、mainのチェックアウトの `spec-dock/.canonical/` に canonical のworktree（以下、カタログ）がある。誤って消されないよう保護され、Git では追跡も表示もされない。mainのチェックアウトがない構成（bare）は対象外で、理由を示して止まる。
- **R-B2 リンク**：各チェックアウトの `spec-dock/initiatives` は、カタログを直接指すリンクにする。mainのチェックアウトでは相対、作業用のworktreeでは絶対のパスを使う。リンクのリンクは使わない。リンクとカタログは Git で管理しない、そのPCの作業環境とする。
- **R-B3 用意のコマンド**：`spec-dock canonical link` は、同じクローンのどのチェックアウトから実行しても、そのクローンのmainのチェックアウトとカタログを見つけ、次を済ませる。何度実行しても結果は同じで、行ったことと、利用者に残る作業（R-B6 の設定）を表示する。
  - カタログがなければ、GitHub の canonical から作り、保護する。
  - Git の除外の設定を足す。
  - mainのチェックアウトと、実行したチェックアウトに、リンクを張る。
  - このPCの定期の同期に、カタログを登録する（定期の実行がなければ作る）。
  - リンクを置く場所に実体のファイルやディレクトリがあるとき（移行前のコミットなど）は、置き換えずに止まり、理由を示す。
- **R-B4 呼ばれる場所**：SpecDock の `worktree create` と `work start` は、中で同じ処理を行う。Orca、Codex、Claude Code、`git worktree add` で作ったworktreeでは、`spec-dock canonical link` を1回実行する。プロジェクトの `make init` などへ組み込むかどうかは、各プロジェクトが必要に応じて決め、SpecDock はそれを前提にしない。
- **R-B5 足りないときの案内**：仕様を使う SpecDock のコマンドは、リンクやカタログがない、または壊れているとき、自分では直さずに止まり、実行すべきコマンドを示す。読むだけのコマンドは、何も書き込まない。
- **R-B6 ツールの設定**：作業用のworktreeから仕様に触れるには、ツールごとに1行の設定が要る（Claude Code の既定の権限モードと acceptEdits では `additionalDirectories`、Codex のサンドボックスでは `writable_roots` に、カタログのパスを加える）。SpecDock は、足りないことを見つけ、そのクローンでの正確な1行を示す。ツールの設定は書き換えない。mainのチェックアウトの中で動くセッションは、設定なしで使える。Claude Code の隔離セッション（`--worktree`）では、仕様を読むだけにする。
- **R-B7 状態と診断**：状態を表示するコマンドが、カタログ、保護、リンク、除外の設定、このプロセスからの読み書きの可否、未保存・未push・保留・競合、最後に成功した同期の時刻、形式の版、定期の実行の状態を示す。問題ごとに、次の1手を1つ示す。
- **R-B8 取り外し**：未保存と未pushの変更がないことを確かめてから、リンク、カタログ、除外の設定、定期の同期の登録を外せる。破壊的な操作なので、対象と結果を明示した指示がいる。

### C. 保存と同期

- **R-C1 定期の同期**：PCのユーザーごとに1つの定期の実行が、登録されたすべてのカタログについて、変更を保存し、GitHub と統合して push する。誰が書いた変更かは問わない。既定の周期は60秒で、変更のない周期はコミットしない。保存の経路はこの1本だけとする。カタログのコミットでは、リポジトリのコード用のフック（`pre-commit` など）を動かさない。
- **R-C2 書きかけの扱い**：30秒以上変わっていないファイルを保存する。変わり続けるファイルも、5分たてば保存する。
- **R-C3 先着優先**：push の前に必ず取り込み、後から push する側が差分を解消する。同じファイルが競合したときは、先に push された版を元の名前に残し、後から push する側の版を `<名前>.conflict-<PC名>-<時刻>.<拡張子>` として隣に保存する。変更と削除がぶつかったときは、変更を残す。カタログに競合のマーカーやマージの途中の状態を残さず、rebase と強制 push は使わない。
- **R-C4 保留**：大量の削除、秘密情報らしいもの、大きすぎるファイルは、自動では保存しない。保留して知らせる。SpecDock のコマンドが行った削除は保留しない。
- **R-C5 リモートの書き換えを受け入れない**：GitHub の canonical が、最後に確認した版の子孫でなくなったら（強制 push や削除）、同期は取り込まずに止まり、知らせる。
- **R-C6 保存の確認**：push していないコミットが10分を超えると、状態の表示で警告する。`work finish` は、その Scope の仕様の変更が push されたことを確かめてから終わる。確かめられないときは、理由を示して止まる。

### D. 同時に動く操作

- **R-D1 PCの中の排他**：定期の同期と、カタログに書く SpecDock のコマンドは、互いの途中の状態を保存しない。1つのコマンドの変更（ディレクトリの移動とリンクの書き換えなど）は、1つの単位として保存される。排他の中ではネットワークを使わず、ほかの操作を長く待たせない。SpecDock のコマンドは自分ではコミットしないので、サンドボックスで動くエージェントから実行しても、同じ結果になる。
- **R-D2 PCの間**：PCどうしには排他を置かない。調整は R-C3 の先着優先だけで行う。

### E. 名前

- **R-E1 識別**：ID と slug は、英小文字・数字・ハイフンだけにする。ディレクトリ名、ブランチ名、URL に使い、作成したときに固定する。
- **R-E2 表示**：題名（GitHub の Issue の題名）は、日本語を含む任意の言語でよく、いつでも変えられる。題名を変えても、slug、ディレクトリ名、ブランチ名は変わらない。
- **R-E3 日本語の題名で作る**：Scope の作成で、日本語の題名を受け付ける（今の CLI は英数字しか受け付けない）。題名に英数字以外の文字が含まれるときは、slug の指定を必須にする。
- **R-E4 表示に使う**：ダッシュボード（`spec-dock/dashboard.md`）と CLI の表示は、GitHub の題名を使う。

### F. 既定のブランチの検査

- **R-F1 検査のコマンド**：SpecDock の1つのコマンドが、チェックアウトの追跡されたツリーを調べる。R-A4 のパスがないこと、無視の設定と SpecDock の宣言がそろっていること、SpecDock の配布物が壊れていないことを確かめる。カタログ、GitHub への書き込み、秘密の情報がなくても動き、CIでそのまま使える。
- **R-F2 独立のワークフロー**：SpecDock は、R-F1 を実行する独立した GitHub Actions のワークフローの見本を配る。PRと、既定のブランチへの push で動く。ワークフローの定義は短く保ち、検査の中身は SpecDock のパッケージが持つ。SpecDock の版を上げても、ワークフローを書き換えなくてよい。各プロダクトへの組み込みは、導入するときに各プロジェクトで行う。
- **R-F3 マージの条件**：spec-dock では、このワークフローを必須の検査にし、失敗したPRはマージできないようにする。

### G. 移行

- **R-G1 使い捨てのスクリプト**：`.meta.json` から GitHub への構造の登録、検証、canonical の作成、既定のブランチからの仕様の切り離しは、直接実行するスクリプトで行う。SpecDock の CLI とパッケージには入れず、保守もしない。利用者の個人のプロジェクトの移行が終わったら捨てる。
- **R-G2 安全に止めて再開できる**：スクリプトは、既定では予定を表示するだけで、何も書き込まない。何度実行しても同じ結果になり、途中で止まっても続きから再開できる。GitHub には足すだけで消さず、取り消しの一覧を残す。GitHub の書き込みの制限を超えない速さで進む。
- **R-G3 先に登録できる**：GitHub への登録は、切り替えより前に済ませられる。登録しても、今の CLI での運用は壊れない。
- **R-G4 データの異常を見つける**：予定の表示は、循環する依存、種類の規則の違反、閉じた親の下の開いた子、ID と番号の不一致（`init-local-00002` は #39、`init-local-00003` は #31）、GitHub との題名の食い違いを一覧にする。
- **R-G5 移行前のブランチ**：移行前に作ったブランチの仕様は、マージの前に canonical へ取り込める。取り込んだ後、ブランチから仕様のツリーを外し、PRを仕様を含まずにマージできる。
- **R-G6 手順書**：ほかのプロジェクトを移行するときの手順を、スクリプトの横に短く書く。

### H. エージェント向けの規則

- **R-H1 短い規則**：配布するスキル（`.agents/skills/spec-dock/SKILL.md`）と AGENTS.md に、エージェントが守る規則を1つの短い節にまとめる。設計書を読まなくても、その節だけで仕様を読み書きし、検索し、競合を解消できる。節には、次のことを書く。
  - 仕様は `spec-dock/initiatives/` にあり、普通に読み書きする。仕様は Git で扱わない（add、commit、stash、reset をしない）。保存と共有は自動で行われる。
  - 仕様が見えないときは `spec-dock canonical link` を実行する。読み書きを拒否されたときは、状態の表示が示す1行の設定を利用者に伝える。
  - 検索では、パスを明示する（`rg 語 spec-dock/initiatives/`）。
  - 構造（作成、親子、依存、状態、題名）は、SpecDock のコマンドだけで変える。
  - `*.conflict-*` のファイルがあれば、中身を元のファイルに統合し、消す。
  - Claude Code の隔離セッションでは、仕様を読むだけにする。
  - 作業を終えるときは `work finish` を使う。
- **R-H2 次の1手を示す**：SpecDock のエラーの文言は、次に実行すべきコマンドか、足すべき設定を含む。

## スコープ

### 対象

- 上の要件を満たす SpecDock の変更（CLI、配布資産、ワークフローの見本、利用者向けの文書、エージェント向けの規則）。
- 移行のスクリプトと手順書（パッケージには入れない）。
- spec-dock リポジトリでの移行と、新しい仕組みでの運用の開始（dogfooding）。

### 対象外

- ほかのプロダクト（退去費用プロダクト、housing-lifecycle、company-os）の移行。各プロジェクトで、R-G6 の手順書に従って進める。
- 各プロジェクトの `make init` などへの組み込み。
- Claude Code と Codex のフックと設定の変更。
- 第三者のリポジトリの移行の支援。移行のスクリプトは、利用者の個人のプロジェクトだけを対象にする。
- Codex のクラウドからの書き込み。Claude Code の隔離セッションからの仕様の書き込み。
- mainのチェックアウトがない構成（bare）、Windows。
- PCをまたぐ排他。
- canonical と既定のブランチの間の同期、GitHub Actions による canonical への書き込み、canonical に置くCIの定義。
- 今ある英語の題名の変更。

### Issue へ渡す境界（候補）

計画書で確定する。候補は次のとおり。

1. GitHub の構造の読み書き（sub-issue、blocked by、ラベル、本文の印）と、`.meta.json` に頼らない読み取り。
2. 名前（日本語の題名、slug、テンプレート、ダッシュボード）。
3. カタログとリンク（`spec-dock canonical link`、状態と診断、取り外し）。
4. 定期の同期（先着優先、保留、登録、`work finish` での確認）。
5. 排他と、SpecDock のコマンドの書き方の統一。
6. 既定のブランチの検査（コマンドとワークフローの見本）。
7. エージェント向けの規則と、利用者向けの文書。
8. 移行のスクリプトと手順書。
9. spec-dock での移行と運用の開始。

## 失敗・境界条件

- **mainで移行前のコミットへ移る**：リンクが実体のディレクトリに置き換わる。カタログは残る。戻ったときに、`spec-dock canonical link` がリンクを作り直す。
- **`git clean -ffdx`**：カタログが消える。保存済みのコミットは `.git` に残る。失うのは、最後の保存の後の編集だけ。`spec-dock canonical link` が作り直す。
- **mainのチェックアウトの移動や改名**：worktree の登録と、作業用のworktreeの絶対パスのリンクが切れる。状態の表示が直し方を示し、`spec-dock canonical link` が張り直す。
- **作業用のworktreeの削除**：リンクだけが消え、カタログは残る（確認済み）。
- **外付けのボリュームが外れている**：定期の同期は何も変えずに失敗し、記録だけを残す。
- **同じPCに同じリポジトリのクローンが複数ある**：クローンごとにカタログがあり、互いには GitHub を通して同期する。
- **ネットワークの断絶や認証の失敗**：コミットはローカルに積まれ、つながったときに push される。長く続いたら警告する。
- **同じファイルの同時編集**：R-C3 で解決し、編集は失われない。後から push した側で作業中のエージェントには、文書が先着の版に変わって見える。
- **ツールの設定が足りない**：Claude Code の既定の権限モードでは、作業用のworktreeからリンク経由の読み取りも書き込みも、作業ディレクトリの外として拒否される（確認済み）。Codex のサンドボックスでは、書き込みが拒否される（確認済み）。どちらも R-B6 の1行で解決する。
- **サンドボックスからの `.git` への書き込み**：Codex のサンドボックスは、mainの `.git` に書けない。SpecDock のコマンドはコミットしないので影響しない（R-D1）。
- **コード用のフック**：リポジトリの `pre-commit` などは、カタログのコミットでは動かさない（R-C1）。
- **非公開で無料のプランのリポジトリ**：ワークフローは動いて失敗を表示するが、必須の検査にはできない（ルールセットとブランチの保護に、Pro 以上のプランか公開が要る）。ほかのプロジェクトを移行するときに、各プロジェクトで扱う。spec-dock は公開なので、必須にできる。
- **GitHub の canonical の削除や強制 push**：GitHub 側では防げない。R-C5 で検出する。
- **GitHub の題名の手作業の変更**：表示が変わるだけで、識別名は変わらない。

## 受け入れ条件

- **AC-01**：移行後の spec-dock の既定のブランチのツリーに、`spec-dock/initiatives` と `spec-dock/.canonical` の下のパスと `.meta.json` が1つもない。
- **AC-02**：作業用のworktreeで書いた仕様が、同じPCの別のworktreeから保存の前にも読め、別のクローン（別のPCの代わり）からはおよそ2分以内に読める。
- **AC-03**：2つのクローンで同じファイルを同時に編集しても、両方の内容が残り（片方は別名ファイル）、どの作業ツリーにも競合のマーカーが残らない。
- **AC-04**：移行の前後で、spec-dock の全Scopeの番号、種類、親子、依存が一致する。移行後、`.meta.json` が1つも残っていない。
- **AC-05**：移行前のブランチの仕様を取り込んだ後、そのPRが仕様を含まずにマージできる。
- **AC-06**：新しいクローンと、ほかのツールで作ったworktreeで、`spec-dock canonical link` を1回実行した後に、仕様を読み書きできる。SpecDock の `worktree create` で作ったworktreeでは、追加のコマンドなしで読み書きできる。
- **AC-07**：利用者が足す設定は、Claude Code と Codex のそれぞれ1行だけで、その内容を SpecDock が正確に示す。mainのチェックアウトでは設定なしで使える。
- **AC-08**：`git clean -ffdx`、mainのチェックアウトの移動、移行前のコミットへの checkout の後、状態の表示が原因と次の1手を示し、`spec-dock canonical link` で元に戻る。
- **AC-09**：日本語の題名で Scope を作れる。ディレクトリ名とブランチ名は英語の slug になり、ダッシュボードには日本語の題名が出る。
- **AC-10**：大量の削除が、自動では push されない。
- **AC-11**：canonical が強制 push で書き換えられたとき、各クローンの同期は取り込まずに止まり、知らせる。
- **AC-12**：spec-dock で、既定のブランチへ仕様を入れるPRは、SpecDock の検査が失敗し、マージできない。
- **AC-13**：`work finish` は、その Scope の仕様の変更が push されるまで終わらない。
- **AC-14**：設計書を渡されていない新しいエージェントが、R-H1 の節だけを頼りに、仕様の読み書き、検索、別名ファイルの統合を迷わずにできる（白紙のエージェントでの試行で確かめる）。

## 制約・前提

- Linux と macOS、Python 3.10 以上。Git は `merge-tree --write-tree` が使える版（2.38 以上）が要る。手元は 2.54.0。
- GitHub の個人アカウント。Issue types は使えない。spec-dock は公開なので、ルールセットで必須の検査を設定できる。エージェントのトークンにはブランチの保護を読む権限がないため、必須の検査の設定は利用者が GitHub の画面で行う。
- GitHub の書き込みの制限は、目安で毎分80回、毎時500回。
- 人がPRをマージする関門を残す。エージェントは、マージできる状態のPRで止まる。
- 今の CLI の契約（直接の選択、StartLock、Artifact の命名、失敗したら止まる境界、読むだけのコマンドは書かない）を壊さない。
- SpecDock は、利用者のツールの設定（`~/.claude/settings.json`、`~/.codex/config.toml` など）を書き換えない。定期の実行は SpecDock 自身のもので、`spec-dock canonical link` だけが作り、取り外しの操作だけが消す。
- dogfooding の規則：提供側のソース（`src/spec_dock/`）を先に変え、配布されたものを `spec-dock/` で確かめる。

## エージェントが決めたこと

利用者から任された細部。異議があれば変える。

- slug を、GitHub の本文の末尾に、画面に出ないHTMLコメントの印として持つ。GitHub だけからディレクトリを作り直せるようにするため。
- テンプレートから `タイトル:` の写しを外す。題名の正本を GitHub だけにするため。
- ツールの設定は示すだけにし、自動で足すオプションも作らない（約束4）。
- 定期の実行は、`spec-dock canonical link` が登録する。SpecDock 自身の仕組みで、ツールの設定ではないため。
- 仕様を読むだけのコマンドは、足りなくても自分では直さず、次の1手を示す。今の CLI の「読むだけのコマンドは書かない」契約を守るため。
- マージの後に Issue を立てる見張りは作らない。同じワークフローを既定のブランチへの push でも動かし、失敗を表示すれば足りるため。
- 移行前の版の SpecDock を止めるには、今あるワークスペースの宣言（`spec-dock/workspace.json`）の版を上げる仕組みを使う。新しい仕組みを足さないため。形式の版を更新するコマンドは、形式を変える必要が出たときに作る。
- canonical にCIの定義を置かない。
- 切り替えは、次の順で、1回の作業として行う。待ちの大半は、人によるPRのマージで、全体は数十分を見込む。
  1. GitHub への登録と検証を、切り替えより前に済ませる（今の運用は止めない）。
  2. 切り替えを始めたら、終わるまで、ほかのエージェントで仕様を編集しない。
  3. canonical を作って push し、既定のブランチから仕様を外すPRを作る。
  4. 人がマージした後、各チェックアウトで `spec-dock canonical link` を実行する。
  5. 作業用のworktreeに残った仕様の変更は、R-G5 の取り込みで canonical に入れる。
- この Epic は、親の `init-local-00003`（#31）が別の題名で閉じていたため、新しい Initiative `init-00423` の下に作った。
