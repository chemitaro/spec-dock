# epic-00424 Centralize Specs On Canonical Branch And GitHub Issues — 要件定義

詳細: [Requirement Guide](../../../docs/authoring/requirement.md)

表示名：仕様の正本を `spec-dock/canonical` ブランチと GitHub Issue に集約する

## 目的

仕様の最新の状態を、どのPC・どのworktree・どのエージェントからも、同じ1か所で読み書きできるようにする。

- 仕様の内容（要件・設計・計画・報告・Artifact）の正本を、コードと履歴を共有しない1本のブランチ `spec-dock/canonical` に置く。
- 仕様の構造（番号・種類・親子・依存・状態・題名）の正本を GitHub Issue に置き、`.meta.json` を廃止する。
- 保存と同期を、人やエージェントが意識しない定期の仕組みに任せる。
- 既定のブランチ（main など）とその系列には、仕様を一切置かない。

## 背景

### 解く問題

今は、仕様のツリー `spec-dock/initiatives/` を、既定のブランチとすべての作業ブランチが追跡している。そのため、次のことが起きている。

- 仕様の最新の状態が、worktreeとブランチごとに分かれ、中央で全体を把握できない。
- ほかのworktreeの書きかけや、マージ前の更新が見えない。反映にはPRのマージが必要になる。
- ブランチを消すと、そのブランチにしかない仕様が失われる（孤児のScope）。
- 構造の情報が `.meta.json` にだけあり、GitHub と食い違っている。GitHub には親子も依存も登録されていない。`.meta.json` の題名は、GitHub の題名と spec-dock で36件、退去費用で62件食い違う。

### 利用の実態（このPC、2026-10-25 時点）

- 仕様の編集は286回。そのうち263回が、Orca や Codex の作業用worktreeの通常のセッションによるもので、mainのチェックアウトからは23回、隔離されていないサブエージェントからは3回だった。
- Claude Code の隔離セッション（`--worktree`）は、一度も使われていない。

### 関係者

- 利用者（人）：仕様を確認し、判断し、PRをマージする。HTMLの説明資料で議論する。
- エージェント（Claude Code、Codex。Orca から起動されることが多い）：仕様を読み書きし、コードを実装する。
- SpecDock の利用者のリポジトリ：spec-dock（このリポジトリ）、退去費用プロダクト、housing-lifecycle、company-os。
- 複数のPC：同じリポジトリを、別々のPCで同時に扱う。

### 前提とする検証

検証した事実は、Artifact [検証済みのGitとGitHubの挙動](artifacts/20261025t080353z-research-verified-git-github-behaviors.md) にまとめた。先行の分析と設計の草案（v0.8）は、同じ `artifacts/` にある3つのHTML資料で、証拠として扱う。

## 観測可能な要件

### A. 正本の置き場

- **R-A1 内容の正本**：仕様の内容は、`spec-dock/canonical` ブランチだけに置く。このブランチは、既定のブランチと共通の祖先を持たず、仕様のツリーと、SpecDock が管理する少数のファイル（無視の設定、正本であることを示す README、形式の版）だけを含む。
- **R-A2 構造の正本**：番号、種類、親子、依存、状態、題名は、GitHub Issue だけに置く。親子は sub-issue、依存は blocked by、種類はラベル（`spec-dock:initiative`、`spec-dock:epic`、`spec-dock:issue`）、識別名（slug）は本文の印で表す。`.meta.json` は廃止する。
- **R-A3 入れ子は写し**：canonical のディレクトリの入れ子は、GitHub の親子を見やすく写したものとする。両者がずれたときは GitHub に合わせる。人やエージェントが手でディレクトリを動かしても、正本の変更とは見なさない。
- **R-A4 既定のブランチに仕様を置かない**：既定のブランチと、そこへ入るPCのツリーには、`spec-dock/initiatives` と `spec-dock/.canonical` の下のパスが1つもない（ファイル、リンク、gitlink を含む）。違反は、コミットの前、PR、マージの後のそれぞれで検出される。
- **R-A5 同期の向き**：canonical から既定のブランチへは、同期もコピーもしない。既定のブランチの変更を canonical へマージすることもしない。SpecDock の変更が canonical に必要なときは、形式の版を上げる一方向の更新でだけ届く。

### B. ローカルの作業環境

- **R-B1 常駐カタログ**：クローンごとに1つ、mainのチェックアウトの `spec-dock/.canonical/` に canonical のworktreeがある。誤って消されないよう保護され、Git では追跡も表示もされない。mainのチェックアウトがない構成（bare）は対象外で、理由を示して止まる。
- **R-B2 リンク**：すべてのチェックアウトの `spec-dock/initiatives` が、常駐カタログを直接指すリンクになる。mainのチェックアウトでは相対、作業用のworktreeでは絶対のパスを使う。リンクのリンクは受け付けない。リンクはGitで管理しない。
- **R-B3 用意は1つの入口に集める**：常駐カタログ、リンク、除外の設定、定期の同期の登録は、SpecDock の1つの操作（取り付け）が作る。何度実行しても結果は同じになる。プロジェクトの `make init`、SpecDock のコマンドの実行、定期の同期、明示の実行のどれから呼んでも、同じ操作が動く。
- **R-B4 新しいworktree**：Orca、Codex、`git worktree add`、SpecDock のどれで作ったworktreeでも、最初の SpecDock のコマンドか、次の定期の同期までに、リンクが張られる。
- **R-B5 壊れたときの診断と修復**：診断の操作が、置き場所、保護、リンク、無視の設定、権限、未保存・未push、形式の版、GitHub とのずれを調べ、直し方を示す。修復できるものは、取り付けの操作で直る。
- **R-B6 取り外し**：SpecDock を外す操作は、未pushの変更がないことを確かめてから、リンク、常駐カタログ、除外の設定、定期の同期の登録を外す。破壊的な操作なので、対象と結果を明示した指示がいる。
- **R-B7 ツールの権限**：作業用のworktreeで動くエージェントが、カタログに書けるようにする。Claude Code と Codex に加える設定は、診断の操作が正確に示す。

### C. 保存と同期

- **R-C1 定期の保存**：PCごとに常駐する定期の実行が、カタログの変更を、誰が書いたものかに関係なく保存して push する。既定の周期は60秒で、変更のない周期はコミットしない。保存の経路はこの1本だけで、Claude Code のフックは使わない。
- **R-C2 書きかけの扱い**：30秒以上変わっていないファイルを保存する。変わり続けるファイルも、5分たてば保存する。
- **R-C3 先着優先**：push の前に必ず取り込む。後から push する側が差分を解消する。同じファイルが競合したときは、先に push された版を元の名前に残し、後から push する側の版を `<名前>.conflict-<PC名>-<時刻>.<拡張子>` として隣に保存する。変更と削除がぶつかったときは、変更を残す。
- **R-C4 作業ツリーを壊さない**：作業中のカタログに、競合のマーカーやマージの途中の状態を残さない。rebase と強制 push は使わない。
- **R-C5 保留**：大量の削除、秘密情報らしいもの、大きすぎるファイルは、自動では保存しない。保留して知らせる。CLIが許可した削除は保留しない。
- **R-C6 見える化**：状態を表示する操作が、未保存、未push、保留、競合、最後に成功した時刻を示す。push していないコミットが10分を超えると警告する。
- **R-C7 リモートの書き換えを受け入れない**：GitHub の canonical が、最後に確認した版の子孫でなくなったら（強制 push や削除）、同期は取り込まずに止まり、知らせる。
- **R-C8 共有のフックを避ける**：カタログのコミットでは、リポジトリのコード用のフック（`pre-commit` など）を動かさない。

### D. 同時に動く操作

- **R-D1 PCの中の排他**：定期の同期と、カタログに書く SpecDock の操作は、互いの途中の状態を保存しない。ディレクトリの移動とリンクの書き換えは、1つの単位として保存される。
- **R-D2 ネットワークを待たせない**：排他の中では、ネットワークを使わない。排他を持つ時間は短くし、ほかの操作を長く待たせない。
- **R-D3 コミットは同期だけ**：SpecDock の操作は自分でコミットせず、操作の記録を残して同期に任せる。サンドボックスで動くエージェントから実行しても、同じ結果になる。
- **R-D4 PCの間に排他を置かない**：PCどうしの調整は、R-C3 の先着優先だけで行う。

### E. 名前

- **R-E1 識別と表示を分ける**：ID と slug（英小文字・数字・ハイフン）は、ディレクトリ名とブランチ名に使い、作成したときに固定する。表示名（GitHub の題名）は、日本語を含む任意の言語でよく、いつでも変えられる。
- **R-E2 日本語の題名を受け付ける**：Scope の作成で、日本語の題名を受け付ける（今の CLI は英数字しか受け付けない）。題名に英数字以外の文字が含まれるときは、slug の指定を必須にする。
- **R-E3 表示**：ダッシュボードと CLI の表示は、GitHub の題名を使う。題名を変えても、slug、ディレクトリ名、ブランチ名は変わらない。

### F. 移行

- **R-F1 移行の道具**：`.meta.json` から GitHub への構造の登録、検証、切り替えを、一時的な CLI のコマンドで行う。既定は予定の表示だけで、何度実行しても同じ結果になる。足すだけで消さず、取り消しの一覧を残す。GitHub の書き込みの制限を超えない速さで進む。
- **R-F2 先に登録できる**：GitHub への登録は、切り替えより前に済ませられる。登録しても、今の CLI での運用は壊れない。
- **R-F3 移行前のブランチ**：移行前に作ったブランチの仕様は、マージの前に canonical へ取り込める。取り込んだ後、ブランチから仕様のツリーを外し、PRを仕様を含まずにマージできる。
- **R-F4 データの異常を見つける**：移行の予定の表示は、循環する依存、種類の規則の違反、閉じた親の下の開いた子、ID と番号の不一致（`init-local-00002` は #39、`init-local-00003` は #31）、GitHub との題名の食い違いを一覧にする。
- **R-F5 形式の版**：canonical は形式の版を持つ。CLI は、版が古ければ更新を案内し、自分より新しければ書き込みを止める。

## スコープ

### 対象

- 仕様の内容と構造の正本の分離と、その移行（R-A、R-F）。
- ローカルの作業環境の用意、診断、修復、取り外し（R-B）。
- 定期の保存と同期、競合の解決、保留（R-C）。
- SpecDock の操作の排他（R-D）。
- 識別名と表示名の分離（R-E）。
- 既定のブランチに仕様が入らないことの強制（R-A4）。
- 上を支える CLI の変更、配布資産、利用者向けの文書、エージェント向けの規則（AGENTS.md とスキル）。

### 対象外

- Codex のクラウドからの書き込み。
- Claude Code の隔離セッション（`--worktree`）からの仕様の書き込み。隔離セッションでは仕様を読むだけにする。
- mainのチェックアウトがない構成（bare）、Windows。
- PCをまたぐ排他。
- canonical から既定のブランチへの同期と、GitHub Actions による canonical への書き込み。
- canonical に置くCIの定義。

### Issue へ渡す境界（候補）

計画書で確定する。候補は次のとおり。

1. GitHub の構造の読み書き（sub-issue、blocked by、ラベル、本文の印）と、`.meta.json` に頼らない読み取り。
2. 移行の道具（予定、登録、検証、切り替え、移行前のブランチの取り込み）。
3. 常駐カタログとリンクの取り付け・診断・修復・取り外し。
4. 定期の保存と同期（先着優先、保留、見える化、定期の実行の登録）。
5. 排他と、SpecDock の操作の書き方の統一。
6. 既定のブランチの強制（検査、PRのCI、マージ後の見張り）と、形式の版の更新。
7. 識別名と表示名（日本語の題名、テンプレート、ダッシュボード）。
8. 各リポジトリへの展開。

## 失敗・境界条件

- **mainで移行前のコミットへ移る**：リンクが実体のディレクトリに置き換わる。常駐カタログは残る。戻ったときに、取り付けがリンクを作り直す。
- **`git clean -ffdx`**：常駐カタログが消える。保存済みのコミットは `.git` に残る。失うのは、最後の保存の後の編集だけ。取り付けが作り直す。
- **mainのチェックアウトの移動や改名**：worktree の登録と、作業用のworktreeの絶対パスのリンクが切れる。診断が直し方を示し、取り付けが張り直す。
- **外付けのボリュームが外れている**：定期の同期は何も変えずに失敗し、記録だけを残す。
- **同じPCに同じリポジトリのクローンが複数ある**：クローンごとに常駐カタログがあり、互いには GitHub を通して同期する（今、退去費用のクローンが2つある）。
- **作業用のworktreeの削除**：リンクだけが消え、カタログは残る（確認済み）。
- **ネットワークの断絶や認証の失敗**：コミットはローカルに積まれ、つながったときに push される。長く続いたら警告する。
- **同じファイルの同時編集**：R-C3 で解決し、編集は失われない。後から push した側の作業中のエージェントには、文書が先着の版に変わって見える。
- **SpecDock の版がPCごとに違う**：R-F5 で、古い版のPCが書き込みを止める。
- **GitHub の保護の制約**：退去費用は非公開で無料のプランのため、ルールセットとブランチの保護が使えず、PRの検査でマージを止められない。canonical の削除や強制 push も、GitHub 側では防げない（R-C7 で検出する）。
- **Scope でない Issue**：退去費用には、Scope でない Issue が500件以上ある。種類のラベルのない Issue は、Scope として扱わない。
- **GitHub の題名の手作業の変更**：表示が変わるだけで、識別名は変わらない。

## 受け入れ条件

- **AC-01**：spec-dock と退去費用で、移行後の既定のブランチのツリーに、`spec-dock/initiatives` と `spec-dock/.canonical` の下のパスが1つもない。
- **AC-02**：移行後、作業用のworktreeで保存した仕様が、同じPCの別のworktreeから保存の前にも読め、別のPCからは最大およそ2分以内に読める。
- **AC-03**：2台のPCで同じファイルを同時に編集しても、両方の内容が残り（片方は別名ファイル）、どの作業ツリーにも競合のマーカーが残らない。
- **AC-04**：移行の前後で、全Scopeの番号、種類、親子、依存が一致する。移行後、`.meta.json` が1つも残っていない。
- **AC-05**：移行前のブランチの仕様を取り込んだ後、そのPRが仕様を含まずにマージできる。
- **AC-06**：新しく作ったworktreeで、最初の SpecDock のコマンドの後に、仕様を読み書きできる。
- **AC-07**：`git clean -ffdx`、mainのチェックアウトの移動、移行前のコミットへの checkout の後、診断が原因と直し方を示し、取り付けで元に戻る。
- **AC-08**：日本語の題名で Scope を作れる。ディレクトリ名とブランチ名は英語の slug になり、ダッシュボードには日本語の題名が出る。
- **AC-09**：大量の削除が、自動では push されない。
- **AC-10**：canonical が強制 push で書き換えられたとき、各PCの同期は取り込まずに止まり、知らせる。
- **AC-11**：既定のブランチへ仕様を入れるPRは、spec-dock ではマージできず、退去費用では検査が失敗として表示される。

## 制約・前提

- Linux と macOS、Python 3.10 以上。Git は `merge-tree --write-tree` が使える版（2.38 以上）が要る。手元は 2.54.0。
- GitHub の個人アカウント。Issue types と push のルールセットは使えない。非公開のリポジトリでは、ルールセットとブランチの保護も使えない。
- GitHub の書き込みの制限は、目安で毎分80回、毎時500回。
- 人がPRをマージする関門を残す。エージェントは、マージできる状態のPRで止まる。
- 今の CLI の契約（直接の選択、StartLock、Artifact の命名、失敗したら止まる境界）を壊さない。
- SpecDock の操作が、利用者のホストの設定（`.claude/settings.json` など）を勝手に書き換えない。
- dogfooding の規則：提供側のソース（`src/spec_dock/`）を先に変え、配布されたものを `spec-dock/` で確かめる。

## 未解決事項

エージェントが推奨案で仮に決めたもの（異議があれば変える）。

- slug を、GitHub の本文の末尾に、画面に出ないHTMLコメントの印として持つ。
- テンプレートから `タイトル:` の写しを外す。
- 移行の道具は、一時的な CLI のコマンド群とし、全リポジトリの移行が終わったら削除する。
- 移行前のブランチは、マージの前に取り込み、PRの検査で止める。マージ後に動く Action は使わない。
- SpecDock の変更は、形式の版と一方向の更新で canonical に届ける。
- canonical にCIの定義を置かない。
- この Epic は、親の `init-local-00003`（#31）が閉じていたため、新しい Initiative `init-00423` の下に作った。

利用者の判断が必要なもの（ヒアリング）。

- **H-1 展開の範囲と順序**：spec-dock を最初に移行し、確かめてから退去費用へ広げる。housing-lifecycle と company-os を、この Epic に含めるか。
