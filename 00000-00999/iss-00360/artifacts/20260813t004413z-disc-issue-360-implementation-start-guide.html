1. 最初に結論

Issue 357〜359で、SpecDockの中核はすでに「Storage Core」「薄いAuthoring Kit」「二つのrepo-local skill」へ絞られました。しかしproviderの配布ツリー、installer、dogfood workspace、package、既存consumerには、旧Planning・Review・Execution・Assurance・Profile・PR orchestrationの物理ファイルや導線が残っています。

Issue 360は、その残存物を配布の全surfaceから一度に切り替える最後のvertical sliceです。新規利用者には新しいTargetだけを配り、既存利用者からはSpecDock所有と証明できる旧ファイルだけを除去します。

最重要の安全原則: パス名やworkspace markerだけで「SpecDock所有」と推定しません。所有を証明できない同名ファイルは保持し、書き込み開始前にoperation全体を停止します。

2. この資料で分かること

  • Issue 360が解決する配布上の問題と、357〜359との境界
  • Target・obsolete・preserveの三分類と、所有権を判定する規則
  • Fresh init、update、init --force、uninstallの正常系
  • symlink、hard link、途中失敗、root差し替えを含む停止条件
  • S00〜S99とH10をどの順番で進め、何を証拠に完了とするか

このHTMLは説明用Artifactです。実装上の判断が食い違う場合は、承認済みのrequirement.md、design.md、plan.mdを優先します。

4. 先に知っておく三つの分類

Target — 今後配るもの

Storage Core、薄いAuthoring Kit、二skill、Storage Core用CI、rootのspec shortcutです。Currentな物理provider treeが正本です。

Obsolete — 退役候補

旧planning runtime、旧docs/template、旧18 + legacy 3 skill、adapter、agent shim、agent-driven workflowです。exact fileと既知identityの両方が必要です。

Preserve — 必ず守るもの

initiatives/**配下のR/D/P/Report、Artifact、Discussion、ADR、assurance、unknown file、利用者所有のskill/config/workflowです。

7. 失敗時はどう止まり、どう回復するか

      

        
Preflight block
unknown ownership、Current collision、unsafe path、symlink parent、directory conflict、hard link mutationは、書き込み前に停止します。

        
Apply中の失敗
失敗phase、完了済み・未完了action、相対path、同じoperationの再実行commandを返します。

        
Post-verify失敗
versionを確定せずmarkerを保持します。成功と表示せず、同一root・同一packageでforward retryします。

9. 実装の進め方

      
計画は安全機構を先に閉じ、その後に配布物を切り替えます。各stepは「REDまたは事前観測 → bounded GREEN → 検証 → report evidence → fresh review → commit / approved-no-op → clean確認」で完結させます。

      
段階1: 入場と安全基盤

      
S00 gateS10 inventoryS20 manifest validationS25 classifierS30 no-follow applyS35 version/retry admission

      
所有権inventory、path validation、衝突分類、TOCTOU対策、version/marker admissionを先に固定します。S10前にmanifest/prune logicを書かず、S30/S35が閉じる前にmutationを接続しません。

      
段階2: Providerの物理cutover

      
S40A legacy runtime retirementS40B Target catalog cutover

      
旧planning backendと専用testを物理削除し、docs/template/skill/workflowをTarget allowlistへ縮小します。

      
段階3: Consumer operation

      
S45 FreshS50 updateS55 prune/preserveS60 forward retryS65 uninstall dry-runS70 uninstall apply

      
同じclassifierとapplyを再利用して、正常系、negative case、preservation、故障注入を閉じます。

      
段階4: 配布全体の証明

      
S80 package parityS85 installed smokeS90 docsS95 verificationS99 3 reviewersH10 IC-3 handoff

      
wheel/sdistから隔離consumerを作り、working checkoutへfallbackせず、357〜359の代表契約とremoved surface不在を検証します。最後はQA・code・specの三者passを必須とし、H10はIC-3判断材料を渡すだけです。

    


    

      
10. テストと完了判定

      
受け入れ条件は22項目、追加の安全・scope closureは15項目です。後段テストの成功で前段の失敗を隠さず、各Closure IDをIssue reportへ一対一で記録します。
