01　何を直し、何を残すのか

SpecDockは、Initiative・Epic・Issueの三階層で仕様、依存関係、成果物を管理するPython製CLIです。providerの src/spec_dock/ は製品のソースで、spec-dock/ はこのrepository自身がSpecDockを使うためのデータです。この二つの役割を混同しません。

利用者の環境では、./spec -h が engine control is missing or invalid で止まっています。基準実装のshimも、helpを外部CLIへ渡す前に独自engine/controlを確認します。helpを読む段階までこの管理状態に依存することが、今回取り除く問題です。ただし、利用者端末でcontrolがなくなった直接原因を、この文書生成環境で再現したわけではありません。

新しい方式では、通常のwheelをcheckout外へインストールし、spec-dock を必要なときだけ起動します。main worktreeを制御拠点にはしません。一方、「どのScopeを作業対象にしているか」は各worktreeに最小限残します。作業対象の記憶まで捨てる変更ではありません。

残すこと取り除くこと
三階層、既存ID、依存、仕様・Artifact・Workbench独自採番台帳、共有branch binding台帳、全worktreeの登録名簿
branch作成・checkoutを含むStart、完了・Closeを含むFinish固定engineのlocator/control必須化、永続operation journal、自動resume/rollback
一worktree一対象、同じ直接対象の二重開始防止、複数対象のSync表示daemon、常時監視、初期cache、通常編集全体のロックや権限制御

基準経路と変更の根拠：external_cli、shim、新旧authorityの区別。

02　なぜengineとcontrolが追加されたのか

旧方式にも解こうとした問題がありました。CLI自身のソースをcheckout内から読むと、コマンドの途中でbranchを切り替えた後、まだ読み込んでいないmoduleだけが別版になるおそれがあります。#409の設計D-02は、このコード混在を避けるため、checkout外の固定engineを採用しました。

さらに、branchとScopeの対応をtracked metadataへ書くと、それだけで作業treeがdirtyになり、checkoutを妨げます。D-08はその対応をGit common-dirのregistryへ移す理由を示しました。D-09とD-13は、共有controlと各worktreeのactiveを分け、登録worktreeの互換性や書き込み許可を判定する仕組みを定めました。

旧要素実際の役割今回の扱い
engineの実体checkout外に置いた実行コード。処理を行う本体通常のインストール済みpackageへ統合する
engine.json（locator）どこにある実体を、どのdigestで使うかの案内通常起動では不要にする。これ自体は実行コードではない
control.jsonmode、世代、登録worktree、互換性などの制御状態新しい中央controlを設けない
active / registry前者は作業対象、後者は採番・削除記録・任意branch対応直接対象一件だけを各worktreeに残し、共有台帳はなくす
journal / writer lock複数段階操作の中断復旧、広い書き込みの直列化journalはなくす。排他はStartの短い区間だけにする

例えば旧Startの新branch経路は、branch作成、registryへの対応保存、checkout、選択保存という段階をjournalへ記録していました。復旧を自動化するためには、その段階や前像も維持する必要がありました。journalは単なる表示用cacheではありません。

今回もコードをcheckout外に置く狙いは残します。ただし、通常の外部インストールを使うので、SpecDock独自の固定配布物をもう一度作る必要はありません。復旧は「現物を確認して、新しい明示操作を行う」方式へ変え、失った過去の送信意図まで自動復元する保証は手放します。

03　状態を三つに分けて読む

「作業中」という一言では、違う種類の状態が混ざります。この設計では、次の三つを別々に表示します。

状態意味意味しないこと
作業対象として選択中そのworktreeに直接対象の記録が一件ある人が今キーボードを操作している、Codexが稼働している
GitHubのOpen / Closedと理由今回確認したIssueの状態。completed、not-planned、unknownを区別する選択されているだけで完了した、Closedなら必ずcompleted
Codexプロセス稼働この版では観測しない。表示値はnot_observed選択日時やPIDの推測による稼働確認

例えばGitHubがcompletedになっても、別の作業場所に選択記録が残ることはあります。Syncは両方をそのまま示します。その記録を見て「依存条件が満たされた」とは判定しません。依存先自身がcompletedであるという確認が必要です。

直接対象とは、今そのworktreeが一つだけ選んでいるScopeです。Issueを選んだときに表示される親EpicやInitiativeは文脈であり、同時に三つの対象を取得しているわけではありません。main worktreeはcloneの最初の作業場所で、mainというbranch名とは別です。

unknownは、状態や操作結果を確認できていないという意味です。「存在しない」「未送信」「完了した」のどれにも置き換えません。staleは、選択記録はあるものの、現在のcheckoutの対象・linkageなどと一致を確認できない状態です。

プロセスが終了しても、時間がたっても記録は残ります。逆にignoredファイルを強制cleanや手削除で失った場合は、台帳から復活させません。Gitとremoteの現状を確認し、新しいStartで選び直します。

05　Startはbranch操作まで行う



work start は、記録だけを置くコマンドには縮小しません。対象と依存を確認し、必要ならbranchを作り、checkoutしてから選択を確定します。三階層のどのScopeにも使えます。


新しいbranchを作るときは --base が必要です。名前を省略すれば従来と同じ <Scope ID>-<slug> を候補にします。既存branchを使うときは --branch で名前を明示し、--base は付けません。共有binding台帳による自動判定をやめる代わりに、利用する名前を確かめます。


# 未実装の新仕様例：対象を含むcleanなcommitから新branchを作る
spec-dock work start iss-00413 --branch fix/external-cli --base HEAD --dry-run --json
spec-dock work start iss-00413 --branch fix/external-cli --base HEAD --json

# 既存branchを再利用するとき（現物確認後、--baseなし）
spec-dock work start iss-00413 --branch fix/external-cli --json


importや資料編集でtracked差分がある場合、Startが自動stashやcommitを行うことはありません。通常Gitで必要な保存を済ませ、切替先commitにもScope/祖先が存在するようにしてから進みます。

06　Finishは完了とCloseを行う



work finish TARGET --yes は対象をcompletedにし、GitHub-backed ScopeならIssueをCloseします。単なる中断、選択解除、引継ぎをFinishとは呼びません。終了後も現在branchに留まり、自動checkout、branch削除、commit/push/mergeはしません。


親を完了するには、必要な子孫自身のcompletedを確認します。Open、unknown、not-plannedの子を完了済みに数えません。GitHubが既にcompletedなら余計なPATCHを送らず、その時点の条件を確認します。真正の旧local backendが他consumerに残る場合の既存データ保全は、GitHubをCloseした実績と区別します。


# 未実装の新仕様例。製品の完了判断と確認後だけ実行する
spec-dock work finish iss-00413 --dry-run --json
spec-dock work finish iss-00413 --yes --json

# 中断だけなら既存の解除を使う。IssueはCloseしない
spec-dock active clear --all

09　失敗したときに何が残るのか



「成功か失敗か」だけでは、GitやGitHubに何が起きたか分かりません。新CLIは確定した効果、未実施、失敗、不明を分けて返します。effects は今回の返答内の説明であり、次のprocessが読む永続journalではありません。


失敗点残るもの結果と次の確認
重複、readiness、lock待ちで停止Gitも選択も変更しない原因を直し、新しいStartを行う
branch作成成功後、checkout失敗新branch。旧選択があればそのままpartial / exit6、started=false。Git原文とref/HEADを確認する
checkout成功後、記録公開失敗現在branchと成功済みGit効果partial。自動で元branchに戻さず、active showとGitを確認する
明示切替で旧記録解除後、新記録が保存できない現在branch、選択は空になり得る解除成功と公開失敗を別effectで返す。旧選択を自動復活しない
Closeの応答・確認が不明選択は残す。remoteは完了したかもしれないunknown / partial6。現GitHubを確認して新しい明示操作へ
Close成功後、選択解除が失敗GitHubはcompleted、選択が残り得るpartial6。次の明示FinishはcompletedをGET確認し、不要な再PATCHをしない
強制停止で返答も失った停止点までの現物だけ次processは過去intentを知らない。自動resume/rollbackしない


Gitの原文を隠さない


例えば、事前確認後に外部編集が入り、checkoutが次のようなエラーを返した場合です。これは説明用のfixtureであり、利用者端末で今回取得したエラーではありません。


error: Your local changes to the following files would be overwritten by checkout:
    spec-dock/workspace.json
Please commit your changes or stash them before you switch branches.
Aborting


この文面を単に「checkoutに失敗しました」に置き換えません。text modeでは原文をstderrへ示します。JSON modeではstdoutを一個のJSONに保ち、原文を error.details.git.stderr に改行ごと保存し、制御下のstderrは空にします。GitのreturncodeとCLIのexit_codeを分けます。branchが既に作られていれば、Gitがexit1でもCLIはpartialのexit6です。


認証tokenやURL内の秘密だけは最小限秘匿し、秘匿したことを明示します。通常のGit文面やpathを一律に削りません。UTF-8に変換できないbyteを置換した場合も、その事実を別fieldで示します。


例外を隠して全体の成功にしない


通常編集へ全writerロックを掛けないため、複数metadataの同時編集全体を一つのtransactionにはしません。公開前のsnapshot確認、無上書き公開、後続validateで不整合を検出し、事後の競合はpartialとして現物を示します。Startの重複開始防止と、任意の非協調編集まで完全に防ぐことを区別します。

10　IDと既存データを守る



正式な新しいInitiative・Epic・Issueは、GitHubのcreateまたは既存Issueのimportで作ります。独自の最大番号+1、予約台帳、UUID、オフライン正式発行は追加しません。GitHubが番号を確定するまでは、正式Scopeを公開しません。


Issue #413を新規形式でimportする場合、IDは iss-00413 です。prefixは階層を表し、番号は5桁以上に整形します。既存IDはこの規則へ無理に付け替えません。


守る対象具体的な扱い
既存IDとGitHub linkageIDのlocalという綴りからbackendやGitHub番号を推定しない
schema3のScope metadata不要な全件schema bump、ID/path/親子/依存の改名をしない
workspace.jsonschema3のままwriter_protocolだけを明示切替。存在する旧control_epochだけ除く
未知の任意field・欠けている任意field既存値を保持する。元々ないtitle/project_linkageを架空補完しない
削除の履歴旧tombstoneは必要なら人間向けに保全。新CLIの永久再import禁止台帳にはしない


添付のCodex記録では240件の現metadataはschema3/backend githubです。init-local-00002 はGitHub #39、init-local-00003 は#31に紐づきます。localという綴りがあるだけで、ローカル発行の新規要件へ戻してはいけません。本生成環境で240件全てのbytesを取得・再検査したわけではないため、実装後の保全試験で全件照合します。


現在の一treeに同じIDやGitHub参照が二重登録されていないかは検査します。ただし別branchに同じScopeが存在するのはGitのversionコピーです。全branch履歴を監視する独自台帳を復活させません。

11　controlなしの環境から切り替える



復旧のために旧controlを作り直すことを、移行の前提にはしません。新しい通常CLIでhelpと安全なreaderを成立させた後、許可された対象にだけ切替を適用します。これは製品実装とは別の実環境作業です。


  1. 対象と実行物を確認します。同じclone、適用するworktree、外部console、candidate sourceとwheelを確認します。
  2. 旧writerを止め、実体を保全します。仕様、ignored成果物、旧active、必要なregistry/journal、static資産をcheckout/Git外に保存し、復元して比較します。
  3. controlなしで診断します。旧記録は読取りに限定します。未知のremote結果を人が照合し、影響を特定できなければ適用を止めます。
  4. workspace宣言だけを切り替えます。dry-run後にbefore bytesを確認し、schema3を保ったまま新writer_protocolへ移ります。全Scope bytesは変えません。
  5. static資産と旧入口を整えます。既知のtool-owned fileだけを明示更新し、未知改変は人間が比較します。
  6. 既存#413を正式importし、資料を移します。新規createではなく既存Issueを取り込み、CLIが返したpathを使います。


# 未実装の新仕様例：最初は無変更のplanを確認する
spec-dock workspace migrate --to-schema 3   --to-writer-protocol specdock.worktree-writer/v1 --dry-run --json

# 既存Issueを取り込む例。適用直前に親と重複を再確認する
spec-dock scope import github issue gh:chemitaro/spec-dock#413   --parent epic-00356 --title "External CLI State"   --slug external-cli-state --dry-run --json


旧activeは自動で新記録へ移しません。それを行うと、Startの重複確認を通さず新しい直接対象を取得してしまうためです。最後の意図を保全してから、現在のGit状態を確認し、新しい明示Startで選び直します。


復旧Issueについて許可された例外配置は docs/issue-plans/iss-00413-external-cli-state/ です。正式import後は生成されたScopeへ資料を保全移動し、旧場所は案内だけにします。Codexが持つ report.md と interview-worktree-start.md は本ZIPに含めず、隣に残す前提です。差替え処理で消したり、新しく作り直したりしません。


import後はtracked差分を通常Gitで保存する必要があります。対象・祖先を候補commitに含め、clean条件を満たしてからStartを確認します。import、資料移動、Start、最終Finishは別の証拠です。資料を置いただけで#413を完了扱いにしません。


移行に失敗したら現物とbackupを比較します。sourceをrevertしてもGitHubの効果まで戻るわけではありません。後続編集やremote結果を無視した自動rollback、旧writerの無条件再開は行いません。実行条件と具体的停止点は移行runbookで確認できます。
